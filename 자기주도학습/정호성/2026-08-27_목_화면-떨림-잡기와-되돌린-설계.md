# 학습 일지 — 2026-08-27 (목) ②

## 오늘의 목표

①에서 만든 헤드트래킹 데모는 동작 자체는 금방 됐다.
문제는 **화면이 심하게 떨린다는 것**이었다.

손톱만한 랜드마크 노이즈도 절두체를 통과하면 화면 전체가 출렁인다.
오늘 시간의 대부분을 여기에 썼고, 최종 빌드가 **b17**이다. 17번 갈아엎었다는 뜻이다.

---

## 1부. 노이즈를 줄이려고 붙인 것

### (1) 홍채 5점 무게중심

홍채는 중심 1점 + 테두리 4점, 총 5점이 나온다.
중심 하나만 쓰지 않고 5점 평균을 쓰면 노이즈가 약 **1/√5**로 줄어든다.
계산량 차이가 거의 없으므로 사실상 공짜로 얻는 개선이다.

### (2) 3프레임 중앙값

동공간거리를 최근 3프레임의 중앙값으로 쓴다.

평균이 아니라 **중앙값**인 이유가 중요하다.
한 프레임이 튄 값(스파이크)을 평균은 죽이지 못하고 1/3만큼 반영해버리지만,
중앙값은 아예 버린다.

### (3) 머리 회전(요) 보정

고개를 옆으로 돌리면 두 눈 사이의 화면상 거리가 짧아진다.
그러면 시스템이 "멀어졌다"고 착각해서 z가 밀린다.

해결은 랜드마크 z(깊이)까지 써서 **3D 거리**를 재는 것이다. 3D 거리는 회전에 불변이다.

```js
const dist3D = Math.hypot(bx-ax, by-ay, dzPx);
const ratio  = Math.min(1.3, dist3D / dist2D);      // 회전 보정 계수
this._rotRatio = this._rotRatio*0.85 + ratio*0.15;  // 느린 EMA
eyeDistPx = dist2D * this._rotRatio;
```

랜드마크 z 자체는 노이즈가 커서 그대로 쓰면 안 된다.
**비율만 뽑아 좁게 클램프하고 느린 EMA로** 써야 한다.
그러지 않으면 깊이가 주기적으로 들락거리는 현상이 생긴다.

### (4) 깜빡임 래치

깜빡일 때마다 z가 튀었다. 눈을 감으면 홍채가 무너져 거리 계산이 망가지기 때문이다.

그래서 **두 눈이 모두 떠 있는 프레임의 거리만 신뢰**하고,
감긴 동안에는 마지막 값을 그대로 유지한다.
Blendshape의 blink 값 0.3을 기준으로 판정했다.

### (5) 각도와 거리를 분리해서 필터링 — 가장 중요했다

처음에는 최종 위치(x, y, z)에 필터를 걸었는데 좌우 흔들림이 잡히지 않았다.

원인을 뜯어보니 이것이었다.

```
x = 각도 × 거리
```

x는 **깨끗한 각도**와 **노이즈가 심한 거리**의 곱이다.
위치를 먼저 만들고 필터를 걸면 이미 z 노이즈가 x에 섞여 들어간 뒤라 뺄 수 없다.

그래서 순서를 바꿨다. **각도와 거리를 따로 필터링한 뒤에 곱한다.**

```js
const axF = filters.ax.filter(ax, tSec);  // 반응성 위주 (min_cutoff 0.8)
const zF  = filters.z .filter(zMm, tSec); // 강한 안정화 (min_cutoff 0.12)
const xMm = -axF * zF;
```

각도는 깨끗하니 반응성 위주로, 거리는 지저분하니 강하게 누른다.
필터 계수를 성분별로 다르게 줄 수 있게 된 것만으로 떨림이 크게 줄었다.

**필터는 최종값이 아니라, 노이즈 특성이 다른 각 성분에 따로 걸어야 한다.**
합성한 뒤에는 이미 늦다.

## 2부. 걷어낸 것 — 실패에서 더 많이 배웠다

b17까지 온 이유는 기능을 더해서가 아니라 **넣었다가 뺀 것이 많아서**다.

### 폐기 1. 카메라 축 자동 정렬 회귀

웹캠이 기울어 설치된 것을 온라인 회귀로 자동 보정하려 했다.
그럴듯해 보였는데 결과는 정반대였다.

문제는 **x와 z가 같은 `eyeDistPx`로 나눠진다는 점**이다.
그래서 두 값의 노이즈가 완전히 상관되어 있다.

회귀는 이 상관을 "사용자가 대각선으로 앉아서 생긴 기울기"로 오학습했고,
결과적으로 **z 노이즈를 x에 실시간으로 주입하는 장치**가 됐다.
좌우 흔들림의 직접 원인이 내가 떨림을 잡으려고 넣은 보정기였던 것이다.

> 통계로 무엇인가를 추정할 때는 **입력들이 독립인지부터** 확인해야 한다.
> 공통 분모를 공유하면 노이즈가 상관되고, 회귀는 엉뚱한 것을 배운다.

### 폐기 2. 속도 외삽 예측

카메라는 30Hz인데 화면은 60~120Hz다.
그 사이를 속도로 외삽해서 채우면 지연도 줄어 좋아 보였다.

그런데 계측해보니 **렌더 좌표의 점프가 트래킹 출력보다 4배 컸다.**

원인은 외삽한 값이 새 측정이 들어올 때마다 교정되면서
**카메라 주기마다 톱니**를 만든 것이었다.
트래킹은 매끄러운데 화면만 지저분했던 이유가 이것이다.

대체 방식으로 **임계감쇠 추적**만 남겼다.

```js
const stiffness = 9 + settings.predictMs * 0.15;
const k = 1 - Math.exp(-frameDt * stiffness);
head.x += (sample.x - head.x) * k;
```

오버슈트와 톱니가 원리적으로 불가능한 구조다.
지연이 조금 생기는 대신 화면이 조용해진다.
UI의 "반응 예측" 슬라이더는 그대로 두되 의미를 추적 강성으로 재해석했다.

> **지연을 줄이는 것보다 지연이 일정한 편이 체감상 낫다.**
> 흔들리는 저지연보다 매끄러운 약간의 지연이 낫다.

### 폐기 3. 무보정 목표 (절반만 지켰다)

원래 설계 원칙은 "보정 없음, 제로 컨피그"였다.
물리 모델을 신뢰하면 보정이 필요 없다는 생각이었다.

실제로 돌려보니 웹캠 설치 각도와 화면 크기 오차가 누적되어 시점이 어긋났다.
결국 C키로 기준점을 잡는 것을 **필수 관문**으로 되돌렸다.

새벽에 쓴 README와 오후에 고친 코드가 서로 다른 말을 하고 있는 것이 그 흔적이다.

## 3부. 측정 없이 튜닝하면 끝나지 않는다

위의 폐기 판단을 내릴 수 있었던 것은 계측 장치를 만들었기 때문이다.

`window.__HT`에 카메라 프레임마다 값을 쌓아뒀다(최근 약 30초).

| 기록 항목 | 용도 |
| --- | --- |
| 복원된 mm 좌표 (x, y, z) | 물리 모델이 맞는지 |
| 최종 렌더 좌표 | 필터 이후 실제 화면 값 |
| blink 값, 눈 모드 | 깜빡임 구간 구분 |
| 회전 보정 비율 | 요 보정이 튀는지 |

**트래킹 출력과 렌더 좌표를 같이 기록한 것**이 결정적이었다.
둘을 비교했더니 트래킹은 매끄러운데 렌더만 4배 튀는 것이 바로 보였고,
범인이 외삽이라는 결론이 나왔다.

눈으로 "떨리는데?" 하면서 계수만 만졌다면 b17이 아니라 b40까지 갔을 것이다.

> **체감으로 튜닝하면 끝이 나지 않는다. 재는 장치를 먼저 만들었어야 했다.**
> 오늘 가장 실용적인 교훈이다.

### 곁다리 — 브라우저 캐시에 두 번 속았다

고쳤는데 안 고쳐진 것처럼 보여서 한참 헤맸다. 브라우저가 옛 js를 물고 있었다.

그래서 빌드 번호(`APP_BUILD = "b17"`)를 화면 HUD에 박아뒀다.
화면만 보면 지금 도는 것이 몇 번 빌드인지 바로 알 수 있다.
b17이라는 이름이 그래서 남았다.

### 곁다리 — requestVideoFrameCallback

`requestAnimationFrame`으로 비디오를 폴링하면 프레임이 이미 도착했는데도
다음 rAF까지 기다리게 되어 최대 16ms를 손해 본다.

`requestVideoFrameCallback`은 프레임 도착 즉시 콜백이 와서 그 지연이 사라진다.
코드 몇 줄 바꾸는 것으로 얻는 개선이다.

## 막힌 것 / 의문

1. 임계감쇠로 바꾸면서 지연이 늘었다. 복싱 게임처럼 빠른 동작에서도 감당되는가.
   격투는 반응 속도가 생명이라 부드러움과의 트레이드오프를 어디서 끊을지 모르겠다.
2. 지금은 지연을 체감으로만 판단하고 있다. 실제 ms를 재려면
   화면에 마커를 띄우고 카메라로 찍어서 왕복을 측정하는 방식이 필요할 것 같다.
3. 요 보정 EMA 계수(0.85/0.15)를 감으로 정했다. 근거가 없다.
