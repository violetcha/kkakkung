# 학습 일지 — 2026-08-24 (월)

## 오늘의 목표

전부터 굴리던 **SUNSEAT**(야구장 좌석별 그늘 안내)을 특화 프로젝트 주제로 확장한다.
확장하기 전에 주제의 축 자체가 맞는지부터 다시 검토하고,
팀명·역할 배치·MVP 범위까지 정리한다.

결과물이 **NEXTSPOT**이다.

---

## 공부한 것

### 1. 그늘만으로는 주제가 성립하지 않는다

처음에는 SUNSEAT을 그대로 키우려 했으나, 정리하면서 세 가지 문제를 확인했다.

| 문제 | 내용 |
| --- | --- |
| 결정론적이다 | 그늘은 태양 위치와 3D 구조만 있으면 계산으로 나온다 |
| AI가 필요 없다 | 천문 계산과 그림자 렌더링이지 학습이 들어갈 자리가 없다 |
| 적용 시간이 짧다 | 하루 중 몇 시간, 계절의 절반뿐이다. 야간 경기에는 무의미하다 |

특히 두 번째가 결정적이었다.
특화 프로젝트에서 "AI 영상"을 주제로 잡았는데 정작 영상을 안 봐도 답이 나오는 문제라면,
주제를 잘못 고른 것이다.

따라서 **그늘은 주제가 아니라 환경 레이어 하나로 내리는 것**이 맞다고 판단했다.

### 2. 무엇으로 축을 옮길 것인가

메인 축을 이 질문으로 바꿨다.

> 지금 어디가 붐비고, 30분 뒤에는 어디가 붐빌 것이며, 그러면 언제 움직여야 하는가

이 질문은 **현장 영상이 없으면 답할 수 없다.** 그래서 AI가 들어갈 자리가 분명하다.

그늘과 비교하면 성격이 완전히 다르다.

| | 그늘 | 혼잡도 |
| --- | --- | --- |
| 입력 | 시각, 좌표, 구조물 | 현장 영상 |
| 계산 방식 | 결정론적 | 관측 + 추정 |
| 시간 의존 | 태양 궤도(예측 가능) | 사람의 행동(예측 어려움) |
| 틀릴 수 있나 | 거의 없다 | 자주 틀린다 → 모델이 필요하다 |

"자주 틀린다"는 것이 오히려 프로젝트로서는 장점이다. 풀 문제가 있다는 뜻이다.

한 줄 문구도 여기서 나왔다.
**"30분 뒤 행사장을 미리 보고, 언제 어디로 움직일지 추천받는다."**

### 3. 타임테이블이 예측의 주 입력이다

오늘 정리하면서 가장 확실해진 부분이다.

영상만 보고 30분 뒤를 예측하면 결국 관성 외삽에 그친다.
"지금 이쪽으로 흐르니 계속 흐르겠지" 수준이다.

그런데 행사장 혼잡은 관성으로 움직이지 않고 **이벤트로 튄다.**

```
공연 종료       → 스테이지 앞 인구가 통째로 빠진다
헤드라이너 직전 → 30분 전부터 미리 채워진다
강우           → 지붕 있는 구역으로 몰린다
```

관성 외삽은 이 세 경우를 전부 틀린다.
그것도 조금 틀리는 것이 아니라 방향이 반대로 나온다.

즉 타임테이블은 부가 데이터가 아니라 예측의 주 입력이다.

```
영상        = 현재 상태 관측
타임테이블  = 미래 이벤트
둘을 합쳐야 예측이 성립한다
```

이 구조가 오늘 잡혔고, 이후 설계의 기준이 됐다.

### 4. 좌석이 있고 없고는 UI 차이일 뿐이다

공간 종류에 따라 문제 성격이 달라서 모드를 세 개로 나눴다.

| 모드 | 대상 | 핵심 |
| --- | --- | --- |
| SEAT | 야구장·경기장 (좌석 고정) | 좌석 ID가 이미 있음 → 좌석별 시야·출입구 혼잡·열 노출 타임라인 |
| SPOT | 페스티벌·야외 공연 (자유 이동) | 좌석 없음 → 구역 단위 밀도·경로·출발 시점 추천 |
| OPS | 행사 운영자 | 동선·시설 배치를 바꿨을 때 혼잡이 어떻게 달라지는지 시뮬레이션 |

처음에는 세 개를 따로 만들어야 하는 줄 알았는데, 정리해보니 아니었다.

셋 다 결국 **"공간을 셀로 쪼개고, 셀별 상태를 시간축으로 예측한다"**는 같은 문제다.
SEAT는 셀이 좌석이고, SPOT은 셀이 구역이며, OPS는 그 셀 상태를 반사실적으로
다시 계산하는 것뿐이다.

**엔진은 하나, 셀 정의와 화면만 다르다.**
이걸 알고 나니 범위가 세 배로 늘어나는 것이 아니라는 확신이 생겼다.

## 한 것

### 이름

| 구분 | 이름 | 이유 |
| --- | --- | --- |
| 팀명 | **시공간** | 공간(어디)만 다루는 것이 아니라 시간에 따른 변화까지 함께 보므로 |
| 프로젝트명 | **NEXTSPOT** | 지금 이 자리가 아니라 다음 자리를 알려주는 서비스이므로 |

이름을 먼저 정한 이유가 있다.
"NEXTSPOT"이라고 못 박고 나니 **현재 상태만 보여주는 기능은 자동으로 후순위**가 됐다.
이름이 범위를 자르는 기준 역할을 했다.

### 핵심 기능 정의

- **실시간 공간 상태 지도** — 영상에서 구역별 밀도, 이동 방향, 대기열, 빈 공간 추정.
  개인 식별은 하지 않는다. 필요도 없고 해서도 안 된다
- **미래 지도** — 현재 흐름과 타임테이블을 결합해 30~90분 뒤 예측
- **개인화 위치 추천** — 시야·혼잡도·이동거리·편의시설·체감환경 우선순위 조합
- **이동 타이밍 추천** — 붐비기 전에 갈지, 빠진 뒤에 갈지
- **좌석·구역 통합 모델** — SEAT/SPOT이 같은 공간 엔진 공유
- **운영 시뮬레이션** — 배치를 바꿨을 때 예상 혼잡 비교

여섯 개 중 **"미래 지도"와 "이동 타이밍"이 서비스의 정체성**이다.
나머지는 이 둘을 위한 재료이거나 확장이다.

### 역할 배치

백엔드 2 / 프론트 2 / AI 2로 나눴다.
손주연·정유림 님이 백엔드를 희망해서 그쪽부터 배치하고 나머지를 맞췄다.

| 팀원 | 역할 | 주요 담당 |
| --- | --- | --- |
| 손주연 | 팀장 · Backend Lead | 일정·의사결정, 행사장·사용자·추천 도메인 설계, API 통합 |
| 정유림 | Backend · Data Pipeline | 현장 상태·행사 일정·날씨 수집, 시계열 저장, 예측 결과 파이프라인 |
| 김산이 | Frontend Lead | 지도 중심 웹 화면, 좌석·구역 히트맵, 공통 프론트 구조 |
| 이주헌 | Frontend · UX | 모바일 UX, 시간 슬라이더, 조건 검색, 추천 인터랙션 |
| 오명헌 | AI/CV Lead | 영상 기반 군중 밀도·이동 방향·대기열 분석, 모델 평가 |
| 정호성 (본인) | Spatial AI · Prediction | 행사장 좌표계·3D 구조, 영상 분석 결과의 지도 매핑, 상태 예측·추천 점수 |

배치할 때 신경 쓴 것은 **AI 파트 2명의 역할을 겹치지 않게 쪼개는 것**이었다.

```
오명헌 : 영상 안에서 무엇이 보이는가        (검출)
정호성 : 그것이 지도 위 어디이고,
         조금 뒤 어떻게 변하는가            (매핑 + 예측)
```

검출과 매핑을 한 사람이 다 하면 병목이 되고, 둘 다 검출을 하면 예측이 빈다.
경계를 화면 좌표와 지도 좌표 사이로 그었다.

내 파트는 세 가지로 정리된다.

1. 화면 좌표를 지도 좌표로 바꾼다 (캘리브레이션, 호모그래피)
2. 그 지도를 미래로 민다 (상태 예측)
3. 점수를 매긴다 (추천 스코어링)

### MVP 범위

6주 안에 끝날 선까지만 잘랐다.

- [ ] 기준 공간 **한 곳**만 선정 (야구장 또는 야외 행사장)
- [ ] 사전 촬영 영상으로 구역별 혼잡도·이동 방향 분석
- [ ] 타임테이블을 반영한 30분 뒤 예측
- [ ] 시간 슬라이더로 현재 지도와 미래 지도 비교
- [ ] 시야·혼잡도·이동거리 중 2~3개 조건을 조합한 위치 추천
- [ ] 햇빛·그늘은 선택형 환경 레이어로 간단히 제공
- [ ] 데모: 질문 입력 → 미래 지도 → 위치·이동 타이밍 추천까지 한 흐름

자를 때는 **"데모에서 한 흐름으로 보여줄 수 있는가"**를 기준으로 삼았다.

실시간 스트리밍 처리, 여러 행사장 지원, 사용자 계정, OPS 모드는 전부 뺐다.
멋있지만 데모 30초 안에 안 보이는 것들이다.

반대로 시간 슬라이더는 기능적으로는 사소한데 남겼다.
**"현재 지도와 미래 지도가 다르다"는 것을 눈으로 보여주는 유일한 장치**이기 때문이다.
이 프로젝트의 핵심 주장을 시연하는 부품이라 뺄 수 없다.

## 배운 것

**주제를 키우기 전에 "이게 우리 기술로 풀 문제가 맞나"를 먼저 봐야 한다.**
그늘은 하고 싶었던 것이지 풀어야 할 문제가 아니었다.
계산으로 답이 나오는 것에 AI를 붙이면 결국 포장만 남는다.

**범위를 자를 때는 "중요한가"가 아니라 "데모에서 보이는가"로 자르는 편이 명확하다.**
중요도로 자르려고 하면 전부 중요해 보여서 아무것도 못 자른다.

## 막힌 것 / 의문

1. **정답 데이터를 무엇으로 둘 것인가.**
   "30분 뒤 이 구역이 붐빈다"를 맞췄는지 확인하려면 30분 뒤의 실제 밀도가 필요하다.
   영상만 있으면 30분 뒤 프레임이 곧 정답이 되지만, 그러려면 영상이
   **긴 연속 촬영본**이어야 한다. 이것을 구할 수 있는지가 프로젝트 전체의 전제다.

2. **화면 좌표를 지도 좌표로 바꾸는 캘리브레이션을 어떻게 할 것인가.**
   행사장 도면이 있으면 호모그래피로 풀리는데, 도면이 없는 경우가 문제다.

3. **밀도를 어떤 단위로 뽑을 것인가.** 사람 수인가 m²당 명수인가.
   사람 수는 서로 가려지면 과소 추정될 텐데 보정이 필요하다.

4. "이벤트로 튄다"는 것을 모델에 어떻게 넣을 것인가.
   타임테이블을 피처로 넣는 것과, 이벤트 전후로 모델을 나누는 것 중 무엇이 맞는가.

5. 그늘 레이어를 실제로 붙일 수 있는가. 3D 구조 없이 가능한가.
