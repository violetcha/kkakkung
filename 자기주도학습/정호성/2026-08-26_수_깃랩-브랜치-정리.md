## 막힌 지점 — protected branch

master에 커밋을 올리려는데 push가 거부됐다.
처음에는 내 권한 문제인 줄 알았는데 아니었다.

**GitLab은 기본 브랜치를 protected로 잡아둔다.**

| 동작 | 기본 정책 |
| --- | --- |
| Developer가 기본 브랜치에 직접 push | 차단 |
| Maintainer가 직접 push | 설정에 따라 허용 |
| force push | Maintainer에게도 기본 차단 |

즉 "master를 비운다"는 작업 자체가 정책상 정면으로 막히는 종류의 작업이었다.
비우려면 기존 커밋을 지우거나 덮어써야 하는데, 그것이 정확히 protected branch가
막으려는 행위이기 때문이다.

---

## 어떻게 풀었나

| 선택지 | 판단 |
| --- | --- |
| protected를 해제하고 push | 되기는 하지만 팀 레포의 보호 장치를 내가 임의로 끄는 것이라 부적절하다 |
| 작업 브랜치를 만들어 MR로 병합 | 정석이다. 이쪽을 택했다 |

`chore/empty-master` 브랜치를 만들어 정리 커밋을 올리고, master 반영은 MR로 처리했다.
`study` 브랜치는 protected가 아니라서 바로 push됐다.

커밋 컨벤션은 팀에서 쓰기로 한 형태에 맞췄다.

```
chore: master 브랜치 내용 비우기
docs(이름): 2026-08-XX 학습일지 - 제목
```

## 배운 것

**막혔을 때 우회로부터 찾지 말고 왜 막았는지를 먼저 봐야 한다.**

protected branch는 "설정을 꺼라"는 뜻이 아니라 "MR을 써라"는 신호였다.
설정을 끄고 push했다면 당장은 됐겠지만, 팀 전체의 안전장치를 혼자 해제한 셈이 된다.

에러 메시지를 장애물로 볼 것인지 설계 의도로 볼 것인지에 따라 대응이 완전히 달라진다.

## 막힌 것 / 의문

1. 팀에서 누가 Maintainer인지 정리되어 있지 않다. MR 승인 흐름을 먼저 합의해야 한다.
2. `study` 브랜치도 결국 6명이 동시에 쓰게 되는데, 충돌 방지 규칙이 필요한가.
   폴더가 사람별로 갈려 있어서 지금은 충돌이 안 나지만 규칙은 정해두는 편이 낫겠다.
