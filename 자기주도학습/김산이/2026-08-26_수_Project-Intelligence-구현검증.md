# 학습 일지 — 2026-08-26 (수)

## 오늘의 목표

범용 `Project Intelligence` Skill의 구현 상태를 점검한다.
파일이 존재한다는 사실과 실제로 사용할 수 있다는 주장을 구분하고,
소스·설치본·플랫폼 규격·복구 가능성까지 단계별로 검증한다.

---

## 공부한 내용

### 1. 파일 존재와 동작 검증은 다르다

`SKILL.md`, Mode 문서, Adapter, Template이 있고 YAML이 파싱된다는 사실은 정적 구조가
유효하다는 뜻이다. 하지만 이것만으로 자동 호출, 인자 전달, 필요한 파일의 지연 로딩,
분석 결과 생성까지 동작한다고 말할 수는 없다.

검증 수준을 다음과 같이 분리했다.

| 검증 단계 | 확인할 내용 |
| --- | --- |
| 정적 구조 | Frontmatter, 디렉터리 구조, 상대 링크, Template 형식 |
| 설치 일치성 | 개발 소스와 실제 설치본의 파일·내용 일치 |
| Discovery | 저장소 구성과 사용 가능한 검증 명령 발견 |
| Mode 동작 | 목적별 분석 결과와 근거 생성 |
| 실행 검증 | 가설을 테스트·재현 명령·정적 분석으로 판정 |
| Native 동작 | 대상 Agent에서 자동 호출과 인자 전달이 실제 동작 |
| 범용성 | 다른 기술 스택에서도 Core 변경 없이 동작 |

아래 단계의 검증이 통과했다고 위 단계까지 자동으로 증명되는 것은 아니다.
예를 들어 링크 검사가 성공해도 Native 호출은 별도로 확인해야 한다.

### 2. 소스와 전역 설치본을 해시로 비교한 이유

개발 폴더를 수정했더라도 전역 설치본이 이전 버전이면 실제 Agent가 다른 지침을 읽을
수 있다. 파일 이름과 수정 시간만 확인하지 않고 SHA-256 해시로 내용을 비교했다.

확인 결과 개발 소스와 Claude 전역 설치본의 추적 파일 12개가 모두 일치했고,
상대 링크 오류는 발견되지 않았다.

```text
개발 소스 파일
→ SHA-256 계산

전역 설치본 파일
→ SHA-256 계산

경로와 해시를 함께 비교
→ 12/12 일치
```

이 과정에서 **작성한 파일**과 **실제로 호출되는 파일**이 같은지 확인하는 절차가
필요하다는 점을 배웠다. 설치 과정을 자동화할 때도 복사 성공 메시지보다 파일 목록과
내용 해시를 확인하는 편이 신뢰도가 높다.

### 3. 가설과 판정 상태를 끝까지 유지하기

분석 결과가 많다고 Skill이 잘 동작하는 것은 아니다. 각 Finding에 코드 위치와 근거,
반대 가설, 실행 가능한 검증 방법, 최종 판정이 있어야 한다.

```text
의심 항목 발견
→ 실제 실행 경로 확인
→ 반대 가설 검토
→ 테스트 또는 재현 계획 수립
→ 실행 가능한 범위 검증
→ CONFIRMED / REJECTED / INCONCLUSIVE 판정
```

`REJECTED`는 실패한 분석이 아니라 정상 동작을 수정 대상에서 제외한 결과다.
외부 서비스나 필요한 실행 환경이 없어 확인하지 못했다면 억지로 결론을 내리지 않고
`INCONCLUSIVE`로 남겨야 한다.

### 4. Claude Code와 Codex Skill 규격의 차이

Claude Code용 Frontmatter에서 사용하는 `argument-hint` 같은 필드는 Claude 환경에서는
의미가 있지만 Codex의 Validator가 허용하는 필드와는 다를 수 있다. 한 플랫폼의
Validator 실패를 근거로 다른 플랫폼용 Skill이 잘못됐다고 결론 내리면 안 된다.

Skill을 검증할 때는 다음 순서를 지켜야 한다.

1. 실제 실행 대상 Agent를 확인한다.
2. 대상 Agent의 공식 Skill 규격을 확인한다.
3. 설치 경로와 호출 방식을 확인한다.
4. 해당 Agent에서 Native 실행을 시도한다.
5. 다른 플랫폼에서도 사용할 경우 별도의 호환 계층을 만든다.

현재 환경에는 Claude CLI가 없어 자동 호출, 인자 치환, 필요한 문서만 읽는 동작을
Native 환경에서 확인하지 못했다. 따라서 정적 구조와 설치 일치성은 검증했지만
Native 동작은 미검증으로 남겼다.

### 5. 안정판과 실험 후보를 구분하는 기준

버전 번호가 높거나 구조가 더 복잡하다고 바로 안정판이 되는 것은 아니다.
실제 설치 여부, 반복 검증 결과, 실패했을 때 복구 가능성, Context 비용을 기준으로
현재 사용할 버전과 실험 후보를 구분했다.

| 기준 | 안정판에서 확인할 내용 |
| --- | --- |
| 설치 상태 | 실제 Agent가 읽는 경로에 설치돼 있는가? |
| 구조 검증 | Frontmatter와 상대 링크가 유효한가? |
| 일치성 | 개발 소스와 설치본 내용이 같은가? |
| 검증 경계 | 확인하지 못한 항목을 완료로 표시하지 않았는가? |
| 복구 가능성 | 실험 버전에서 문제가 생겼을 때 되돌릴 수 있는가? |

실험적인 차세대 후보는 활성 버전에서 분리하되 바로 삭제하지 않고 별도 보관했다.
보관 위치에서 추적 대상 67개 파일이 모두 유지되는지 확인해 이후 비교와 복구가
가능하도록 했다.

### 6. 완료율보다 검증 경계를 기록하기

`90% 완성`처럼 하나의 숫자로 표현하면 무엇이 실제로 동작하고 무엇이 추정인지
알기 어렵다. 대신 확인한 항목과 남은 항목을 분리했다.

확인한 범위:

- Frontmatter와 파일 구조 점검
- 개발 소스와 전역 설치본 12/12 해시 일치
- 상대 링크 오류 없음
- 안정판과 실험 후보 분리
- 실험 후보 추적 파일 67/67 보관 확인

아직 확인하지 못한 범위:

- Claude CLI에서 자동 호출과 인자 전달
- 서로 다른 기술 스택에서의 범용성
- 장기간 누적되는 분석 결과의 정리 정책
- 일반 Prompt와 Skill을 같은 조건에서 비교하는 평가

완료 비율보다 이 목록을 남기는 편이 다음 검증 작업을 정하고 결과를 설명하는 데
더 유용했다.
