## 공부한 내용

### 1. MSA에서 Circuit Breaker가 필요한 이유

마이크로서비스 구조에서는 한 서비스의 장애가 해당 서비스에서 끝나지 않을 수 있다.
서비스 A가 장애 상태인 서비스 B를 계속 호출하면 응답을 기다리는 동안 A의 Thread와
Connection도 점차 고갈되고, 결국 정상 요청까지 처리하지 못하는 연쇄 장애가 발생할 수 있다.

Circuit Breaker는 일정 시간 동안의 호출 실패율이나 지연 시간을 관찰한 뒤,
실패가 기준을 넘으면 문제가 있는 서비스를 호출하지 않고 빠르게 실패를 반환한다.

| 상태 | 의미 |
| --- | --- |
| `CLOSED` | 요청을 정상적으로 전달하면서 실패율을 관찰한다. |
| `OPEN` | 대상 서비스 호출을 차단하고 즉시 실패 또는 대체 응답을 반환한다. |
| `HALF_OPEN` | 일부 요청만 보내 대상 서비스가 복구됐는지 확인한다. |

Circuit Breaker를 단순한 예외 처리 기능이 아니라 **장애가 시스템 전체로 번지는 것을
막는 경계**로 이해했다. Spring 환경에서는 Resilience4j 등을 사용할 수 있으며,
Timeout·Retry·Fallback과 함께 적용할 수 있다.

Retry는 일시적인 실패를 다시 시도하는 방법이지만, 이미 장애가 지속되는 서비스에
무분별하게 적용하면 오히려 호출량을 늘릴 수 있다. 따라서 Timeout으로 대기 시간을
제한하고, Circuit Breaker로 반복 호출을 차단하며, 필요한 경우 Fallback으로 제한된
기능을 제공하는 식으로 각 기능의 책임을 나눠야 한다.

### 2. Spring 공식 문서를 AI Context로 활용하는 방법

검색 결과나 요약 글에만 의존하지 않고 Spring Framework 공식 문서를 전체 텍스트로
변환해 AI가 참고할 수 있는 지식 자료로 만드는 방법을 조사했다.

```text
공식 문서
→ 구조가 보존된 텍스트 데이터
→ 필요한 부분 검색
→ AI Context에 주입
→ 답변을 원문과 대조
```

문서 exporter를 직접 실행하는 과정에서는 Spring Framework 소스와 Gradle 관련 임시
디렉터리가 생성됐고, Windows에서 임시 파일을 정리할 때 `shutil.rmtree` 오류가 발생했다.
이를 통해 문서 변환 작업도 운영체제별 파일 잠금과 임시 디렉터리 정리 방식을 고려해야
한다는 점을 알게 됐다.

공식 문서를 텍스트로 만들었다고 해서 답변이 자동으로 정확해지는 것은 아니다.
문서 버전, 원문 위치, 검색 범위를 함께 남기고 AI가 만든 설명을 다시 원문과 비교해야
신뢰할 수 있는 학습 자료가 된다.

### 3. 영상 AI 프로젝트 주제 선정 기준

5~6명이 약 7주 동안 개발할 팀 프로젝트를 가정하고 영상 AI 주제를 탐색했다.
운동 자세 교정, 냉장고 식재료 인식처럼 구현 사례가 많은 주제는 안정적이지만
차별성이 약하다고 판단했다. 반대로 새로움만 강조하면 데이터 확보와 구현 가능성이
떨어질 수 있어 다음 기준으로 후보를 비교했다.

| 기준 | 확인한 질문 |
| --- | --- |
| 사용자 문제 | 누가 어떤 수작업이나 불편 때문에 사용하는가? |
| AI 역할 | 탐지·분류·추적·OCR·매칭 중 무엇을 담당하는가? |
| 서비스 범위 | AI 외에 웹·앱·백엔드에서 구현할 기능이 충분한가? |
| 데이터 | 학습과 검증에 필요한 자료를 현실적으로 확보할 수 있는가? |
| 시연성 | 입력과 처리 결과를 발표 현장에서 바로 보여줄 수 있는가? |
| 구현 위험 | 개인정보·GPU 비용·응답 시간 문제를 감당할 수 있는가? |

스포츠, 일상, 육아, 로컬, 커머스, 교육 등 12개 영역에서 후보 100개를 만든 뒤
사용 장면, AI가 줄여주는 수작업, 시연 효과를 기준으로 범위를 줄였다.

### 4. 구체화한 영상 AI 후보

#### 아기 첫 순간 캐처

홈캠 영상에서 뒤집기나 첫걸음 같은 자세 변화를 감지해 앞뒤 구간을 성장 앨범에
저장하는 서비스다. Pose Estimation으로 관절 좌표를 얻고 상태 변화를 판단하는
방식을 검토했다. 감지 장면을 시연하기 좋지만 가정 내 영상의 개인정보와 오탐을
어떻게 다룰지가 핵심 위험이다.

#### 가족앨범 디지털 복원 아카이브

종이 사진을 촬영해 올리면 화질 개선과 컬러화 후 인물·연대별로 정리하는 서비스다.
복원 전후가 명확해 시연 효과가 좋고 가족 초대, 태그, 댓글 같은 서비스 기능을
확장할 수 있다. 다만 얼굴 데이터 보관과 여러 모델의 처리 시간·비용을 검토해야 한다.

#### 대형폐기물 배출 도우미

가구를 촬영하면 품목을 분류하고 주소지에 맞는 수수료와 신고 절차를 안내하는
서비스다. 실제 불편이 분명하지만 지자체마다 다른 데이터 형식과 실제 신고·결제
연동 범위를 먼저 확인해야 한다.

### 5. Project Intelligence의 초기 문제 정의

프로젝트 코드를 AI에게 질문할 때 일부 파일만 보고 그럴듯한 답을 만드는 문제도
함께 고민했다. 이를 개선하기 위해 AI가 먼저 저장소의 전체 구조와 사용 가능한
검증 수단을 발견한 뒤 분석하도록 하는 `Project Intelligence` 아이디어를 구체화했다.

초기 분석 목적은 다음 세 방향으로 나눴다.

- `performance`: DB Query, Transaction, Lock, Network I/O, Cache 등의 병목 후보 탐색
- `bug-hunt`: 예외 처리, 동시성, 상태 불일치, Edge Case 탐색
- `consistency`: Naming, Layer, DTO·Entity, 예외 처리 방식의 일관성 확인

특정 프로젝트의 기술을 하드코딩하기보다 저장소를 분석해 필요한 정보를 동적으로
찾는 범용 Skill로 발전시키는 방향을 잡았다.
