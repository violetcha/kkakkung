# 학습 일지 — 2026-08-27 (목)

## 오늘의 목표

AI 기능이 포함된 서비스에서 Spring Backend와 AI Server의 책임과 통신 방식을
구분한다. AI를 활용해 만든 결과를 수치로 검증하는 방법을 정리하고,
최근 해외 서비스의 핵심 경험을 분석해 팀 프로젝트 후보로 발전시킨다.

---

## 공부한 내용

### 1. Spring Backend와 AI Server를 분리하는 이유

AI 모델 실행을 Spring Backend 내부에 모두 넣으면 배포 단위와 기술 스택이 강하게
결합되고, 모델 처리 지연이나 메모리 문제가 일반 API까지 영향을 줄 수 있다.
Spring은 사용자·권한·도메인·데이터 일관성을 담당하고, Python 기반 AI Server는
전처리·추론·후처리를 담당하도록 경계를 나누는 구조를 검토했다.

```text
Client
→ Spring Backend
   ├─ 인증·권한
   ├─ 요청 검증과 작업 상태 관리
   └─ 결과 저장·조회
        ↕
   AI Server
   ├─ 전처리
   ├─ 모델 추론
   └─ 후처리
```

서버를 분리하면 AI Server를 독립적으로 Scale-out하고 모델 배포 주기를 분리할 수 있다.
대신 네트워크 실패, 요청·응답 규격, 작업 상태 동기화처럼 프로세스 내부 호출에는 없던
문제를 해결해야 한다.

### 2. 동기 HTTP와 비동기 Message Queue 비교

| 방식 | 적합한 상황 | 확인할 위험 |
| --- | --- | --- |
| 동기 HTTP | 처리 시간이 짧고 사용자가 즉시 결과를 기다리는 요청 | Timeout, 연결 고갈, 장애 전파 |
| 비동기 Queue | 영상 처리처럼 시간이 길고 재시도가 필요한 작업 | 중복 처리, 순서, 재전송, 상태 추적 |

동기 호출에서는 Backend의 Timeout을 AI Server의 최대 처리 시간보다 무작정 길게 두지
않고, 실패 시 사용자에게 다시 시도 가능한 상태를 제공해야 한다. 장애가 지속될 때는
Circuit Breaker로 호출을 차단해 Backend 자원을 보호할 수 있다.

비동기 처리에서는 요청을 작업 ID와 함께 Queue에 넣고, AI Server가 처리한 결과를
저장한 뒤 Backend가 상태를 조회하거나 알림을 보내는 흐름을 사용할 수 있다.
메시지는 재전송될 수 있으므로 동일 작업 ID가 다시 들어와도 결과가 중복 저장되지 않는
멱등성 설계가 필요하다.

### 3. AI 결과를 검증 가능한 형태로 만들기

AI Coding Agent를 사용하면 코드 생성 속도는 빨라질 수 있지만, 생성된 코드가 실제로
더 나은지는 별도로 검증해야 한다. AI 사용 여부 자체보다 동일한 조건의 Before/After를
비교하고 실패 범위를 기록하는 것이 중요하다.

관심 지표를 다음과 같이 정리했다.

| 영역 | 지표 예시 |
| --- | --- |
| 성능 | TPS, 평균·상위 백분위 Latency, 자원 사용량 |
| 안정성 | Error Rate, Timeout, 재시도·중복 처리 횟수 |
| 정확성 | 테스트 통과율, 실패 Test Case, Regression 발생 여부 |
| 변경 범위 | 코드 변경량, 영향받은 모듈과 API |
| 작업 효율 | 동일 범위의 개발 시간, 검토와 수정에 든 시간 |

측정 조건이 다르면 숫자를 직접 비교할 수 없다. 같은 Commit, 데이터, 서버 사양,
동시 사용자 수, 실행 시간과 워밍업 조건을 맞추고 여러 번 실행한 결과를 비교해야 한다.
테스트 통과도 해당 테스트가 다루는 범위의 증거일 뿐, 운영 환경 전체를 검증했다는
의미로 확대하면 안 된다.

### 4. 해외 바이럴 서비스에서 주제를 찾는 방법

처음부터 완전히 새로운 서비스를 상상하는 방식 대신 최근 해외에서 화제가 된 서비스를
조사하고 핵심 재미와 사용자 행동을 분리해 보는 접근을 사용했다.

```text
해외 바이럴 서비스 탐색
→ 사용자가 반복하는 핵심 행동 확인
→ 국내 적용 시 달라질 조건 분석
→ Clone에 그치지 않도록 문제와 도메인 재구성
→ 영상 AI가 필요한 한 지점만 선택
→ 7주 MVP 범위 검토
```

바이럴됐다는 사실만으로 좋은 프로젝트가 되는 것은 아니다. 실제 핵심 기능이 무엇인지,
팀 프로젝트로 확장할 기술적 범위가 있는지, AI를 억지로 붙이지 않아도 되는지 확인해야 한다.

### 5. 조사한 팀 프로젝트 후보

#### Demumu 기반 AI 생존 인증

사용자가 정해진 시간에 사진이나 영상으로 상태를 인증하고, AI가 실제 행동 여부를
확인하는 서비스로 발전시켰다. 일정 시간 인증이 없으면 친구나 지정한 사용자에게
알림을 보낼 수 있다.

- AI 역할: 영상 속 사용자와 지정 행동의 존재 여부 확인
- 서비스 기능: 인증 주기, 친구 연결, 상태 공유, 미인증 알림
- 확인할 위험: 오탐, 민감한 상태 정보, 허위 인증 방지, 알림 책임 범위

#### Focus Friend 기반 AI 집중펫

집중 시간을 캐릭터 성장과 연결하고, 카메라 분석은 집중 경험을 보조하는 기능으로
제한하는 아이디어다.

```text
집중 세션 시작
→ 자리 이탈 또는 스마트폰 사용 감지
→ 집중 기록 반영
→ 캐릭터 성장과 보상 해금
```

- AI 역할: 자리 이탈과 스마트폰 사용 같은 제한된 행동 감지
- 서비스 기능: 집중 기록, 통계, 캐릭터와 아이템, 친구 비교
- 확인할 위험: 계속 촬영되는 영상의 개인정보, 감지 오류, 백그라운드 실행 부담

#### Beli 기반 AI 취향도감

사용자가 음식, 장소, 카페, 패션, 콘텐츠 등을 기록하면 취향 프로필을 만들고 친구와
취향 유사도를 비교하는 서비스다.

- AI 역할: 사진·텍스트 기록의 태그 보조와 취향 패턴 요약
- 서비스 기능: 기록, 컬렉션, 친구 비교, 추천, 취향 변화 시각화
- 확인할 위험: 추천 근거 부족, 초기 데이터 부족, 도메인을 넓힐 때 분류 체계 복잡도

#### Jiffcy를 조사하며 확인한 점

처음에는 새로운 서비스 구조가 있다고 생각했지만 추가로 확인하니 핵심은 메시징 경험에
가까웠다. 유명하거나 바이럴된 서비스라도 핵심 기능을 분해했을 때 단순 Clone으로
끝나거나 프로젝트 확장성이 부족할 수 있다는 점을 확인했다.

### 6. AI를 서비스 전체가 아닌 한 기능으로 제한하기

후보를 비교하면서 AI 모델을 서비스의 주인공으로 만들기보다 사용자의 수작업을 줄이거나
재미를 강화하는 한 지점에 배치하는 편이 7주 프로젝트에 적합하다고 판단했다.

MVP에서는 다음 항목을 먼저 확인해야 한다.

1. AI 없이도 사용자 흐름을 설명할 수 있는가?
2. AI가 담당하는 입력과 출력이 한 문장으로 정의되는가?
3. 사전학습 모델로 핵심 기능을 빠르게 검증할 수 있는가?
4. 실패했을 때 사용자가 직접 수정하거나 다시 시도할 수 있는가?
5. 웹·앱·백엔드·AI 구성원이 나눠 맡을 구현 범위가 있는가?
6. 발표 현장에서 처리 전후 또는 감지 결과를 바로 보여줄 수 있는가?
