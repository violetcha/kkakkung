## 공부한 것

### 1. 엔진 선택 기준 — 병목이 어디인지가 답을 정한다

Unity vs 웹(Three.js)을 놓고 고민했다. 처음엔 "3D 게임이니 Unity"라고 생각했다.
표로 정리해보니 판단이 뒤집혔다.

| | 웹 (Three.js) | Unity |
|---|---|---|
| 얼굴 랜드마크 · 머리 자세 | MediaPipe 공식 지원, 즉시 | Sentis+ONNX 직접 구성 or 비공식 플러그인 |
| 웹캠 → 텍스처 | `VideoTexture` 한 줄 | 번거로움 |
| 3D 공포 연출 | 직접 구성 | **URP/HDRP 압도적 우위** |
| 배포 | **URL 하나** | WebGL 100MB+ (웹캠+ML은 지뢰밭) |

Unity가 이기는 항목은 **렌더링 품질과 레벨 에디터**다.
그런데 이 게임의 미로는 **전부 상자**다. 모델링이 없고 렌더 부하도 없다.
공포는 안개·어둠·사운드가 만드는데 그건 웹에서도 된다.

반대로 Unity가 지는 항목은 **얼굴 인식과 배포**인데, 이건 이 프로젝트의 핵심이다.

> **가장 어려운 문제가 가장 쉬워지는 쪽을 고른다.**

교훈: 기술 비교는 일반적 우열이 아니라 **내 병목**을 기준으로 해야 한다.
"Unity가 3D에 더 좋다"는 참이지만 이 프로젝트에서는 무의미한 참이었다.

### 2. 연속 신호를 이산 명령으로 바꾸는 문제 — 히스테리시스 게이트

이 게임은 **입력 1회 = 정확히 한 칸**이다. 연속 이동이면 위험을 보고 바로 도망칠 수
있어서 공포가 사라진다. 그런데 얼굴 각도는 **연속값**이다.

단순 임계값으로 하면 고개를 돌리고 있는 동안 매 프레임 발동해서 **초당 수십 칸**이 나간다.
재장전 구조가 필요하다.

```
armed = true
if (|yaw| > 발동 && armed) { 회전(); armed = false; }
if (|yaw| < 재장전)        { armed = true; }   // 중립 복귀해야 다시 발동
```

여기서 한 발 더 나갔다. **전진과 회전은 발동 방식이 달라야 한다.**

| 명령 | 방식 | 이유 |
|---|---|---|
| 회전 | 1회 발동 + 재장전 | 고개 돌린 채 두면 계속 회전해버린다 |
| 전진 | **홀드 반복** | 5칸 복도를 가려고 몸을 5번 흔들면 피곤하다 |

홀드 반복으로 바꿔도 **격자 한 칸씩 이동한다는 설계는 유지된다.**
기울인 자세를 유지하면 쿨다운마다 한 칸씩 나아갈 뿐이다.

교훈: 신호 처리와 게임 디자인이 분리된 문제가 아니었다. 같은 문제였다.

### 3. One Euro Filter — "부드럽게 하면 느려진다"의 해법

MediaPipe raw 출력은 가만히 있어도 미세하게 떨린다. 단순 저역통과 필터를 걸면
딜레마에 빠진다. **강하게 걸면 지터는 사라지지만 반응이 늦고, 약하게 걸면 반대다.**

One Euro Filter는 컷오프를 **속도에 따라 적응**시켜 이걸 정면으로 해결한다.

- 느리게 움직일 때 → 강하게 스무딩 (지터 제거)
- 빠르게 움직일 때 → 약하게 스무딩 (지연 제거)

```js
const dv = (v - prev) / dt;
const edv = dxFilter.filter(dv, alpha(dcutoff, dt));
const cutoff = mincutoff + beta * Math.abs(edv);   // ← 여기가 핵심
return xFilter.filter(v, alpha(cutoff, dt));
```

튜닝 파라미터가 `mincutoff`와 `beta` 둘뿐이고 구현이 50줄이다.
Kalman도 후보였지만 상태 공간 모델을 세울 필요가 없는 이 용도엔 과했다.
One Euro는 정확히 이 문제(모션 트래킹 지터)를 위해 만들어진 물건이다.

### 4. 좌표계 규약을 피하는 설계 — 오일러 각 대신 랜드마크 비율

머리 회전을 얻는 정석은 `facialTransformationMatrixes`(열우선 4×4)에서 오일러 각을
뽑는 것이다. 그런데 오일러 각 추출은 **회전 순서 규약(YXZ/ZYX…)에 따라 결과가 달라진다.**

문제는 이거다. **부호 하나만 틀려도 조작이 통째로 반대가 되는데, 그 버그는 카메라 앞에
앉기 전까지 발견되지 않는다.** 코드를 읽어서는 알 수 없다.

그래서 규약이 필요 없는 신호를 골랐다.

```
dL = 코끝.x − 왼쪽볼.x
dR = 오른쪽볼.x − 코끝.x
yaw = (dR − dL) / (dL + dR)        // −1 ~ 1, 무단위
```

상대 거리비이므로 **얼굴 크기와 카메라 거리에 자동으로 불변**이고 계산이 명시적이다.
행렬 각도는 참고값으로 화면에 같이 띄웠다.

그리고 **방향 반전 체크박스**를 UI에 넣었다. 부호가 뒤집힐 가능성 자체는 없앨 수
없으니, 코드를 고치는 대신 체크 한 번으로 확정하게 했다.

**실제로 부호가 틀려 있었다.** 고개를 왼쪽으로 돌리면 오른쪽으로 갔다.
체크박스로 5초에 확인하고, 코드에서 뒤집어 확정했다.

교훈: **검증할 수 없는 환경에서는 "틀릴 방법이 적은" 설계를 고른다.**
정석이 더 정확해도, 틀렸을 때 발견이 늦으면 손해다.

### 5. 크로스토크 — 두 신호가 같은 원인에 반응하면 독립이 아니다

전진/후진 신호로 **얼굴 bbox 면적**을 썼다. 몸을 앞으로 기울이면 얼굴이 커진다.

그런데 **고개를 좌우로 돌리면 얼굴 bbox도 작아진다.**
즉 **회전할 때마다 "후진"이 오발동한다.** 구조적 결함이다.

두 가지로 대응했다.

| 방법 | 성격 |
|---|---|
| **행렬 병진 성분** `data[14]` 사용 | 순수 거리라 회전에 영향받지 않음. **근본 해법** |
| yaw 억제 — 고개가 중립을 벗어난 동안 전후 신호를 0으로 | bbox를 계속 쓸 때의 저비용 대응 |

여기서 재미있는 점: 4번에서 오일러 각을 피했는데, 같은 행렬의 **병진 성분은 안전하게
쓸 수 있다.** 위치는 회전 순서 규약과 무관하니까. 같은 데이터라도 어느 부분을 쓰느냐에
따라 위험이 다르다.

교훈: 신호를 고를 때 "이게 내가 재려는 것에만 반응하나"를 따져야 한다.

### 6. 성능은 재기 전에 고치면 안 된다 — 오늘 최대 실패

"화면이 매끄럽지 않다"는 문제가 나왔다. 나는 바로 **추측으로 고치기 시작했다.**

- 픽셀 비율 2.0 → 1.25
- 블룸을 절반 해상도로
- 그림자 맵 1024 → 768
- 랜드마크 오버레이 점 개수 줄이기

전부 그럴듯한 최적화였고, 전부 **헛수고였다.**

그다음에 측정을 붙였다. `detectForVideo()` 소요 시간을 재보니 **17~18ms.**
프레임 예산은 60fps 기준 **16.6ms**다.

```
추론 1회(18ms) > 프레임 예산(16.6ms)
→ 추론이 도는 프레임은 렌더 비용이 0이어도 무조건 밀린다
```

**렌더링을 아무리 줄여도 안 없어지는 문제였다.** 내가 처음에 만진 항목은 원인과
관계가 없었다. 측정 한 줄이 최적화 네 개보다 가치 있었다.

교훈: 병목을 재기 전의 최적화는 효과 크기를 모르는 게 아니라 **방향조차 모르는** 상태다.

### 7. 평균 fps는 히칭을 숨긴다

이게 6번과 짝이다. 평균 fps만 보면 "45~50 나오는데 왜 이상하지?" 하게 된다.

```
추론 20fps × 18ms = 초당 360ms  →  메인 스레드의 36%
```

평균은 그럴듯한데, **추론이 도는 프레임은 100% 늦는다.**
초당 20회 규칙적으로 튀는 것이고, 이건 평균 fps에 거의 안 나타난다.

> **체감은 평균이 아니라 최악 프레임이 만든다.**

그래서 `프레임 ms`와 `추론 ms`를 따로 표시하고, 16ms를 넘으면 배지가 붉게 변하게 했다.
평균 fps 한 개보다 이 두 숫자가 훨씬 많은 걸 말해줬다.

### 8. 폴백은 "선언"이 아니라 "경로"다

추론을 Web Worker로 빼려고 했다. 그러면서 두 가지를 잘못했다.

**첫째, 검증하지 않은 경로를 기본값으로 만들었다.** 워커가 실패하니 앱이 아예 안 됐다.

**둘째, 폴백이 가짜였다.** 실패하면 드롭다운을 `메인`으로 바꾸도록 했는데,
워커 모드에서는 메인 쪽 모델을 애초에 만들지 않았다. 그래서

```
드롭다운만 main → landmarker 는 null → infer() 즉시 리턴
→ 신호가 한 번도 안 옴 → calibrating 플래그가 영구 true
→ 캘리브레이션 버튼이 "측정 중…" 에서 영원히 잠김
```

증상은 "캘리브레이션이 안 됨"이었지만 원인은 폴백이었다. 한참 헤맸다.

교훈: 폴백은 **실제로 실행되는 경로**여야 한다. 상태 변수를 바꾸는 것과
동작하는 것은 다르다. 그리고 검증 안 된 아키텍처를 기본 경로에 두면 안 된다.

부수적으로 배운 것: **`alert()`은 디버깅을 방해한다.** 실행을 막고 메시지를 복사할
수도 없다. 화면 패널로 바꾸니 원인 파악이 훨씬 빨라졌다.

### 9. 내 코드에 없는 원인은 관측 지점을 늘려서 찾는다

"URL로 들어가면 창이 두 번 뜬다"는 문제. 코드를 아무리 봐도 창을 여는 곳이 없었다.
`window.open`도 없고 iframe도 없다. 문서 구조가 중복됐나 세어봤지만 전부 1개였다.

그래서 개발 서버에 **요청 로그**를 붙였다. 3분 만에 답이 나왔다.

```
002 GET 200 /spike-play.html  dest:document mode:navigate
003 GET 200 /spike-play.html  dest:document mode:navigate
004 GET 404 /dev-sw.js        dest:serviceworker mode:same-origin
```

`dev-sw.js`는 **Vite PWA 플러그인의 서비스 워커** 파일명이고, **5173은 Vite 기본 포트**다.
이전에 그 포트에서 돌린 프로젝트가 서비스 워커를 등록해뒀고, **서비스 워커는
오리진(포트 포함)에 영구 등록**되므로 내 서버와 무관하게 살아남아 요청을 가로챘다.

해결은 **포트를 바꾸는 것**이었다 (5173 → 5199). 서비스 워커 스코프는 포트를 포함하니
다른 포트는 깨끗한 오리진이다.

부수적으로 서버 버그도 하나 발견했다. 없는 파일에 **디렉터리 목록 HTML을 404로**
돌려주고 있었다. 서비스 워커·스크립트·아이콘 요청이 HTML을 받으면 파싱 오류가 난다.
루트만 목록을 주고 나머지는 `text/plain` 404로 고쳤다.

교훈: 원인이 내 코드에 없으면 **내 코드 밖에서** 찾아야 하고, 그러려면 관측 지점이
필요하다. 로그 없이 추측만 하다가 시간을 많이 썼다.

### 10. TDZ — 문자열 치환으로 코드를 고칠 때의 함정

패치를 문자열 치환으로 적용하다가 **`const` 선언보다 앞에서 참조**하는 코드를 만들었다.

```js
$('diag').innerHTML = ... trackProcessorOK ...   // ← 여기서 참조
// ... 2000줄 아래 ...
const trackProcessorOK = ...;                     // ← 선언
```

최상위 스코프에서 TDZ 위반이면 **ReferenceError로 모듈 전체가 죽는다.**
화면은 "로딩 중…"에서 멈추고, 원인은 전혀 안 보인다.

배포 전에 최상위 `const`/`let` 선언 위치를 스캔하는 검사를 돌려서 잡았다.
그 검사를 안 만들었으면 그대로 나갔을 것이다.

교훈: **삽입 위치를 사람이 정하는 패치는 선언 순서를 깨뜨릴 수 있다.**
문법 검사(`new vm.Script`)만으로는 TDZ가 안 잡힌다. 문법은 통과하니까.

### 11. 조작과 감정을 일치시키기 — 기술이 아닌 설계 통찰

"전진은 어떤 동작으로 해야 하나"를 정해야 했다. 고개를 위로 드는 게 직관적으로
보였지만 기각했다.

**전진은 게임에서 가장 자주 쓰는 동작**이다(전진:회전 ≈ 2:1 이상). 그런데 고개를 들면
**화면을 못 본다.** 가장 빈번한 동작에 시야 이탈을 만드는 셈이다.

채택한 건 **상체를 앞으로 기울이기**다. 이유가 편의가 아니었다.

> 공포 상황에서 몸을 앞으로 내미는 것(확인하려는 반응)과 뒤로 빼는 것(놀라 물러나는
> 반응)은 **이미 사람의 자연 반응**이다. 조작 동작과 공포 반응이 일치하면
> 학습 비용이 0이고 몰입이 깨지지 않는다.

그리고 이 결정에서 공짜로 얻은 게 있다. **엿보기(peek)** 다.
임계값 미만 구간을 연속적으로 카메라 회전에 매핑하니, 고개를 살짝 빼서 코너 너머를
훔쳐보는 동작이 자연스럽게 생겼다. 공포게임의 클래식 메커닉인데 설계에서 파생됐다.

교훈: 입력 설계를 인체 반응에서 출발하면 UX와 게임 디자인이 동시에 풀린다.

### 12. 게임 규칙은 쓰기 전에 산수로 검증해야 한다

술래잡기 규칙을 정하다가 두 개의 구조적 결함을 발견했다. 둘 다 **구현 전에 종이에서**
나왔다.

**① 같은 속도면 잡을 수 없다.**
이산 이동에서 술래와 도망자가 같은 쿨다운으로 한 칸씩 움직이면 **거리가 영원히 불변**이다.
"한 칸 이동"은 이 게임 공포의 기둥이라 포기할 수 없으니, 비대칭을 어딘가 넣어야 한다.
→ 쿨다운 차등(400ms vs 320ms)으로 시작하고, 술래가 자기 벽 사이를 순간이동하는 안을 실험.

**② 벽으로 다 막으면 게임이 성립하지 않는다.**
술래가 벽을 설치하는 규칙이니, 탈출구로 가는 경로를 전부 막으면 도망자는 이길 수 없다.
→ **벽을 놓을 때마다 BFS로 경로를 검증**하고, 끊는 배치는 거부하는 것을 절대 규칙으로.

교훈: 규칙의 결함은 플레이해보기 전에 산수로 잡을 수 있는 것도 있다.
"같은 속도면 거리가 안 좁혀진다"는 구현해봐야 알 일이 아니었다.

## 막힌 것 / 남은 의문

1. **나는 이 프로젝트 화면을 직접 본 적이 없다.** 이게 가장 큰 구멍이다.
   문법·CDN 응답·서버 응답만 검증했다. 조명 세기(34), 톤매핑 노출(1.05),
   안개 밀도(0.105), 캐릭터 비율, One Euro 기본값은 전부 **계산 또는 추정치**다.
   → 문서에 "실측 확정"과 "추정"을 구분해 표시해뒀다.

2. **워커에서 프레임이 흐르지 않는 원인 미특정.** 오류 없이 `ready`까지는 도달한다.
   다음에 시도할 때는 `MediaStreamTrackProcessor`를 버리고 **bitmap 펌프만으로**
   먼저 성공시켜야 한다. 변수를 하나로 줄이는 게 핵심이다 (실수 10의 교훈).

3. **추론 18ms는 안 내려간다.** 블렌드셰이프를 껐는데 거의 변화가 없었다.
   비용의 대부분이 랜드마크 모델 본체다. 옵션 조정으로는 못 줄인다.
   → 지금은 수용 가능하지만 씬이 무거워지면(S3 AI·사운드, S5 네트워크) 다시 문제가 된다.

4. 술래 추격 성립 방식 미결정 — 쿨다운 차등(A) vs 벽 텔레포트(B).
   B가 훨씬 흥미롭지만("벽을 놓는 게 곧 내가 튀어나올 구멍을 놓는 것") 밸런싱이 어렵다.

5. 목 피로가 실제로 어느 정도인지 모른다. 10분 세션을 전제로 설계했지만 안 재봤다.
