## 판정과 범위

초기 문서는 역할별 파일·단계·시험을 상세히 정의했지만 **각자 AI에 번호를 주면 막힘 없이 최종 완료된다는 수준은 아니었다.** 단위 구현 착수와 통합 인수 선행을 구분하지 않았고, 일부 실제 연결 API·실행 순서·공유 기록이 빠져 있었다. 기존 형식 검사가 통과해도 이를 잡지 못했다.

이번 변경은 각 역할의 문서와 지정 기획 장·공개 계약만으로 자신의 구현·검증·인계를 진행하도록 보완한다. 모든 역할의 전체 계획을 읽을 필요는 없다. 실제 소스와 공개 export·fixture·다른 역할의 공개 인계는 확인해야 한다. 최종 통합과 Cloud·실장치·부하 인수는 실제 선행 구현과 환경을 필요로 한다. 문서만으로 이를 대신할 수 없다.

## 충돌을 줄이는 실제 작업 방식

| 연결                             | 생산자 | 소비·최종 조립 | 변경 방법                                                 |
| -------------------------------- | ------ | -------------- | --------------------------------------------------------- |
| 맵·규칙 → 게임 서버              | A      | B              | A 내부 공개 export, B loader/driver에서 변환·연결         |
| 상태·명령 → 웹·입력              | B      | C/D, 웹 조립 C | B만 protocol 원본, C/D는 소비·인계 요청                   |
| 장치·센서·브라우저 미디어 → 화면 | D      | C              | D facade, C bridge·DOM host·texture                       |
| 서버 미디어·운영 → 기동/라우트   | E      | B              | E coordinator/auth/operations export, B bootstrap 조립    |
| 환경·의존성·계측                 | F      | B/D/E          | F만 manifest/config/exporter, 소비자는 자기 파일에서 연결 |
| 검증 결과·선행 요청              | 각자   | 필요한 소비자  | 자기 handoff 파일만 수정, F가 공통 인수 집계              |

파일 충돌 가능성을 0이라고 보장하지 않는다. 공유 계약의 의미가 바뀌면 생산자와 소비자가 함께 검토해야 한다. 역할별 checkout에서 한 명이 같은 파일을 소유하고, 공통 변경은 별도 계약/설정 인계로 처리하며, 합칠 때 최신 develop과 실제 diff를 재확인한다.

작업 개수만으로 업무량이 균등하다고 판정하지 않았다. B의 서버 조립, C의 화면 조립, F의 환경·검증은 통합 병목이다. 각자의 1–5만 동시에 요청해도 C의 실제 입장에는 B-07–13, E의 실제 발급에는 F 환경과 B 세션이 필요하다. 따라서 계약/단위 인계를 먼저 보내고 각 역할의 후속 번호를 진행한 뒤 통합 인수를 재개해야 한다. 일정은 목표이며 116개 확정 작업의 완료 시간 보증이 아니다. 이 대기 상태와 다음 담당 요청을 문서에서 숨기지 않는다.

## 이번 변경의 검증

최종 검사는 같은 checkout의 공통 사본·작업 ID·선행 그래프·소유 경로·링크/표·TypeScript 계약·fixture·실행 도구를 대상으로 한다. 결과 집계는 `node scripts/check-execution-plan.mjs`에서 재현할 수 있다. 제품 동작을 바꾸지 않았으므로 앱 전체·Cloud·장치·배포 검사를 이 문서 변경의 통과 수로 합산하지 않는다.

기본 셸의 Node는 22.23.2였지만 저장소 고정 버전은 24.19.0이다. 최종 도구 검사는 제공된 Node 24.19.0으로 실행한다. 기존 pnpm wrapper가 자동 install을 시도하며 비대화형 modules 교체 확인에서 중단되어, 설치된 도구의 직접 실행 경로를 사용했다. 이를 신규 clone의 설치 검증 성공으로 보고하지 않는다.

확인한 결과: **122개 ID / 활성 116 / 결정 대기 6 / 구현 지시 547 / 계획된 시험 사례 570 / 소유 경로 445**, 계약 fixture **25개**와 실행 도구 회귀 **11개** 통과. 변경 파일 Prettier·ESLint·`git diff --check`도 통과했다. 도구 회귀는 번호/보류/잘못된 범위·경로 소유/미등록 경로·rename 원본·commit/stage/working·공통 블록 예외의 허용 및 거절을 검사한다. 여섯 역할의 고정 1–5 입력은 별도로 읽기 전용 출력 검사를 수행한다. 이 수치는 실제 제품 구현·Cloud 검증 수가 아니다.
