## 팀원이 AI에 전달할 내용

자기 담당 문서와 최신 결정·기획서·공통 계약을 함께 기준으로 삼는다. AI는 저장소 지침·실제 코드·설치된 SDK 타입과 다른 담당자의 공개 계약을 직접 읽어야 한다.

```text
내 담당은 A야. docs/execution/a-game-core.md와 docs/spec/decisions.md,
v0.0.8 기획서, EXEC-CONTRACT-3를 기준으로 오늘 1번부터 5번까지 진행해줘.
PRODUCT_DECISION_PENDING 번호는 구현하지 말고 보류한 뒤 다음 번호를 진행해줘.
현재 코드·저장소 지침·공개 타입·fixture를 직접 확인하고 담당 파일 범위를 지켜줘.
검증된 중간 산출물과 완료 작업은 단계·검증·미통합 조건을 구분해 내 Git 신원으로 로컬 커밋해줘.
작업별 MR 본문과 이번 실행분 합본을 작성하고 파일 링크와 전체 본문을 보여줘.
푸시·MR 생성·원격 병합·Jira 변경은 하지 마.
```

“오늘 번호”는 날짜마다 1부터 다시 센다. A의 D2 오늘 1번은 고정 번호 **A-19 / KN-05**다. 보류 번호를 건너뛰어도 다른 번호는 그대로다. 다른 날짜에는 “D2 1–5번” 또는 “A-19부터 A-23까지”처럼 지정한다. 재실행 전 코드·commit·진행 기록을 확인해 동일 변경을 다시 커밋하지 않는다.

- B 명령·개인 뷰 변경: C·D
- E 세대·바인딩·회수 결과 변경: B·D

- readiness·운영 준비 변경: B·E

공통 계약 변경은 원본·fixture와 영향을 받는 생산자·소비자를 함께 고친 후 검사기로 동기화한다. 담당자별 함수명이나 payload를 따로 확정하지 않는다.

## 실행 상태·커밋·MR

상태는 **PLANNED → CONTRACT_READY → LOCAL_VERIFIED → INTEGRATED → ACCEPTED**로 기록한다. 외부 전제 부재는 BLOCKED, 미정 콘텐츠는 PRODUCT_DECISION_PENDING이다. 문서상의 상태를 Jira에 자동 적용하지 않는다.

1. 지정 파일에서 구현·오류 처리·수명 정리·정보 은폐를 진행하고 실제 검사 결과를 남긴다.
2. 계약·fixture나 단위 구현이 검증되면 중간 커밋을 허용한다. 실제 생산자·소비자 연결과 필요한 Cloud·장치 증거 전에는 ACCEPTED로 표시하지 않는다.
3. 해당 파일만 stage하고 scope 없는 `type: 변경 내용`으로 로컬 커밋한다. 실제 담당자 Git 신원을 사용하며 AI 공동 저자·타인 author·기존 commit 재작성을 하지 않는다. Jira 키는 실제 키만 마지막 문단에 넣고 `Refs:`는 쓰지 않는다.
4. `.local/execution/<담당>.json`에 ID·단계·실제 검사·commit·미통합 선행·결정 대기를 기록한다.
5. `.local/mr/<담당>/<원본ID>.md`와 `<일차>-combined.md`에 관련 Jira / 변경 사항 / 변경 이유 / 리뷰 포인트 / see also 다섯 항목의 본문을 실제 diff와 증거로 작성한다. 파일과 전체 본문을 담당자에게 제공한다.
6. push·MR 생성·원격 병합·Jira 변경은 별도 요청 없이 수행하지 않는다. 이 실행계획의 인계에서는 담당자가 원격 작업을 직접 한다.

실제 Jira가 아직 없으면 `feat/mvp-a-d1` 같은 담당/일차 브랜치를 사용할 수 있고 F는 `ci/mvp-f-d1`을 사용한다. 가짜 Jira 키를 만들지 않는다. 기존 브랜치·미커밋 변경·Git name/email을 확인하며 신원이 없으면 구현은 진행하고 커밋만 보류한다.
