상태: **팀 검토용 계획. 원본 122개 ID 중 실행 계획 116개·제품 결정 대기 6개이며 신규 Jira 에픽·스토리는 등록하지 않았다.**

기존 구현 에픽 10개와 신규 에픽 후보 5개, **15개 에픽 영역·원본 작업 ID 122개**를 유지한다. **116개는 실행 계획**, MP-06·EQ-06·EQ-07·EQ-08·EQ-09·EQ-12는 **PRODUCT_DECISION_PENDING**이다. 각 활성 행은 구현 또는 검증 결과를 리뷰할 스토리 후보이며, 결정 대기 행은 사용자 결정이 기록될 때까지 착수·완료 집계에 넣지 않는다.

## 1. 기준과 현재 출발점

기획 범위는 [v0.0.8 원본](spec/README.md)에 [최신 결정 정정표](spec/decisions.md)를 우선 적용하고, 연결 계약은 [공통 원본](execution/common.md)과 [타입·fixture](execution/contracts/types.ts)를 따른다. 현재 구현 상태는 [요구사항](../requirements.md)과 [검증 결과](verification.md)를 기준으로 했다. 코드 배치는 [아키텍처](architecture.md), 수명은 [미디어 수명](media-lifecycle.md), 작업·검증 규칙은 [기여 가이드](../CONTRIBUTING.md)와 [협업 컨벤션](collaboration-conventions.md)을 따른다. 스켈레톤 변경은 [MR !3](https://lab.ssafy.com/s15-ai-image-sub1/S15P21C204/-/merge_requests/3)에 연결되어 있다. 이 계획은 해당 변경의 병합 완료를 전제로 하지 않는다.

위 시험 수는 기존 스켈레톤 검증 기록이며, 이번 문서 작업에서 앱 시험을 다시 실행했다는 의미가 아니다. 기존 전체 maze/players 공개, 간이 ready, 도메인 스텁, 인터페이스 문서는 제품 기능 완료로 집계하지 않는다. `test:maps`도 현재 전체 맵 인증 시험이 아니다.

### 유지할 기술과 범위

- 단일 저장소의 `apps/web`, `server`, `packages/protocol`, `packages/game-core`와 루트 lockfile 하나를 유지한다.
- Node.js `24.19.0`, pnpm `11.19.0`, TypeScript `6.0.3`, Colyseus `0.18`을 기준으로 한다. 정확한 의존성 버전은 manifest·lockfile이 우선이다.
- React/Vite·R3F/Three.js, 브라우저 MediaPipe Worker, 가공 얼굴 Canvas/captureStream, LiveKit Cloud, 단일 Node 서버·Nginx·Docker Compose를 전제로 한다.
- CI/CD는 사용자가 제시한 **Jenkins 방향**으로 계획한다. 현재 Jenkinsfile·원격 연동은 미구축이며, 기획서가 Jenkins를 명시적으로 확정했다고 해석하지 않는다.
- 32×32·3대3·180초·2명 탈출/포획, 개인 출구·지도 교환·술래 감지기/덫·자연 구속 만료/유예, 모션과 보조 입력을 구현한다. RL-05 공통 우선순위는 유지하고 EQ-11은 구속 HUD만 구현한다.
- 도망자 아이템의 종류·효과·배치/획득·소지·사용은 아직 미정이다. 관련 6개 ID는 유지하되 사용자 결정 전 제품 타입·메시지·상태·UI·시험 구현을 진행하지 않으며, 승인된 범위 제외나 완료로 바꾸지 않는다.
- DB·Redis·Python 서버·직접 운영 SFU·추가 서버·관전·진행 매치 복원·중도 충원은 이 계획에 추가하지 않는다. 마이크는 선택이고 경기 전 카메라 준비는 필수다.

현재 `kkakkung`과 `sandbox`의 서로 다른 계약을 섞지 않는다. SV 작업에서 제품 프로토콜 변경·버전을 명시하고 웹/서버 소비자를 함께 옮긴다. 기존 `server/rooms`·`domain` 담당 경계를 유지하며 서버 전체 상태·맵·seed·튜닝을 웹이나 protocol에 옮기지 않는다. `SessionRuntime`의 비동기 연결 취소용 generation을 실제 미디어 세대 구현으로 간주하지 않는다.

## 2. 작업을 작게 나누는 기준

1. **작업 하나에 주 담당자 한 명, 검증 가능한 결과 하나**를 둔다. 표의 BE/FE/AI/DevOps/QA는 담당 영역이며 실명 배정은 아니다.
2. 한 행은 검증 가능한 결과를 묶은 원본 작업 단위다. [6인 실행계획](execution/README.md)에서는 각 행 안에 구체적인 구현·시험 순서를 적어 AI가 순차 실행하게 했다. 작업 개수나 단계 수를 작업시간·Story Point로 환산하지 않는다. 2–3일 목표의 병목은 중간 인계와 실제 통합 결과로 확인한다.
3. 정상 처리와 그 동작의 경계·실패 시험은 같은 작업에 포함한다. 테스트를 형식적으로 별도 스토리로 늘리지 않는다.
4. 서버 판정과 화면 연결은 결과·소유자가 달라 분리한다. 예를 들어 지도 교환은 요청→취소→병합→사건→화면으로 나누고, 덫은 후보→선정/소모→구속/유예로 나눈다.
5. 실제 Cloud 강제 권한, 강제 종료, 여러 기능의 동시 Tick, 6대 완주, 60세션 부하는 통합 검증 작업으로 별도 관리한다.
6. 한 작업이 완료되려면 표의 완료 조건, 관련 계약의 생산자·소비자 검증, 변경 영역 시험과 필요한 문서 갱신이 함께 충족되어야 한다. 공통 검사는 [테스트 가이드](testing.md)를 따른다.

### 표 읽는 법과 완료 판정

- `AC-01` 등의 번호는 **이 문서 안의 임시 작업 ID**다. Jira 키·브랜치명·커밋 연결 키로 사용하지 않는다.
- “선행 작업”은 **해당 작업을 완료하기 위해 필요한 결과**다. 합의한 계약과 fixture로 병렬 착수할 수 있지만 실제 소비 경로가 연결되기 전 제품 완료로 표시하지 않는다.
- `—`는 문서 내부 선행 작업이 없다는 뜻이다. Cloud 계정·장치·서버 권한 등 외부 전제가 없다는 뜻은 아니다.
- 표의 “근거” 숫자는 원래 v0.0.8 장 번호를 보존한 것이다. 충돌 시 D-2026-09-08-01과 EXEC-CONTRACT-2가 우선하며 보류 행의 원문 후보는 구현 지시가 아니다. Jenkins는 사용자 방향과 협업 기준이 근거다.
- 경로는 기존 코드의 소유 영역과 **추가 예정 위치**를 함께 표시한다. 아직 없는 폴더를 미리 빈 파일로 만들라는 뜻이 아니다.
- 단위 시험용 합성 상태, 가짜 Gateway, 인터페이스만 완료한 결과는 실제 Cloud·전체 MVP 통과로 보고하지 않는다.
- 현재 상태는 **실행 계획 116개 / PRODUCT_DECISION_PENDING 6개 / 담당 역할 A–F 배정 / 신규 Jira 미등록**이다. 실명과 Story Point는 아직 배정하지 않았다. 실행 순서·중간 인계는 담당 문서를 따르며 보류 행 때문에 활성 작업을 멈추거나 보류 내용을 임의 확정하지 않는다.

## 7. 이번 스프린트에 넣기 전 검토

기획서는 2026-09-07–09-13을 목표 주간으로 제시하며, 사용자가 정한 실행 목표는 **9월 8–10일 2–3일 구현·통합과 9월 11일 금요일 오전 MVP 인수**다. [6인 실행계획](execution/README.md)에 날짜별 순서와 중간 인계를 배치했다. 확정 소요시간 견적은 아니며 실제 선행 코드·Cloud·장치 준비와 확정 범위 G1–G6 결과를 확인해야 한다. 116개 실행 계획과 6개 제품 결정 대기를 구분해 스프린트 상태를 보고한다. 임시 ID 수를 사람·일 수나 Story Point로 환산하지 않는다.

| 검토 항목 | 결정할 내용                                                     | 계획에 미치는 영향                                                               |
| --------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 작업 크기 | 담당자가 한 번에 리뷰할 수 있는지, 하루 초과 예상 행은 어디인지 | 큰 작업을 수락 조건별로 재분할. 묶어도 한 결과·한 담당이 유지되는 작은 행은 조정 |
| 책임      | BE/FE/AI/DevOps/QA 영역별 주 담당과 리뷰 담당                   | 실제 인원을 적고 공통 파일 충돌·검토 병목 확인                                   |
| 가용 시간 | 스프린트 종료일, 팀원별 실작업 가능 시간, 통합/수정 시간        | 전체 예상 소요와 비교해 스프린트 가능 여부 산정                                  |

| 통합 여유 | G1 회귀, 5판 완주, 60세션 시험 뒤 결함 수정 시간                | 마지막 날에 처음 통합하지 않도록 별도 여유 배정                                  |

특히 MC-01의 Cloud 조사, MC-07의 회수 장벽, OP-06의 재시작 대조, QA-07의 동시 판정 조합은 구현 난도가 높은 후보다. 검토 때 하루 안에 완료 조건을 만족하기 어렵다고 판단하면 내부 결과를 나눠 산정한다. 현재는 외부 시스템을 임의 변경하거나 새 스택을 선택하는 조사로 확대하지 않는다.

확정된 핵심 기능이 미완성이면 공개일을 조정하고 통합 중간본으로 보고한다. 확정 기능은 완성했으나 10방 시험만 미실시/실패하면 기능 완료와 부하 상태를 함께 기록하며 실제 검증된 상한까지만 운영한다. QA-13 보고서를 작성하더라도 QA-12·전체 목표가 통과했다고 표시하지 않는다. 아이템 6개 작업과 G3-C의 제품 결정 대기는 어느 경우에도 별도 미완료 상태로 남긴다.

## 8. 팀원·AI에게 넘길 작업 양식

검토 승인 뒤 한 행을 실제 스토리로 옮길 때 다음 양식을 사용한다. 관련 Jira 키는 **실제 생성된 값**으로만 채운다.

```text
문서 작업 ID: <예: KN-05>
실제 Jira: 미등록 또는 실제 키
상위 에픽: <이 문서의 기존 에픽 또는 승인 후 생성된 에픽>
제목: <담당 영역과 작업 내용>
담당자 / 리뷰 담당:
상태 / 예상 시간:

배경:
- v0.0.8의 관련 장, D-2026-09-08-01 적용 내용, 현재 코드에서 부족한 동작

목적:
- 이 작업이 완료되면 가능한 행동 한 가지

작업 내용:
- 활성 행의 책임과 수정 영역. PRODUCT_DECISION_PENDING이면 구현하지 않고 재개에 필요한 결정만 기록한다.
- 선행 작업의 실제 계약·결과
- 생산자/소비자 연결과 버전 영향

완료 조건:
- 표의 완료 조건을 검증 가능한 체크 항목으로 옮긴다.
- 정상·경계·실패 동작과 실제 확인 방법을 적는다.
- 미실시 Cloud/장치/부하 검증은 완료로 표시하지 않는다.

관련 MR:
- 실제 MR 생성 후 링크

AI 전달:
- AGENTS.md, CONTRIBUTING.md, 변경 영역 README를 먼저 읽는다.
- 이 스토리의 범위와 선행 계약을 확인하고 기존 담당 경계를 유지한다.
- 최신 결정 정정표·EXEC-CONTRACT-2 타입/fixture·담당 상세를 함께 읽고 원문과 충돌하는 미정 콘텐츠를 구현하지 않는다.
- 실행한 검사, 남은 조건, 다른 작업에 필요한 계약을 보고한다.
```

협업 규칙은 계속 **scope 없는 `type: 변경 내용`**이다. 관련 Jira가 있는 커밋은 본문/푸터에 접두사 없이 실제 키만 단독 줄로 적는다. `Refs:`를 붙이지 않으며 AI 공동 저자를 추가하지 않는다. MR 본문은 관련 Jira / 변경 사항 / 변경 이유 / 리뷰 포인트 / see also를 유지한다.

이 문서는 작업 지시를 준비하는 자료다. 실제 Jira 등록·스프린트 배정·브랜치 생성·커밋·푸시·MR·배포는 해당 작업 요청과 승인 범위에 따라 별도로 진행한다.
