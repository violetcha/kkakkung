## 문제와 수정

운영 설정 파일은 매초 비동기로 검사하며 확인한 메모리 사본의 유효 기한은 5초다.
기존 구현에서는 검사 지연으로 이 기한을 넘기면 정상 파일을 다시 읽는 경로도 차단했다.
일시적인 파일 IO 지연이나 프로세스 정지 뒤에도 운영자가 재시작해야 하는 복구 공백이었다.

[RuntimeEvidence](../server/src/config/RuntimeEvidence.ts)는 확인 기한 5초를 유지한다.
기한이 지난 동안 소유권·최초 사용·공식 사용량 확인 권한을 거절한다. 매초 검사에서
같은 경로의 일반 파일·크기·처음 검증한 내용의 SHA를 다시 확인한 경우만 사본을 갱신한다.
5초 이상 걸린 읽기는 완료돼도 새 증거로 쓰지 않고, 그 읽기가 끝난 후 다음 주기에 다시 검사한다.
진행 중 Promise는 공유하며 파일 IO를 무제한 중첩하지 않는다.

파일 변경·누락·읽기 오류, 시계 역행/비정상 값, 기존 attestation의 실제 만료·최대 나이,
공급자 종료는 계속 잠금으로 남는다. 파일을 돌려놓거나 늦은 응답이 도착해도 재개하지 않는다.
continuous 설정에 수동 승인 기한이나 대시보드 잔량을 새로 만들지 않는다.
기존 회수 미확인·감사·예산·입장 게이트는 각각 별도로 통과해야 한다.
이 변경이 중단된 경기를 성공으로 바꾸거나 READY/OPEN을 강제로 설정하지 않는다.

## 안전한 원인 관측

내부 진단은 현재/최초 실패 코드, 확인·지연 복구 횟수, 읽기 진행 여부,
최대 읽기 시간, 역행한 시계 차이만 가진다. 경로·파일 내용·토큰·Cloud 자격은 포함하지 않는다.
로컬 제품 통합 검사의 엄격한 IPC 실패 보고에 이 값을 연결한다. 공개 HTTP 진단 경로는 없다.

212의 첫 전체 검사에서는 기존 attested 제품 통합이 마지막 재경기 DEVICE_CHECK에서
`NAMESPACE_OWNERSHIP_UNCONFIRMED`로 멈췄다. 미해결 세대와 잔류 참가자는 모두 0이었다.
최초 원인 필드가 없었던 실행이므로 이 사건이 정확히 파일 검사 지연 때문이라고 확정하지 않는다.
진단만 추가한 단독/전체 재검사 25개(1개 미선택)/2,560개는 통과했다.
208/210의 과거 실패도 동일 원인으로 묶지 않는다.

검사 기한 후 재검증을 못 하는 별도 결함은 실제 파일·제어한 시계의 회귀로 확인했다.
수정 전 develop 파일을 사용하면 `restores permission after a verified lease delay`가
기대 true/실제 false로 실패했고 수정 후 통과했다. 실제 Cloud 지연이나 부하 증거는 아니다.
