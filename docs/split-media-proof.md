# 공개 미디어의 영상·음성 분리 검증

Jira [S15P21C204-211](https://ssafy.atlassian.net/browse/S15P21C204-211), W02 구조 검증.
선행 [실제 MC-PUBLIC-01](public-media-authority.md)은 격리 전달 후보를 확인했지만 제품 통합은 아니다.

## 추가로 확인하는 이유

현재 제품은 모든 다른 참가자의 얼굴 트랙을 허용하고 음성은 서버의 거리/역할 정책에 따라
허용한다. 고정 SDK2.18.0의 `forwardParticipant(room, identity, destinationRoom)`는
참가자의 모든 트랙을 함께 복제한다. 특정 음성 트랙만 선택하는 인자가 없다.
[공식 참가자 전달 문서](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/)
및 저장소의 설치된 SDK 구현을 대조했다.

한 참가자가 영상/음성을 같이 게시하는 앞선 진단만으로는 “얼굴 유지·음성 차단”을 보장할 수 없다.
새 MC-PUBLIC-02는 두 사람이 각각 영상 게시 연결과 개인 음성 게시/수신 연결을 사용하는
후보를 시험한다. 두 연결의 제품 Runtime/장치/세대 수명 통합은 이 시험 이후다.

## 제한된 실제 전달 시나리오

1. CAMERA만 게시하는 얼굴 방1개와 참가자별 MIC 게시/수신 방2개를 만든다.
   얼굴 토큰은 canSubscribe=false, 음성 토큰은 자기 방에서만 canSubscribe=true다.
   원본4신원·최대 복제4개를 포함해 동시8참가자 이내다.
2. 각각 다른 사람의 얼굴만 개인 방에 전달한다. 악의적으로 모든 상대를 허용하고 직접 구독을
   시도해도 음성은 수신할 수 없어야 한다. 새 얼굴 색상은 실제 양성 대조다.
3. 서버가 A의 음성을 B의 방으로 전달하면 새 색/주파수 표식과 수신 bytes를 확인한다.
4. 전달된 A만 B 방에서 제거한다. 원본 게시자와 얼굴은 유지하고2초 동안 음성이 차단되는지
   확인한다. 단순 API 응답이나 조용한 화면만으로 통과하지 않는다.
5. 같은 원본/목적지에 다시 전달해 새 음성이 도착하는지 확인하고 반대 방향도 양성 대조한다.
   서버 조회와 브라우저의 실제 identity/participant SID/track SID를 대조한다.
   원본 대비 SID 유지 여부는 기록하며 복제와 원본이 같다고 미리 가정하지 않는다.
6. 모든 발급/전달 시도 대상을 먼저 정리 목록에 넣고 참가자 회수·부재·방 삭제를 확인한다.

`LiveKitGateway.forwardParticipant`는 기존 공통 API 예산·큐 기한·취소·전송 직전 권한 검사,
유한 SDK HTTP timeout·지역 자동 재전송 금지·안전한 오류/해시 관측을 사용한다.
MC-PUBLIC-01의 별도 직접 SDK 전달 경로도 이 경로로 옮겼다.
기존 제품 모드 fixture는 예상치 않은 전달을 성공으로 흉내 내지 않고 실패시킨다.

공통 Cloud 실행기·깨끗한 소스 SHA/lockfile·전용 `qa-public-` namespace가 필수다.
합성 미디어만 사용하며 실제 장치나 운영 namespace를 사용하지 않는다.
정상40/정리30호출, 시험240초+정리90초,3방/8참가자,50분/400MB 예약 이내로 실행한다.
기존 자격 파일은 동호스트 격리 시험에서만 사용하고 로컬/인자/증거로 추출하지 않는다.
누락·실패·미확인 회수는 `splitTransportVerified=false`이며 어떤 결과도
`productPublicReady`/`promotionAllowed`를 true로 만들지 않는다.

## 현재 요금제와 제품 통합 조건

2026-09-13 16:37 KST 실제 프로젝트 Quota and limits 화면에서 동시 참가자100,
API10,000/분을 확인했다. 내부 제품의 더 작은 API 제한은 이 값 때문에 자동 변경하지 않는다.
Billing은 Build 포함5,000분/50GB, 사용293분/약1GB, 다음 청구0달러였다.
이는 관측 시점의 값이며 다음 실제 실행 전에 예산 신선도를 다시 확인한다.
[공식 한도 설명](https://docs.livekit.io/deploy/admin/quotas-and-limits/)을 함께 참고한다.

아래는 후보 설계의 보수적 산정이며 실제 과금/부하 측정 결과가 아니다.

- 6인 한 경기: 얼굴 방1+개인 방6=7방, 실제 SDK 연결12개.
- 최대 얼굴 복제30개+음성 복제30개를 별도 예약하면 원본을 포함해72참가자다.
- 10경기는 실제 SDK 연결만120개여서 현재100 한도를 넘는 것으로 산정된다.
  복제가 quota/청구에 정확히 어떻게 반영되는지는 별도 확인이 필요하다.

현재 포함량을 넘기거나 요금제를 올려 시험하지 않는다.10방 목표를 임의로 완료 처리하거나
낮추지 않으며, 최종 후보의 실제 용량/비용 확인과 필요한 한도 결정은 W19 선행 조건이다.
제품 구현은 하나의 세대가 두 게시/수신 연결을 소유하도록 토큰·원본/복제 바인딩·서버 권한·
취소·회수·durable 재기동·사용량과 웹 수명을 함께 연결해야 한다.
실장치 입력/성능, G1 보안 전체와 공개 설정 전환은 별도 인수다.
