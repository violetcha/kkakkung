# 미디어 내구 이력 축약

관련 Jira: [S15P21C204-209](https://ssafy.atlassian.net/browse/S15P21C204-209), K02 / W05·W14.
현재 단계는 **이전·신규 사용량 형식 읽기 준비**다. 제품의 자동 축약/새 aggregate 쓰기는
아직 연결하지 않았으며 이 문서나 중간 커밋만으로 K02 완료를 선언하지 않는다.

## 형식과 중복 요청

`usage-checkpoint.json`의 기존 version/checksum envelope와 `official`/`reservations`를 읽는다.
새로운 선택 필드 `compacted`에는 version1, `retiredThroughEpochMs`, `compactedAtEpochMs`,
`reservationCount`, `minutes`, `bytes`를 둔다. 축약 시각과 경계는24시간 이상 떨어져야 하며
횟수/누계의 유효 범위와 남은 예약을 합친 오버플로를 검사한다.
누계는 로컬 보수 추정이며 공식 청구 잔량을 대신하지 않는다. 활성 예약 여유에서 다시 차감하지 않는다.

신규 미디어 예약은 `u1-<발급 epoch ms>-<UUID>`를 사용하고 추가 시간 조각은 기존처럼 `:<순번>`이다.
현재 남아 있는 기존 예약의 ID·중복 결과·회수 의무는 그대로다. 축약 경계가 있는 파일을 읽은 뒤
존재하지 않는 옛 ID 또는 경계 이전 요청을 새 예약으로 생성하지 않는다. 미래 시각·시계 역행도 거절한다.
이 ID는 서버 내부의 예약 식별자이며 플레이어의 임의 시각을 권위 입력으로 사용하지 않는다.

기존 파일을 읽고 정상 예약·회수·공식 대조를 수행하는 것만으로 `compacted`를 생성하지 않는다.
이미 존재하는 aggregate는 다음 쓰기와 재시작에도 보존한다. 빈 hot 목록이어도 실제 journal 경계가
없으면 정상 최초 설치로 바꾸지 않는다. 공유 retry의 옛 스냅샷이 이미 축약된 예약을 다시 기록하면
실패로 처리하고 현재 파일을 증거로 남긴다. 확인되지 않은 재시도를 조용히 삭제하지 않는다.

## 단계별 적용

1. 호환 reader와 신규 예약 식별자, retry 재생성 거절을 정상 배포한다.
   이 단계는 새 aggregate를 쓰지 않으므로 이전 이미지가 기존 파일과 새 ID를 계속 읽을 수 있다.
2. 해당 reader 이미지가 실제 last-good에 포함된 뒤 제품 축약 경로를 활성화한다.
   writer·기록·회수·사용량·입장 상태를 확인하고 모든 회수/정산 확인 뒤24시간을 보존한다.
3. journal checkpoint/회전, 두 retry 엔진의 종료 스냅샷과 공유 checkpoint 정리,
   사용량 aggregate 갱신 순서의 중간 장애·재시작을 검증한다. 미확인·진행 중 기록은 보존한다.
4. 실제 다수 종료 세대에서 보관량·재시작 조회 수·복구 기한을 확인한다.
   이전 reader가 확인된 digest로만 자동 롤백한다. 수동 파일 초기화로 복구하지 않는다.

2–4단계는 아직 미구현/미검증이다. 회전 가능 helper만 호출해 공유 retry/usage가 축약됐다고 하지 않는다.
운영 명령 감사 entries의 장기 requestId 인덱스, 실제 Cloud 부하와 외부 호스트 복원은 별도 범위다.

실제 디스크 기반 사용량 복원/예약/회수/공식 대조, 잘못된 누계·미래 경계·옛 요청 거절,
공유 retry의 재생성 거절, 실제 Coordinator 조립을 포함한5파일108회귀와 서버 타입을 통과했다.
처음 추가한 시험의 새 방/시간 조각 구분과 스키마 오류 기대값을 바로잡았고,
상속 타입의 private 필드 충돌도 수정했다. 208·209를 합치고 develop `c25bc88e`까지
동기화한 `166d834`의 전체 검사는246파일·2,513개·E2E14개로 통과했다.
원격/실제 배포·last-good와 후속 자동 축약은 아직 별도 확인한다.
