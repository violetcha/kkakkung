# 미디어 내구 이력 축약

관련 Jira: [S15P21C204-209](https://ssafy.atlassian.net/browse/S15P21C204-209), K02 / W05·W14.
현재 단계는 **자동 축약 병합·배포 확인과 과거 방 조회 개선**이다. reader는 MR !132/배포 #103으로
last-good를 확보했고 writer는 MR !133으로 병합했다. 중간 커밋만으로 K02 완료를 선언하지 않는다.

## 형식과 중복 요청

`usage-checkpoint.json`의 기존 version/checksum envelope와 `official`/`reservations`를 읽는다.
새로운 선택 필드 `compacted`에는 version1, `retiredThroughEpochMs`, `compactedAtEpochMs`,
`reservationCount`, `minutes`, `bytes`를 둔다. 축약 시각과 경계는24시간 이상 떨어져야 하며
횟수/누계의 유효 범위와 남은 예약을 합친 오버플로를 검사한다.
누계는 로컬 보수 추정이며 공식 청구 잔량을 대신하지 않는다. 활성 예약 여유에서 다시 차감하지 않는다.

신규 미디어 예약은 `u1-<발급 epoch ms>-<UUID>`를 사용하고 추가 시간 조각은 기존처럼 `:<순번>`이다.
현재 남아 있는 기존 예약의 ID·중복 결과·회수 의무는 그대로다. 축약 경계가 있는 파일을 읽은 뒤
존재하지 않는 옛 ID 또는 경계 이전 요청을 새 예약으로 생성하지 않는다. 살아 있는 같은 경기 예약의
새 시간 조각은 계속 허용하며 회수된 부모나 다른 경기의 조각은 거절한다. 미래 시각·시계 역행도 거절한다.
이 ID는 서버 내부의 예약 식별자이며 플레이어의 임의 시각을 권위 입력으로 사용하지 않는다.

기존 파일을 읽고 정상 예약·회수·공식 대조를 수행하는 것만으로 `compacted`를 생성하지 않는다.
이미 존재하는 aggregate는 다음 쓰기와 재시작에도 보존한다. 빈 hot 목록이어도 실제 journal 경계가
없으면 정상 최초 설치로 바꾸지 않는다. 공유 retry의 옛 스냅샷이 이미 축약된 예약을 다시 기록하면
실패로 처리하고 현재 파일을 증거로 남긴다. 확인되지 않은 재시도를 조용히 삭제하지 않는다.

## 단계별 적용

1. 호환 reader와 신규 예약 식별자, retry 재생성 거절을 정상 배포한다.
   이 단계는 새 aggregate를 쓰지 않으므로 이전 이미지가 기존 파일과 새 ID를 계속 읽을 수 있다.
2. 해당 reader 이미지가 실제 last-good에 포함된 뒤 제품 축약 경로를 활성화한다.
   writer·기록·회수·사용량·입장 상태를 확인하고 모든 회수/정산 확인 뒤24시간을 보존한다.
3. journal checkpoint/회전, 두 retry 엔진의 종료 스냅샷과 공유 checkpoint 정리,
   사용량 aggregate 갱신 순서의 중간 장애·재시작을 검증한다. 미확인·진행 중 기록은 보존한다.
4. 실제 다수 종료 세대에서 보관량·재시작 조회 수·복구 기한을 확인한다.
   이전 reader가 확인된 digest로만 자동 롤백한다. 수동 파일 초기화로 복구하지 않는다.

2–3단계는 제품 Coordinator와 실제 파일 회귀에 연결하고 전체·원격 검사를 통과했다.
4단계 중 과거 방 반복 조회 개선은 아래 조건으로 구현했다. 실제 다수 방/Cloud 비용·복구 기한 인수는 후속이다.
운영 명령 감사 entries의 장기 requestId 인덱스, 실제 Cloud 부하와 외부 호스트 복원은 별도 범위다.

## 축약 전 과거 방의 재조회

24시간 보관 중인 방도 매번 개별 조회·삭제·재조회를 하면 240방에서 최소 722회 API가 필요하다.
복구 시 아래 조건을 모두 갖춘 방은 처음과 마지막의 전체 방 목록 조회로 부재를 재검증한다.
나머지 방은 기존 개별 검사를 유지한다. 공유 API 예산과 복구 기한을 늘리지 않는다.

- 기록 무결성·단일 writer·namespace 소유권과 검증된 회수 프로필이 유효하다.
- 같은 방의 현재 저널이 복원 당시와 같고 모든 세대가 REVOKED다.
- 관련 예약의 모든 시간 조각이 같은 경기의 RELEASED이며 원격 회수와 사용량 확인 시각이 있다.
- 관련 retry도 REVOKED다. 원래 JWT 만료와 마지막 회수/정산/재시도 확인 뒤 10분이 모두 지났다.
  여기에 실제 검증된 시계 오차·회수 cutoff 여유와 1초를 더한다.
- 두 전체 조회에서 방이 없고 마지막 조회 뒤에도 위 조건이 그대로다.

LiveKit은 연결된 참가자에게 토큰을 갱신하며 갱신 유효기간은 10분과 원래 토큰 잔여기간 중 긴 쪽이다.
따라서 원래 JWT 만료나 방 목록에서의 부재만으로 검사를 생략하지 않는다.
근거는 [공식 토큰 갱신 문서](https://docs.livekit.io/frontends/reference/tokens-grants/#token-refresh)와
[공식 ListRooms API](https://docs.livekit.io/reference/other/roomservice-api/#listrooms)다.

방 재출현·잘못된 응답·통신 실패·새 세대·소유권 상실·시계 역행은 성공으로 처리하지 않는다.
이 조회 개선은 이력을 삭제하지 않는다. 실제 보관량 정리는 별도의 24시간 축약이 담당한다.

## 자동 처리와 장애 경계

Coordinator의 기존 유지보수 루프가 READY·빈 경기/연습/입장 대기에서 분당 최대1회 시작한다.
한 번에 최대256개 예약 묶음을 처리하고 긴 파일 쓰기가 미디어 권한 갱신을 기다리게 하지 않는다.
새 경기의 다른 예약은 계속 보존하며 종료 시에는 축약 쓰기부터 기다리고 shared/usage/journal을 닫는다.

각 묶음의 모든 조각이 RELEASED이고 회수·사용량 확인 뒤24시간이 지났으며 JWT도 만료돼야 한다.
관련 저널/retry가 모두 REVOKED인지, scope·예약 내용·writer·소유권·시각을 단계별로 다시 확인한다.
실행 중인 retry와 확인 콜백·대기 쓰기는 삭제하지 않는다. 순서는 다음과 같다.

1. journal checkpoint를 쓰고 로그를 회전한다. 미확인·최근 기록은 남긴다.
2. 현재/과거 retry 소유자의 직렬 큐에서 완료된 메모리 스냅샷을 정리한다.
3. 공유 retry 파일에서 같은 묶음만 제거한다. 이전 전체 스냅샷이 이를 되살리면 실패한다.
4. 앞 단계의 제거를 다시 확인하고 usage 누계·경계와 남은 예약을 원자적으로 쓴다.

각 단계 사이에 종료되면 아직 남은 RELEASED/REVOKED 증거로 다음 기동에서 재검증한다.
이력을 초기화하거나 가짜 예약을 만들지 않는다. 쓰기/소유권 실패는 발급을 잠그며 자동 resume를 하지 않는다.
일반 읽기·예약·공식 대조는 aggregate를 새로 만들지 않고 검증된 축약 경로만 작성한다.
