# 팀 협업 컨벤션

적용 저장소: `S15P21C204`. AI 작업 지침은 [AGENTS.md](../AGENTS.md), 설치·코드 경계·검사는 [CONTRIBUTING.md](../CONTRIBUTING.md)를 함께 읽는다. 팀이 명시적으로 정한 규칙은 **커밋·MR 제목에 scope를 쓰지 않는 것**과 **관련 Jira가 있는 커밋의 본문 또는 푸터에 실제 이슈 키를 적는 것**이다.

## AI에게 작업을 맡길 때

AI 도구가 지침을 자동으로 읽는다고 가정하지 않는다. 대괄호 부분을 채워 전달한다.

```text
저장소 루트의 AGENTS.md와 docs/collaboration-conventions.md를 먼저 읽고 따라줘.
제품 기준은 docs/product-spec.md와 docs/spec/decisions.md, 파트별 구현은 docs/impl/야.
이번 작업은 [작업 내용]이고, 관련 Jira는 [실제 이슈 키 또는 없음]이야.
커밋·MR 제목은 scope 없이 type: 변경 내용 형식, 커밋 마지막 문단에는 Jira 키만 단독 줄로 적어줘.
이번 실행 범위는 [예: 구현·검증·로컬 커밋까지]야. 푸시·MR 생성·병합은 [내가 직접 / 요청할 때만] 해줘.
내 Git 신원을 유지하고 AI 공동 저자는 넣지 마.
작업 후 변경 내용, 실제 검증 결과, 남은 사항을 보고해줘.
```

## Jira

- 기능·업무 영역별 에픽 아래 스토리로 관리한다. 제목은 `[BE] 작업 내용`처럼 영역을 앞에 붙인다: `[BE]`, `[FE]`, `[AI]`, `[DevOps]`, `[QA]`, `[docs]`, 여러 영역은 `[FE/BE]`.
- 프로젝트 키와 번호는 실제 이슈에서 확인한다. 저장소 이름으로 키를 추측하거나 이전 프로젝트 키(`S15P11C206-*`)를 쓰지 않는다.
- 상태는 할 일 → 진행 중 → 완료. MR 병합과 Jira 완료는 따로 확인하며 자동 전환을 가정하지 않는다. 스프린트는 보드의 활성 스프린트를 쓴다.
- 한 스토리에 여러 MR을 연결할 수 있다.

```markdown
## 배경

현재 문제 또는 작업이 필요한 상황

## 목적

작업 후 달성할 결과

## 작업 내용

- 구현하거나 수정할 내용

## 완료 조건

- 완료 여부를 확인할 동작과 검증 조건

## 관련 MR

- 실제 MR 번호·링크·상태

## 선행·후행

- 관련 스토리
```

## 브랜치

통합 브랜치는 `develop`이다.

```text
<type>/<실제-Jira-키>-<영문-kebab-case-설명>
feat/S15P21C204-251-ten-room-capacity
docs/S15P21C204-252-docs-cleanup
```

다른 작업자의 브랜치나 미커밋 변경을 덮어쓰지 않는다. 관련 Jira가 없으면 번호를 만들지 말고 MR에 이유를 적는다.

## 커밋과 MR 제목

```text
<type>: 변경 내용
```

| 타입       | 사용 목적                      |
| ---------- | ------------------------------ |
| `feat`     | 기능 추가                      |
| `fix`      | 오류 수정                      |
| `refactor` | 동작을 유지하는 내부 구조 정리 |
| `docs`     | 문서 작성·수정                 |
| `chore`    | 의존성·도구 등 유지보수        |
| `ci`       | CI·배포 파이프라인 구성        |
| `test`     | 테스트 추가·수정               |
| `design`   | 화면 스타일·디자인 수정        |

관련 Jira가 있는 커밋은 마지막 문단에 접두사 없이 키만 단독 줄로 쓴다. 여러 키는 한 줄에 하나씩.

```text
fix: 준비 상태 변경 시 중복 요청 처리 오류 수정

이미 반영한 요청을 다시 받아도 준비 상태가 뒤집히지 않도록 수정한다.

S15P21C204-000
```

GitLab for Jira Cloud app은 커밋 메시지의 키로 커밋을, 브랜치 이름의 키로 브랜치를, MR 제목·설명의 키로 MR을 연결한다. 브랜치 키만으로 커밋 연결을 보장하지 않으므로 커밋과 MR 본문에 각각 적는다. 키 참조는 Jira 상태를 바꾸지 않는다.

Windows PowerShell 5.1에서 `Set-Content -Encoding utf8`로 만든 메시지 파일은 BOM이 붙어 커밋 제목이 깨진다. BOM 없는 UTF-8로 쓴다.

## MR 본문

[MR 템플릿](../.gitlab/merge_request_templates/default.md)의 다섯 항목을 유지한다. 하지 않은 작업이나 실행하지 않은 검증을 적지 않는다.

```markdown
## 관련 Jira

실제 Jira 이슈 키 (없으면 그 사실과 이유)

## 변경 사항

- 구현하거나 수정한 내용

## 변경 이유

- 해결하려는 문제와 변경이 필요한 이유

## 리뷰 포인트

- 검토가 필요한 동작, 경계 조건, 설계 판단

## see also

- 관련 문서·MR
- 실행한 검증 명령과 결과
- 미검증 항목과 이유
```

공개 계약을 바꾸면 해당 생산자와 소비자 담당이 함께 리뷰한다(예: 서버 private-view·응답 → 웹·비전, 미디어 바인딩·세대 → 서버 Room·비전, 센서 callback → 웹, Worker·CSP → 비전).

## 구현 문서

파트별 구현은 [구현 명세](impl/)에 둔다. 코드를 바꾸면 그 동작을 소유한 파트 문서를 같은 변경에서 고친다. 문서는 코드에서 확인한 현재 사실만 적고, 수치·조건마다 코드 줄을 근거로 단다. 날짜별 작업 일지는 쌓지 않고 끝난 이력은 git 기록과 MR에 남긴다.

## 병합과 배포

- MR은 `develop`으로 병합한다. 병합하면 Jenkins가 검증·이미지 빌드·제품 배포까지 이어서 실행한다.
- 원격 CI 성공, MR 병합, 실제 배포 성공(`release.json=READY`, 실행 이미지 SHA, READY/OPEN)은 각각 확인한다.
- 소스 브랜치는 병합 시 삭제한다. 보호 브랜치·필수 승인 규칙이 있다고 가정하지 않고 실제 설정을 확인한다.
