# CI·배포·운영 구현 명세

## 1. 역할과 경계

이 파트는 저장소가 스스로 검증하고, 커밋 SHA로 이미지를 만들고, 한 대의 호스트에 배포·롤백하고, 배포된 서비스를 감시하는 방식을 소유한다. 실행 주체는 세 층이다. Jenkins 파이프라인(`Jenkinsfile`, `infra/jenkins/*.Jenkinsfile`)이 단계 순서와 잠금을 정하고, `scripts/`의 Node 스크립트가 판단(검사 계획·생략·배포 장벽)을 하고, `infra/`의 compose·nginx·Dockerfile이 실행 환경을 정한다. Jenkinsfile은 `docker compose`를 직접 부르지 않는다. 컨테이너 교체는 `scripts/deploy-release.mjs`만 한다.

배포 스크립트 일부는 다른 파트의 코드를 직접 import한다. `product-release.mjs`는 서버의 `ProductDeployment.ts`를, 실패 기동 복구는 서버 `operations/`의 검증 함수를, DP-06 사전 검사는 `tests/cloud/`의 preflight 파서를 쓴다. 워크스페이스 경계 검사(`check-boundaries.mjs`)는 `apps/web`, `server`, `packages/*`의 `src`만 보고 `scripts/`와 `tests/`는 검사하지 않는다.

| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| server    | `/health/live`, `/health/ready`, `/api/operations/status`, `/api/operations/commands`, 운영 명령 snapshot, `/api/operations/invitations`, `/api/config`, 환경 변수 의미 | [server.md](server.md)       |

Verify의 트리 해시는 이렇게 정한다. 배포가 아닌 빌드는 먼저 남아 있던 병합을 `git merge --abort`로 지우고 `git merge --no-commit --no-ff origin/develop`을 시도한다. 성공하면 `MERGED_TREE=true`이고 트리는 `git write-tree`, 실패하면 병합을 취소하고 `HEAD^{tree}`를 쓴다. HEAD는 움직이지 않는다. 범위는 배포 빌드면 `deploy`, 아니면 `mr`이다. 검증 기록은 `$STATE_DIR/verified-trees/<tree>.json`(`mr`) 또는 `$STATE_DIR/verified-trees-deploy/<tree>.json`(`deploy`)에 `tree`, `commit`, `build`(`$JOB_NAME#$BUILD_NUMBER`), `verifiedAt`로 남고, 쓸 때마다 수정 시각 순으로 최신 200개만 남긴다. 형식이 깨진 기록은 없는 것으로 본다.

### 2.4 검증 대상 SHA

`trigger-commit.mjs`는 체크아웃 SHA(`--head`), 배포 빌드 여부(`--deploy`, `IS_DEPLOY` 값), GitLab 변수 `gitlabMergeRequestLastCommit`(`--mr`), `gitlabAfter`(`--push`)를 받는다. 알려온 커밋은 `--mr`이 있으면 그것, 없으면 `--push`다. SHA 형식은 소문자화 뒤 `[0-9a-f]{7,40}`이다.

| 경우                                                   | 결과                                                                                |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 체크아웃 SHA 형식 오류                                 | 종료 1                                                                              |
| 알려온 커밋 형식 오류                                  | 종료 1                                                                              |
| 배포 빌드                                              | 체크아웃 SHA를 그대로 출력. 알려온 커밋과 달라도 멈추지 않고 stderr에 설명만 남긴다 |
| 배포가 아니고 체크아웃이 알려온 커밋으로 시작하지 않음 | 종료 1 (소스 브랜치에 새 push가 왔다는 뜻)                                          |
| 알려온 커밋 없음                                       | 체크아웃 SHA 출력                                                                   |
| 모르는 인자                                            | 종료 2                                                                              |

stdout에는 SHA 하나만 쓰고 설명은 stderr로만 낸다. `ci-verify.mjs`가 설치 전에 이 값과 실제 `HEAD`를 다시 대조한다(3.1절).

### 2.5 호스트 잠금

잠금을 쓰는 곳은 모두 `/var/lib/jenkins/verify.lock` 하나를 쓴다. `livekit-usage`·`watchdog` 잡은 잠금을 쓰지 않는다.

| 위치              | 잠금 방식                                                                      | 잠금 범위                                                                     |
| ----------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `Verify`          | `flock /var/lib/jenkins/verify.lock docker run ... node scripts/ci-verify.mjs` | CI 컨테이너 실행 동안만. 앞뒤 `host_state`와 `verified-tree record`는 잠금 밖 |
| `Build images`    | `exec 9>...; flock 9`                                                          | 그 `sh` 블록 끝까지(`build-release-images.mjs` 전체)                          |
| `Deploy` 재빌드   | `exec 9>...; flock 9`                                                          | `pnpm install --frozen-lockfile && pnpm build:packages` 컨테이너              |
| `Deploy` product  | `exec 9>...; flock 9`                                                          | `--check-only` 실행, `production.env` 설치, 실제 배포 실행까지 한 블록        |
| `Deploy` skeleton | `exec 9>...; flock 9`                                                          | `production.env` 설치, `verify-release.mjs`, `deploy-release.mjs`             |
| `image-scan` 잡   | `flock ... docker run trivy`                                                   | 이미지 하나 스캔마다                                                          |

잠금이 없는 곳: `Prepare`(CI 이미지 빌드 포함), `Secret scan`, `post`의 이미지 정리. Verify는 잠금 전후로 `/proc/loadavg`의 부하 세 값과 `/proc/stat`의 steal·idle 틱을 로그에 남긴다. Deploy는 빌드마다 두 `sh` 블록(재빌드, 프로파일별 배포)을 돌리고 각 블록이 잠금을 따로 잡고 놓으므로, 두 블록 사이에 다른 잡이 끼어들 수 있다.

### 2.6 Verify·Deploy의 컨테이너 실행

Verify와 Deploy 재빌드는 같은 CI 이미지를 jenkins uid/gid(`-u "$(id -u):$(id -g)"`)로 띄운다. 공통 환경은 `HOME=/tmp`, `CI=true`, `npm_config_prefix=/tmp/npm`, `PNPM_HOME=/tmp/pnpm`, `npm_config_store_dir=/tmp/pnpm-store`이고, 호스트 `/var/lib/jenkins/.cache/pnpm-store`를 `/tmp/pnpm-store`에, `$WORKSPACE`를 `/workspace`에 마운트한다. Verify는 여기에 `EXPECTED_SOURCE_SHA`와 `CI_VERIFY_MODE=$VERIFY_SCOPE`를 더한다.

Deploy는 조건 없이 먼저 작업 공간에서 `pnpm install --frozen-lockfile && pnpm build:packages`를 실행한다. Verify가 생략됐더라도 배포 스크립트와 DP-06 스모크가 읽는 `packages/*/dist`가 이 작업 공간에서 만들어진다. 이후 배포 스크립트는 CI 컨테이너가 아니라 Jenkins 호스트의 `node`로 돈다.

| 프로파일   | Deploy가 실행하는 명령                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `product`  | `set +x` 후 `node --import tsx scripts/product-release.mjs --check-only --env-file "$PROD_ENV_FILE" ...` → `install -m 600 "$PROD_ENV_FILE" "$STATE_DIR/production.env"` → 같은 스크립트를 `--env-file "$STATE_DIR/production.env"`로 실제 실행. 공통 인자 `--evidence-dir "$STATE_DIR/runtime-evidence" --preflight "$STATE_DIR/cloud-preflight.json" --sha "$GIT_SHA" --base-url "$PUBLIC_URL" --state-dir "$STATE_DIR"` |
| `skeleton` | `production.env` 설치 → `verify-release.mjs --sha --tag --verified-sha "$GIT_SHA" --profile skeleton --output "$STATE_DIR/releases/$TAG.json"` → `deploy-release.mjs --manifest ... --evidence "$STATE_DIR/releases/$TAG" --base-url "$PUBLIC_URL" --state-dir "$STATE_DIR"`                                                                                                                                               |

### 3.1 검증 진입점의 단계와 실패 코드

`scripts/ci-verify.mjs`의 순서는 도구체인 확인 → 검증 대상 SHA 대조 → 모드 확인 → `pnpm install --frozen-lockfile` → Chromium 확인 → 검사다. `CI_VERIFY_DRY_RUN=1`이어도 도구체인 확인, SHA 대조, 모드 확인, `mr` 모드의 변경 목록 계산(`git diff`)은 실제로 하고 그 실패 코드로 끝난다. 출력만 하고 실행하지 않는 것은 install, Chromium 설치, 계획의 검사 명령이다.

## 5. 릴리스 이미지·매니페스트·정리

`build-release-images.mjs <40자리 SHA>`는 `kkakkung-game:<SHA 8자>`(`Dockerfile.game-server`)와 `kkakkung-web:<SHA 8자>`(`Dockerfile.web`)를 저장소 루트 컨텍스트로 만들고 라벨 `org.opencontainers.image.revision=<전체 SHA>`를 붙인다. 태그가 이미 있으면 다시 빌드하지 않는다. 기존 태그의 라벨이 다르면 `EXISTING_IMAGE_REVISION_MISMATCH`, 빌드 실패는 `IMAGE_BUILD_FAILED`, 빌드한 이미지의 라벨이 다르면 `BUILT_IMAGE_REVISION_MISMATCH`, SHA 형식 오류는 `INVALID_RELEASE_SHA`이고 모두 종료 1이다.

`verify-release.mjs`는 이미지를 만들지 않는다. 두 이미지를 `docker image inspect`로 읽어 매니페스트(`releaseSha`, `tag`, `verifiedSha`, `profile`, 선택 `operatingMode`, `images.{game,web}.{ref,digest,revision}`, `previous`, `officialBudgetMaxAgeMs`, `createdAt`)를 쓴다. `previous`는 호스트의 `last-good-tag`(8자리 hex), `last-good-digest`(`game`·`web` 두 줄의 `sha256:<64hex>`), `last-good-profile`에서 만들고, 셋 중 태그나 두 digest가 없으면 `null`이다. 프로파일 기록이 없으면 `releases/<tag>.json`의 digest가 일치할 때만 거기서 프로파일을 가져온다. `operatingMode`와 `officialBudgetMaxAgeMs`도 digest가 일치하는 이전 매니페스트에서만 가져온다. 종료 코드는 0(작성), 2(사용법), 3(`BLOCKED: IMAGE_MISSING` 또는 `BLOCKED: MANIFEST_INVALID`)이다.

매니페스트 검증(`validateManifest`)은 문제를 모두 모아 돌려준다.

| 검사        | 규칙                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| SHA·태그    | `releaseSha` 40자리 hex, `tag` 8자리 hex이며 `releaseSha`의 접두사                                   |
| 검증 SHA    | `verifiedSha === releaseSha`                                                                         |
| 프로파일    | `product` 또는 `skeleton`                                                                            |
| 운영 모드   | 있으면 `attested`/`continuous`, `continuous`는 `product`에서만                                       |
| 이미지      | `game`·`web` 둘 다 필요, `ref`는 `이름:태그`, `digest`는 `sha256:<64hex>`, `revision === releaseSha` |
| 이전 릴리스 | 있으면 `tag` 8자리, 두 digest 형식, `operatingMode`·`profile`·`officialBudgetMaxAgeMs` 형식          |

| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1             | compose 교체 (phase `DEPLOYING`)                                                                                                                        | `<라벨>_COMPOSE_FAILED`                              |
| 2             | 로컬 `/health/ready` 200 대기. 503이고 본문 `state: 'RECOVERING'` 또는 `status: 'recovering'`을 처음 보면 phase `RECOVERING`, 기한을 `recoverMs`로 바꿈 | `<라벨>_READY_TIMEOUT`                               |
| 3             | 실행 중 두 컨테이너 이미지 = 매니페스트 digest                                                                                                          | `<라벨>_SWAP_MISMATCH`                               |
| 4 (운영)      | `readiness === 'READY'` 대기, `LOCKED`면 즉시 실패                                                                                                      | `<라벨>_READINESS_LOCKED`, `<라벨>_RECOVERY_TIMEOUT` |
| 5 (운영)      | `resume` 명령 → terminal → `admission=OPEN`, `readiness=READY`                                                                                          | `<라벨>_RESUME_*`, `<라벨>_RESUME_MISMATCH`          |
| 4' (skeleton) | ready 본문 `mediaEnabled`가 참이면 실패                                                                                                                 | `<라벨>_OPERATIONS_EXPECTED`                         |
| 6             | 스모크 (phase `SMOKE`). 운영 경로이고 롤백이 아니면 DP-06 Cloud, 그 밖(skeleton, 모든 롤백)은 HTTP                                                      | `SMOKE_FAILED`                                       |
| 7 (운영)      | 공개 재검사                                                                                                                                             | `PUBLICATION_CONDITIONS` (결과 `PUBLISH_BLOCKED`)    |

공개 재검사는 `readiness=READY`, `admission=OPEN`, `unresolvedCount=0`을 요구한다. `continuous`면 서버 `operatingMode`가 `continuous`이고 `remainingMinutes`, `remainingBytes`, `checkedAtEpochMs`가 모두 `null`이어야 한다. 그 밖이면 서버가 `continuous`가 아니어야 하고, 예산 최신성 값이 있고, `checkedAtEpochMs`가 0 이상·현재 이하이며 `현재 − checkedAt ≤ officialBudgetMaxAgeMs`여야 한다.

전진 장벽의 결과 처리:

- 통과하면 `last-good-tag`, `last-good-profile`, `last-good-digest`(`game <digest>` / `web  <digest>`)를 쓰고, 운영 경로면 결과 `READY`(phase `READY`), 아니면 `DEPLOYED_WITHOUT_OPERATIONS`(이유 `OPERATIONS_UNAVAILABLE`)다.
- `PUBLISH_BLOCKED`면 새 릴리스를 그대로 두고 롤백하지 않는다. last-good도 쓰지 않는다.
- 그 밖의 실패는 롤백한다. 운영 경로면 먼저 `ROLLBACK_DRAIN` 드레인, 이전 릴리스가 없으면 `NO_PREVIOUS_RELEASE`, 이전 digest 이미지가 없으면 `PREVIOUS_IMAGE_MISSING`, ID가 다르면 `PREVIOUS_DIGEST_MISMATCH`. 이전 릴리스로 장벽(`ROLLBACK`)을 다시 통과하면 결과 `ROLLED_BACK`, phase `READY`다. 롤백 중 어느 단계든 실패(롤백 장벽의 `PUBLISH_BLOCKED` 포함)하면 결과·phase `ROLLBACK_BLOCKED`, `detail`은 `<실패 세부>; original: <원래 원인>`이다.

롤백 장벽은 이전 릴리스의 `profile`(없으면 현재 판단), `operatingMode`(없으면 `attested`), `officialBudgetMaxAgeMs`(없으면 현재 매니페스트 값)를 쓴다. 롤백은 last-good을 쓰지 않는다.

## 8. 실패 기동 복구 (`--recover-failed-startup`)

이 경로는 서버를 띄우지 않는다. 한 번도 입장을 받지 못한 채 실패한 이전 배포 컨테이너를 정상 정지하고 운영 볼륨을 보관해, 다음 배포가 그 앞 릴리스의 drain 증거를 다시 쓰게 해 주는 사전 조건 검사다. 통과해도 그 뒤 일반 장벽(compose 교체·ready·resume·스모크·공개 재검사)은 그대로 돈다.

`ROLLBACK_BLOCKED`는 이 경로가 만드는 결과가 아니라 **입력 조건**이다. 대상 태그의 `releases/<tag>/release.json`이 정확히 다음이어야 한다: 결과 `ROLLBACK_BLOCKED`, 이유 `ROLLBACK_DRAIN_FAILED`, `lastGoodWritten: false`, product. 단계 기록은 정확히 `manifest`·`images`·`isolation`·`operations`·`DRAIN terminal`·`DRAIN state`·`RELEASE compose up`(PASS) → `RELEASE recovering`(INFO) → `RELEASE_READY_TIMEOUT`(FAIL) → `rollback start`(INFO) → `ROLLBACK_DRAIN_FAILED`(FAIL)의 11개이고, 시각이 단조 비감소(같은 시각 허용)하며, `DRAIN state` 세부가 `admission=DRAINING unresolved=0` 또는 `admission=LOCKED unresolved=0`, `RELEASE compose up` 세부가 `tag=<실패 태그>`여야 한다. 즉 새 이미지가 ready를 못 넘고, 롤백 drain이 실패해 멈춘 배포만 대상이다.

### 9.3 내부 스모크 리스너

`node scripts/write-smoke-proxy.mjs <토큰 파일> <출력 conf>`는 토큰 파일 내용이 64자리 소문자 hex가 아니면 `SMOKE_KEY_INVALID`로 실패한다. 인자 부족·형식 오류는 모두 잡히지 않은 예외로 던지므로(별도 `process.exit` 없음) 종료 코드는 Node 기본값 1이다. 검사를 통과하면 nginx 설정을 모드 600으로 쓴다. 그 설정 자체가 토큰을 `map` 지시자의 정규식(`~^<토큰>$`)에 그대로 담으므로, 이 스크립트는 발급 도구(12절 표의 세 도구)만큼 토큰을 파일에 쓰는 도구다. 설정은 `127.0.0.1:18081`에서 듣고, `X-Kkakkung-Smoke-Key`가 토큰과 정확히 같지 않으면 403이다. 통과한 요청은 `127.0.0.1:8080`으로 넘기되 키, `Cookie`, `X-Forwarded-User`, `X-Auth-Request-User`, `X-SSO-User`, `X-Demo-Admin`을 빈 값으로 지우고 WebSocket 업그레이드와 3,600초 읽기 제한을 둔다. 표준 출력·오류에는 토큰을 내지 않는다.

### 13.1 루트 스크립트와 `pnpm verify` 순서

루트는 `packageManager: pnpm@11.19.0`, `engines.node: >=24.19.0 <25`, `engines.pnpm: 11.19.0`이다. 워크스페이스는 `server`, `apps/*`, `packages/*`이고 빌드 허용은 `esbuild: true`, `msgpackr-extract: false`다.

`pnpm verify`는 아래 순서로 실행하고 앞 단계가 실패하면 멈춘다.

1. `format:check` — `prettier --check .`
2. `lint` — `eslint .` 후 `node scripts/check-boundaries.mjs`
3. `typecheck` — `build:packages`(`tsc -b tsconfig.packages.json`) → `pnpm -r typecheck` → `tsc -p tsconfig.qa.json --noEmit`
4. `test` — `build:packages` → `vitest run`
5. `build` — `build:packages` → `@kkakkung/game-server` build → `@kkakkung/web` build
6. `check:bundle` — `node scripts/inspect-public-bundle.mjs --directory apps/web/dist`(S15P21C204-402)
7. `check:product-assets` — `node scripts/check-product-assets.mjs`
8. `test:e2e` — `build:packages` → `playwright test`

그 밖 스크립트: `setup:env`, `dev`, `dev:web`, `dev:server`, `format`, `test:maps`(`certified-maps.test.ts`, `maze-template.test.ts`만), `maps:generate`, `maps:check`, `check:environment`, `cloud:check`, `probe:build`/`probe:dev`(`tests/cloud/vite.config.ts`), `livekit:token`, `deploy:smoke`(`deployment-smoke.mjs`). `maps:check`, `check:environment`, `check-security-headers.mjs`는 `pnpm verify`에 없다.

ESLint는 `dist`, `node_modules`, `.local`, `test-results`, `playwright-report`, `apps/web/public/models/**`를 무시한다. 추천 규칙에 `_`로 시작하는 인자를 허용하는 `no-unused-vars`를 더한다. 모든 `**/*.mjs`에는 `process`·`console`·`URL`·`setTimeout`·`clearTimeout`·`fetch`·`AbortController` 전역을 열어 주는 별도 블록이 있고, `scripts/check-security-headers.mjs`만 그 위에 `document`·`navigator`·`localStorage`·`setInterval`(이 스크립트의 일부가 Playwright `page.evaluate` 안에서 브라우저로 실행되기 때문)과 `no-empty`의 빈 catch 허용을 더 얹는다. `apps/web/**/*.{ts,tsx}`에서는 `@kkakkung/game-core`, `@kkakkung/game-core/*`, `**/game-server/**`, `**/server/**`, `**/packages/game-core/**` import를 금지한다. `packages/game-core/src/**/*.ts`에서는 전역 `Date`·`fetch`·`setTimeout`·`setInterval`과 `Math.random`을 금지한다.

`check-boundaries.mjs`(12절)의 경계 검사는 `.test.ts`로 끝나는 파일만 걷기에서 빼므로 `.test.tsx`는 제외되지 않고 그대로 검사된다. 의존성 목록도 각 `package.json`의 `dependencies`만 읽어 `devDependencies`는 보지 않는다.

### 13.4 Cloud 시험의 실행 조건

Cloud 케이스를 시작할 수 있는 곳은 `run-cloud-check.mjs --case <ID> --preflight <파일> --evidence <디렉터리> [--dry-run]` 하나다.

1. 케이스가 허용 목록에 있어야 한다. `QA-01`, `QA-07`, `QA-10`, `QA-13`은 로컬 전용이라 거절한다. 목록에 없거나 파일이 없거나 파일에 `it`/`test` 호출이 0개면 `BLOCKED` 종료 3이다.
2. preflight를 현재 `git rev-parse HEAD`, `pnpm-lock.yaml` sha256, 현재 시각, 환경과 대조한다. 알 수 없는 필드, `sourceCommit`·`lockfileHash` 불일치, 미래의 `checkedAt`, 만료, 잔여량 음수, 허용 케이스 누락, 예약 초과, 환경에 없는 자격 이름, 장치 매니페스트 없음, `QA-02`·`QA-09`의 대표 장치 아님, 증거 경로가 `.local/qa/` 밖이거나 `..` 포함, 방당 6석 초과, `참가자 × (실행 + 정리)초 ÷ 60 > 예약 참가자-분`, `QA-11`의 단계 시간 누락이면 거절한다. 거절은 `BLOCKED: preflight rejected`와 문제 목록, 종료 3이다.
3. `--evidence`가 preflight의 `evidenceDir`와 달라도 종료 3이다.
4. `--dry-run`이면 요약만 출력한다. 아니면 `pnpm exec vitest run --config vitest.cloud.config.ts <파일>`을 `RUN_CLOUD_TESTS=1`, `CLOUD_TEST_CASE`, `CLOUD_PREFLIGHT_PATH`, `CLOUD_EVIDENCE_DIR`로 실행하고 `run-summary.json`을 쓴 뒤 Vitest 종료 코드로 끝낸다.

## 14. 주요 흐름

### 14.1 MR 빌드

1. Prepare: 체크아웃이 GitLab이 알려온 MR 커밋과 접두 일치로 확인한다(알려온 커밋이 없으면 그대로 통과). 이미지 입력 변경 여부와 `origin/develop..HEAD` 스캔 범위를 정한다.
2. Secret scan: 범위 안의 커밋을 gitleaks로 검사한다.
3. Verify: 작업 공간에서 develop을 병합(실패하면 소스 그대로)한다. 트리 해시의 `mr` 기록이 있으면 생략하고, 없으면 잠금 아래 CI 컨테이너에서 변경 경로 기반 MR 계획을 돌린 뒤 기록한다.
4. Build images: 이미지 입력이 바뀐 경우만 잠금 아래 빌드한다.
5. Deploy: 건너뛴다. `post`에서 상태 게시, 성공 시 이미지 정리, 항상 병합 취소·dangling 이미지 정리를 한다.

### 14.2 develop 제품 배포

1. Prepare: 체크아웃 SHA를 그대로 검증 대상으로 정하고, 이미 배포된 머리인지(사람이 시작한 빌드 제외) 판정한다.
2. Secret scan: `last-good-tag..HEAD`를 스캔한다.
3. Verify: `deploy` 기록이 없으면 typecheck와 무거운 통합 시험 두 파일을 돌린다.
4. Build images: 커밋 태그 이미지를 재사용하거나 빌드한다.
5. Deploy: 잠금 아래 작업 공간을 재빌드한다. `product-release --check-only`로 환경·증거·preflight를 확인하고, 환경 파일을 설치한 뒤 실제 실행한다: 매니페스트 → 격리 검사 → drain → compose 교체 → ready/RECOVERING → readiness → resume → DP-06 → 공개 재검사 → last-good 기록.
6. 실패 시 교체 후 실패면 드레인 → 이전 digest로 같은 장벽 재통과(HTTP 스모크) → `ROLLED_BACK`, 불가면 `ROLLBACK_BLOCKED`로 남기고 `post { failure }`가 기록을 출력하고 DM을 보낸다.

### 14.3 실패한 첫 기동 복구

1. 이전 배포가 `ROLLBACK_BLOCKED`/`ROLLBACK_DRAIN_FAILED`로 멈춰 새 컨테이너가 `LOCKED` 상태로 남아 있다.
2. 운영자가 `product-release.mjs --recover-failed-startup <실패 태그>`로 새 커밋을 배포한다(Jenkinsfile은 이 인자를 넘기지 않는다).
3. 시퀀스는 격리 검사 뒤 drain 대신 복구 어댑터로 두 번 관측·검증하고 컨테이너를 정상 정지·보관한다.
4. 이후 일반 장벽을 그대로 통과해야 `READY`다.

## 15. 상태 기계

배포 시퀀스의 phase 전이다. phase는 `release.json`에 기록되고, 최종 결과는 phase와 별도의 `result`다.

| 현재 phase                       | 조건                                                                 | 다음 phase / 결과                                              |
| -------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------- |
| (시작) `BLOCKED`                 | 매니페스트·이미지·토큰·preflight·격리·운영 경로·복구 가드 실패       | `BLOCKED` / `BLOCKED` (종료 3)                                 |
| `BLOCKED`                        | 운영 경로 있음, 드레인 시작                                          | `DRAINING`                                                     |
| `BLOCKED`                        | 운영 경로 없음(skeleton) 또는 복구 가드 통과                         | `DEPLOYING`                                                    |
| `BLOCKED`                        | 첫 product 전환: 실행 중 이미지가 검증된 이전 skeleton digest와 다름 | `BLOCKED` / `FAILED`(`MIGRATION_SOURCE_SWAP_MISMATCH`, 종료 1) |
| `DRAINING`                       | drain terminal 실패·시간 초과·상태 불일치                            | `DRAINING` / `FAILED` (롤백 없음)                              |
| `DRAINING`                       | drain 확인                                                           | `DEPLOYING`                                                    |
| `DEPLOYING`                      | ready 503 `RECOVERING` 첫 관측                                       | `RECOVERING`                                                   |
| `DEPLOYING`·`RECOVERING`         | ready·이미지·readiness·resume 통과                                   | `SMOKE`                                                        |
| `SMOKE`                          | 스모크·공개 재검사 통과, 운영 경로                                   | `READY` / `READY`                                              |
| `SMOKE`                          | 스모크 통과, skeleton                                                | `SMOKE` / `DEPLOYED_WITHOUT_OPERATIONS`                        |
| `SMOKE`                          | 공개 재검사 실패                                                     | `SMOKE` / `PUBLISH_BLOCKED` (롤백 없음)                        |

| 롤백 중                          | 이전 릴리스 없음·이미지 없음·digest 불일치·장벽 실패                 | `ROLLBACK_BLOCKED` / `ROLLBACK_BLOCKED`                        |

### 미설명

- `infra/README.md`, `infra/SSO.md`, `infra/jenkins/SETUP.md`: 근거 불인정 문서.
- `infra/.env.example`, `infra/production.env.example`, `infra/sso.env.example`: 변수 이름의 틀이다. 값의 의미는 server.md 소유이고, 이 문서에서는 주석 불일치 한 곳만 인용했다.
