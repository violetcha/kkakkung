# game-core 구현 명세

## 1. 역할과 경계

`@kkakkung/game-core`는 두 진입점을 낸다. `./match`는 제품 규칙이다. 서버가 넘겨준 맵·튜닝·명단·인증된 명령으로 순수 상태 전이를 계산하고, 파일·시계·네트워크는 읽지 않는다. `.`(루트)는 연속 좌표를 쓰는 진단용 월드다. 패키지에는 런타임 의존성이 없다. 빌드는 `tsc -b`, 개발 감시는 `tsc -b --watch`, 타입 검사는 `tsc --noEmit`이다. `tsconfig.json`은 루트 기본 설정을 확장하고 `src/**/*.ts`를 컴파일한다(`src/**/*.test.ts` 제외). 선언·선언 맵·소스 맵은 `dist`에 나온다. `test/` 아래 시험은 컴파일 범위 밖에 있고 루트 Vitest 설정으로 실행된다.

## 2. 진단 월드와 진단 API

루트 진단 월드는 제품 규칙이 아니다. `createWorld`는 `halfExtent > 0`과 `speed ≥ 0`을 요구하고 틱 0, 빈 명단으로 시작한다. `addPlayer`는 비어 있지 않은 ID와 20자 이하 닉네임을 받아 `(0, 0)`, `lastSeq -1`로 등록하고, 이미 있는 ID면 예외를 던진다. `stepWorld`는 명령마다 `seq`가 음이 아닌 안전 정수인지, `x`·`z`가 -1~1인지 검사한다. 플레이어별로 `lastSeq`보다 크고 가장 큰 `seq` 명령 하나만 적용한다. 대각선 입력은 길이 1로 정규화하고, `speed × dtSeconds`만큼 움직인 뒤 ±`halfExtent`로 자르며, 틱을 1 올린다. 이전 상태 객체는 바꾸지 않는다. sandbox `GameRoom`은 `halfExtent 8`, `speed 4`, `dtSeconds 0.05`로 이 월드를 돌린다.

`match/index.ts`의 진단 API는 `GameSnapshot`을 쓴다. `tryMove`는 참가자 존재·`alive`·`trapped`와 32칸 경계만 검사하고, 벽·점유·쿨다운은 보지 않으며 상태도 바꾸지 않는다. `checkCapture`는 항상 빈 배열을, `checkWinCondition`은 항상 `null`을 돌려준다. `generateMaze`는 시드를 무시하고 외곽과 4칸 간격 기둥으로 된 32×32 고정 격자를 만든다. `pickSpawn`은 도망자를 `(2 + 10i, 2)` 남향, 술래를 `(2 + 10i, 29)` 북향에 놓는다.

## 3. 경기 생성과 상태

`createMatch`는 팀마다 1~3명을 허용한다. 다음 경우에는 `RangeError`를 던진다: 빈 팀, 한 팀 4명 이상, 배치 플레이어 수와 명단 수 불일치, 술래 영역 수가 술래 수와 다르거나 영역이 없는 술래가 있음, 빈 `matchId`·`gameInstanceId`, uint32가 아닌 시드, 중복 플레이어 ID, 배치에 없는 플레이어, 배치 역할 불일치, 출구 등록 실패(`exit registry: <코드>`, 8절 표). 기본값은 단계 `GAME_LOADING`, 결과 정책 `rules`, 제한시간 `round`이다. 도망자마다 출구 하나가 등록된다. 초기 장비는 술래 센서 1·함정 1, 도망자 0·0이다. 도망자는 자기 출발 셀만, 술래는 자기 영역 셀과 그 둘레 벽면을 처음부터 알고, 출발 자세에서 처음 본 셀·벽면도 생성 시점의 지식에 들어간다.

`createPractice`는 지정 역할 한 팀 1~3명만 받고 `TEAM_PRACTICE`에서 시작한다. 출구 등록부와 우선순위 순서를 만들지 않고, `deadline`·`result` 입력은 무시한다. 이동·회전·도망자 간 교환·술래 설치 규칙은 같다. 다만 포획·팀 승패·제한시간·잡기는 없고, 함정은 우선순위 순서가 없어서 발동하지 않는다. 연습 배치에는 출구가 없으므로 `EXIT_START`는 항상 거절된다. 경기와 연습은 각자 `gameInstanceId`와 `MatchState`를 가진다.

`MatchState`는 참가자별로 진행 중 동작, 대기 턴, 유지 이동, 잡기 창 끝 틱, 구속·면역 끝 틱, 장비 재고·소유 장비, 설치·교환·탈출 도전, 다음 도전 가능 틱을 기록한다. 경기 단위로는 출구 등록부, 교환 세션, 지연 흔적, 설치 예약, 지식, 현재 가시 표면, 교환·설치·도전·이벤트 시퀀스를 보관한다.

읽기 투영의 규칙:

- `getPlayerSelf`는 종료한 참가자에게 `playerId`·역할·종료 상태만 돌려주고, 활성 참가자의 `loading`은 항상 `null`이다.
- `getVisibleEntities`는 현재 가시 셀에 있는 다른 활성 참가자를 돌려준다. 이동 중이면 출발 셀이나 도착 셀 중 하나만 보여도 된다. 장비는 `SPENT`가 아니면서 가시 셀에 있는 것만 돌려준다. 센서에는 벽면이 붙고, 소유자는 어느 쪽에도 붙지 않는다.
- `getPlayerKnowledge`는 기록이 없으면 `mapVersion 0`과 빈 목록을 돌려주고, 술래에게는 활성 출구 목록을 항상 비워서 준다.

## 5. 틱 처리와 명령 거절

`stepMatch`는 정수 틱만 받고, 직전 틱보다 크지 않으면 `RangeError`를 던진다. 상태가 이미 `RESULT`나 `ABORTED`면 명령마다 `canceled/ROUND_ENDED`를 하나씩 내고, 이벤트·효과·제어 처리 없이 틱만 기록한다. 그 밖의 틱은 다음 순서로 처리한다.

1. 제어 중 `START_PLAYING`과 `EXPIRE_MOVE`를 들어온 순서대로 적용한다. `START_PLAYING`은 경기이면서 `GAME_LOADING`이고 `startTick`이 현재 틱 이하 정수일 때만 `PLAYING`으로 바꾼다. 이때 `deadlineTick`을 `startTick + roundTicks`로 정하고, `deadline: none`이면 `null`로 둔다.
2. 끝 틱에 이른 구속을 풀고, 그 끝 틱부터 면역을 시작한다.
3. 이미 예약된 이동·회전 중 끝 틱에 이른 것을 완료하고, 이동마다 발소리를 낸다. 경기 `PLAYING`이면 완료 전후 위치로 포획을 판정한다.
4. 설치 예약을 정리한다(자세 상실 시 취소, 끝 틱이면 장비 생성). 무장 틱에 이른 장비를 무장한다. 제한시간을 뺀 즉시 승패가 났으면 이 틱의 명령을 모두 `canceled/ROUND_ENDED`로 끝내고 5·6단계를 건너뛰어 7단계로 간다. 이 경우 그 틱의 교환 세션 정리와 흔적 공개도 일어나지 않는다.
5. 장비 발동, 탈출 도전 정리(만료. 나머지 분기는 방어 코드, 9절), 명령 처리(입력 순서), 대기 동작 시작을 차례로 한다.
6. 교환 세션을 정리하고, 공개 틱에 이른 흔적을 활성 술래에게 보내고, 제한시간을 포함해 승패를 판정한다.
7. 제어 중 `CONNECTION_LOST`, `ABORT_MATCH`, `PLACE_PLAYER`를 순서대로 적용하고(4단계에서 종료했어도 실행), 모든 활성 참가자의 시야·지식을 새로 계산한다.

## 6. 이동·회전·포획·승패

격자는 정수 셀이고 방향은 북 0(y-1)·동 1(x+1)·남 2(y+1)·서 3(x-1)이다. 전진은 바라보는 방향으로, 후진은 반대 방향으로 한 칸이며, 그 칸이 격자 안의 통로여야 예약된다. 다른 참가자의 점유는 검사하지 않는다. 이동은 `moveTicks`, 회전은 `turnTicks` 길이의 `Action`이 되고, 권위 셀·방향은 끝 틱에 완료할 때만 바뀐다. 동작 슬롯은 하나라서 이동과 회전이 겹치지 않는다. 회전은 왼쪽이 -1, 오른쪽이 +1(mod 4)이다.

입력 버퍼는 유지 이동 하나와 대기 턴 하나를 담는다. 정지한 활성 참가자는 틱마다 대기 턴을 먼저 소비하고, 대기 턴이 없으면 구속 중이 아닐 때 유지 이동을 다시 예약한다. 이 재예약이 막히면 결과 없이 넘어간다. 도전 중이거나 설치 중인 참가자는 재개하지 않는다. `EXPIRE_MOVE`는 유지 이동의 시퀀스가 제어의 시퀀스 이하일 때만 유지 이동을 지운다. 따라서 만료 판단 뒤에 도착한 새 입력은 살아남는다. 이동이 완료될 때마다 `footstep` 공간 효과음(도착 셀, `sourcePlayerId`)이 한 번 난다.

## 7. 술래 장비·구속

설치는 활성 술래가 동작 없이 서 있고, 다른 설치가 없고, 그 종류의 재고가 있을 때 시작한다. 함정은 자기가 서 있는 통로 셀에, 센서는 바라보는 칸이 내부 벽일 때 그 벽의 자기 쪽 면에 놓는다. 다음 경우는 거절한다: 모든 참가자의 시작 셀, 외곽 벽, 같은 셀이나 같은 벽면을 장비 또는 예약이 이미 차지함(소유자 무관). 출구 등록부는 읽지 않으므로 출구 벽도 일반 벽과 같다.

예약하면 `ins-N`(장비 `eq-N`)이 생기고, 끝 틱은 `+installationTicks`, 무장 틱은 끝 틱 `+armTicks`이다. 공개 `InstallationView`에는 ID·종류·세 틱만 들어가고, 목표 셀·방향·벽면은 서버 내부 `PendingInstallation`에만 있다. 매 틱 정리 단계에서 소유자가 활성이 아니거나, 움직이거나, 셀·방향이 바뀌었으면 비용 없이 예약을 지운다. 끝 틱까지 버티면 재고 1을 쓰고 `UNARMED` 장비를 만든다. 무장 틱이 되면 `ARMED`가 된다.

## 8. 지도 교환·지식·시야

교환 조건은 다음을 모두 만족해야 한다.

- 두 참가자 모두 활성 도망자이고 서로 다른 사람이다.
- 같은 셀이거나 직교로 이웃한 통로 셀에 있다(대각선 불가).
- 둘 다 구속 중이 아니고 탈출 도전 중이 아니다.
- 적어도 한쪽이 상대가 모르는 바닥·벽면·활성 출구 발견을 가지고 있다.

참가자마다 세션 슬롯은 하나다. 요청하면 `xch-N` 세션이 열리고 기한은 `tick + exchangeExpiryTicks`다. 요청 단계에서는 지식이 옮겨지지 않고 흔적도 생기지 않는다. 받은 사람이 기한 전에 수락하면 두 기억의 합집합을 각자 독립된 사본으로 가진다. 출구는 아직 활성인 것만 합친다. 실제로 지식이 늘어난 쪽만 `mapVersion`이 1 오르고, 각자 자기 새 버전이 담긴 `EXCHANGE_COMPLETED`를 받는다.

세션 정리는 명령 처리 뒤에 돈다. 끝난 세션은 양쪽 슬롯을 함께 비우고, 두 당사자에게만 `EXCHANGE_CANCELED`를 보낸다. 정리 단계의 사유 판정 순서는 다음과 같다.

| 순서 | 사유          | 조건                                    |
| ---: | ------------- | --------------------------------------- |
|    1 | `EXPIRED`     | `tick ≥ expiresAtTick`                  |
|    2 | `NOT_ALLOWED` | 당사자가 명단에 없음, 도망자가 아님     |
|    3 | `NOT_ACTIVE`  | 한쪽이 개인 종료                        |
|    4 | `NOT_ALLOWED` | 거리 이탈, 한쪽 구속, 한쪽 탈출 도전 중 |

정리 단계 밖에서 세션이 끝나는 경우는 따로다. `EXCHANGE_CANCEL`과 한쪽의 `EXIT_START`는 즉시 세션을 끝내고 두 당사자에게 `EXCHANGE_CANCELED`(`CANCELED`)를 보낸다. 새 정보가 없는 수락(`EXCHANGE_ACCEPT`가 `NOT_ALLOWED`로 거절)도 세션을 닫고 두 당사자에게 `EXCHANGE_CANCELED`(`NOT_ALLOWED`)를 보낸다. 수락한 사람은 거절 결과도 함께 받는다(S15P21C204-380).

수락한 틱의 두 사람 셀의 중점(인접이면 반 칸 좌표)이 `mk-xch-N` 흔적으로 예약된다. 흔적은 20틱 뒤 활성 술래 전원에게 `HUNTER_MARKER`로 공개되고, 공개 뒤 40틱(발생 뒤 60틱)에 만료된다. 공개 틱에 활성 술래가 없으면 흔적은 보내지지 않고 사라진다. 이미 노출 창이 지난 흔적도 보내지 않는다. 같은 표식 ID는 두 번 예약되지 않는다.

접근 셀에 들어가는 것만으로는 아무것도 잠기지 않는다. 도전은 `EXIT_START`로만 열린다. 조건은 다음과 같다: 활성 도망자가 자기 활성 출구의 접근 셀에 서서 그 벽을 정면으로 보고 있음, 동작 없음, 구속 아님, 다른 도전 없음, `nextAttemptTick` 이후. 도전 `ch-N`에는 `minSuccessTick = tick + 40`, `expiresAtTick = tick + 160`, 자세 종류가 담긴다. 자세 종류는 도전이 시작될 때 본인에게만 알려진다.

도전 중에는 이동·회전·교환 요청이 막히고, 대기 턴·유지 이동도 시작 때 지워진 뒤 재개되지 않으며, `PLACE_PLAYER`도 도전자를 옮기지 않는다. 그래서 도전 중인 도망자의 셀·방향은 바뀌지 않는다. `stepMatch`에서 도전이 끝나는 경로는 다음 넷뿐이다.

| 끝나는 경로                           | 결과·사유                                       | 재시도 제한     |
| ------------------------------------- | ----------------------------------------------- | --------------- |
| 명령 처리 전 도전 정리에서 160틱 만료 | `EXIT_CHALLENGE_ENDED`(`failed`/`EXPIRED`)      | `tick + 10`     |
| `EXIT_CANCEL`                         | `EXIT_CHALLENGE_ENDED`(`canceled`/`CANCELED`)   | `tick + 10`     |

도전 정리 단계에는 만료 뒤에 개인 종료(`canceled`/`NOT_ACTIVE`), 구속·출구 상실·자세 불일치(`canceled`/`NOT_ALLOWED`)를 판정해 재시도 제한을 거는 분기도 있다. 이 분기는 방어 코드이고 `stepMatch`에서 도달 불가다. 개인 종료는 도전을 먼저 지우고, 출구는 소유자가 종료될 때만 닫히며, 자세는 위 이유로 바뀌지 않고, 함정 구속은 도전자에게 일어나지 않는다(7절). 팀 결과나 중단으로 경기가 끝나면 진행 중이던 도전 기록은 이벤트 없이 그대로 남는다. 재시도해도 자세 종류는 다시 뽑지 않는다.

`EXIT_PROGRESS`는 순서대로 확인한다: `method`가 `pose|keys`이고 `completed`가 불리언인지, 본인의 진행 중 도전 ID인지, `minSuccessTick` 이후인지, 활성 도망자인지, 소유 출구가 활성인지, 여전히 접근 셀에서 벽을 보고 있는지. `completed: false`는 도전을 그대로 두고, `completed: true`는 개인 `ESCAPED`를 확정한다. 이 중 만료(`EXPIRED`)·비활성(`NOT_ACTIVE`)·출구·자세(`NOT_ALLOWED`) 확인은 방어 코드이고 `stepMatch`에서 도달 불가다. 만료 틱의 보고는 도전 정리가 먼저 지워 `STALE_REQUEST`가 되고, 종료한 행위자는 공통 검사에서 `NOT_ACTIVE`가 되며, 출구·자세는 도전 중 바뀌지 않는다. 두 방법에 같은 조건을 적용하며, 몸 자세나 카메라 영상이 진짜인지는 코어가 확인하지 않는다.

### 통로 그래프와 연결성

통로 그래프의 노드는 통로 셀(`y*width+x`)이고, 간선은 직교로 이웃한 통로끼리 잇는다. BFS 거리는 이동 횟수(간선 수)라서 인접 두 셀의 거리는 1이고, 경로가 없으면 `-1`이다. Tarjan 방식으로 이중 연결 성분과 단절점을 구하고, 가장 큰 성분을 핵심부로 삼는다. 막다른 가지는 단절점 뒤의 작은 성분이 되어 핵심부 밖으로 빠진다.

`validateConnectivity`는 다음 오류를 낸다: `DISCONNECTED`(통로가 한 덩어리가 아님), `NO_CORE`, `SPAWN_NEIGHBORS`, `SPAWN_NOT_CORE`, `EXIT_APPROACH_NOT_CORE`. 인증 맵 시험·맵 생성 스크립트와 함께, 서버 맵 로더도 경기에 쓸 변형마다 이 검사를 먼저 한다(`minSpawnNeighbors`는 튜닝 값). 실패하면 준비가 `LOADER_FAILED`(`connectivity:<첫 오류>`)로 끝난다(S15P21C204-383).

### 온라인 배치 선택

선택기는 명단을 역할별 기본 문자열 순서로 정렬하고, 정확히 술래 3명·도망자 3명과 고유 ID를 요구한다. 난수는 uint32 시드의 mulberry32이고, 섞기는 Fisher-Yates, `layoutId`는 `<topologyVersion>:<fnv1a(자리·출구 JSON)>`이다. 한 번의 시도는 다음 순서로 진행한다.

1. 술래 영역 3개를 섞어 술래에게 하나씩 준다. 도망자 시작 영역 3개도 섞어 도망자에게 하나씩 준다. 영역마다 유효 시작 후보 중 하나를 고른다. 유효 시작 후보의 조건은 통로 이웃 `minSpawnNeighbors` 이상, 핵심부 안, 앞이 통로인 방향이 하나 이상이다.
2. 도망자 간 거리와 도망자·술래 간 거리가 하한 이상인지 확인한다.
3. 도망자마다 핵심부 안에 있고 경로 길이가 `minExitPathLength`–`maxExitPathLength`(JSON 18–45, 한 변 31 미만 맵은 아래 규칙으로 축소)인 출구 후보를 섞어 최대 12개(`EXIT_CANDIDATES_PER_RUNNER`)를 남긴다.

## 11. 연결 상실, 중단, 이벤트

`CONNECTION_LOST`는 명단에 있는 참가자의 `connected`만 끈다. 그 뒤의 처리는 다음과 같다.

- 참가자가 이미 개인 종료했거나 경기가 끝났으면 그것으로 끝이다.
- 연습이면 연습을 계속하고 `RETIRE_PLAYER`(`connection-lost`)를 낸다.
- 경기(`GAME_LOADING` 또는 `PLAYING`)면 `ABORTED`/`GAME_CONNECTION_LOST`로 중단한다. 도망자와 술래 모두 해당한다.

`ABORT_MATCH`는 종료하지 않은 상태라면 경기·연습 모두 `ABORTED`로 만든다. 중단 사유는 `GAME_CONNECTION_LOST`, `SERVER_TICK_OVERLOAD`, `MEDIA_POLICY_UNCERTAIN`, `MEDIA_UNAVAILABLE` 네 가지다. 중단은 `RETIRE_INSTANCE`(`aborted`), 팀 결과는 `RETIRE_INSTANCE`(`round-ended`), 개인 종료는 `RETIRE_PLAYER`(`personal-ended`)를 낸다.

도메인 이벤트 ID는 `matchId/gameInstanceId/tick/seq`이고 `seq`는 경기 전체에서 증가한다.

## 12. 주요 흐름

1. 서버가 튜닝 JSON을 `validateTuning`으로 검증한다. 맵 원본의 해시를 구해 `validateTemplate`과 `createTemplateVariants`를 돌리고, `seed % 변형 수`로 변형을 고른다.
2. 서버가 폴백을 인증하고 `selectWithFallback`을 예산 안에서 진행한다. 온라인 배치가 나오면 쓰고, 아니면 인증된 폴백을 쓰며, 둘 다 없으면 `LAYOUT_UNAVAILABLE`이다.
3. `createMatch`가 명단·배치·출구·초기 지식을 고정한다. `START_PLAYING`이 오면 `PLAYING`이 되고 `startTick + 3600` 마감이 잡힌다(`deadline: none`이면 마감 없음).
4. 틱마다 서버가 인증된 명령과 제어를 넣는다. 코어는 5절 순서로 동작·포획·장비·도전·명령·교환·흔적·결과를 처리하고 결과·이벤트·회수 의도를 돌려준다.
5. 서버 `PlayerProjection`이 개인 상태, 가시 표면·대상, 기억 지도를 따로 읽는다. 개인 종료나 팀 종료 뒤에 같은 입력이 와도 다시 적용되지 않는다.
6. 연습은 `preparePracticeLayout`과 `createPractice`로 별도 인스턴스를 만든다. `TEAM_PRACTICE`에서 바로 명령을 받고 포획·잡기·함정 발동·팀 결과·제한시간은 없다.

## 15. 확인된 한계와 코드 쪽 발견

- 제품 서버는 2:2 쇼케이스 배치를 3:3 선택 뒤 빈 자리를 떼어 만든다. 코어의 `sortRoster`와 폴백 슬롯 결합은 3:3만 받으므로 2:2를 선택기에 직접 넣으면 거절된다.
- 튜닝 파일명은 `mvp-v1.json`인데 내부 `tuningVersion`은 `mvp-v2`다. 서버 기본 경로도 `mvp-v1.json`이다. 의도는 코드로 판단할 수 없다.
- 탈출 도전 주변에는 `stepMatch`에서 도달할 수 없는 방어 코드가 있다. 도전은 동작이 없을 때만 시작되고 보류 입력을 지운다. 도전 중에는 이동·회전 명령이 거절되고, 대기 동작 재개와 `PLACE_PLAYER`도 도전자를 건너뛴다. 그래서 도전자의 셀·방향은 바뀌지 않고, 완료된 이동이 없으니 함정 후보도 되지 않는다. 출구는 소유자가 개인 종료할 때만 닫히는데, 그때 도전은 이미 지워진다. 도달 불가 분기는 다음과 같다.

  | 위치                                           | 도달 불가 분기                                                                     | 실제로 먼저 걸리는 곳                                           |
  | ---------------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------- |
  | 도전 정리(`advanceChallenges`)                 | 개인 종료 `NOT_ACTIVE`, 구속·출구 상실·자세 불일치 `NOT_ALLOWED`(재시도 제한 포함) | 개인 종료는 도전을 먼저 지움. 나머지 조건은 도전 중 생기지 않음 |
  | 함정 발동의 도전 종료(`lockRestrainedActions`) | `EXIT_CHALLENGE_ENDED`(`canceled`/`NOT_ALLOWED`), 재시도 제한 없음                 | 도전자는 함정 후보가 되지 않음                                  |
  | 탈출 보고(`verifyProgress`)                    | `EXPIRED`, `NOT_ACTIVE`, 출구·자세 `NOT_ALLOWED`                                   | 도전 정리 → `STALE_REQUEST`, 공통 검사 → `NOT_ACTIVE`           |
  | 도전 취소(`cancelChallenge`)                   | 행위자 없음 `NOT_ALLOWED`                                                          | 공통 검사 → `NOT_ALLOWED`                                       |

  이 분기들을 고정하는 시험은 `place()`·`patch()`로 상태를 직접 주입해 조건을 만든다. 따라서 도전 종료 경로 중 재시도 제한이 걸리는 것은 실제로 만료와 `EXIT_CANCEL` 둘뿐이다.

- 팀 결과 사유 이름 `two-escaped`/`two-captured`는 3인 기준이지만 뜻은 과반이라 도망자가 1~2명이어도 같은 이름을 쓴다. 공개 계약이라 이름은 두고, 웹 문구가 실제 수를 쓴다(S15P21C204-380).
- `match/index.ts`는 제품 API와 함께 진단 스텁을 공개한다. `checkCapture`·`checkWinCondition`은 값을 계산하지 않고, `tryMove`는 벽도 보지 않는다. 이 스텁은 제품 프로필 없이 뜨는 `TeamRoom`이 여전히 호출한다. 호출자는 `DevKkakkungRoom`이다.
- 탈출 완료의 진정성은 코어가 확인하지 않는다. 코어는 보고된 `completed`와 시간·상태·위치 조건만 검사한다.
