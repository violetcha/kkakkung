## 통합 검증 방식

별도 프로세스의 실제 A 게임 코어·맵, B 인증 HTTP·Colyseus·Room, C 제품 런타임 6개와 E 운영/회수/예산을 연결했다. D 장치와 Cloud 전송은 합성이며 경기의 실제 3,600틱을 로컬에서 가속한다.

첫 경기 결과 → 역할 교환 재경기 결과 → 같은 팀 재경기 결과 → 1명 교체 후 경기 결과 → ACTIVE 방장의 게임 소켓 종료로 ABORTED → 새 방장의 로비 복귀·인원 보충 → 다음 경기 결과를 확인한다. 중간 미디어 전용 장애에서는 논리 게임 참가 유지와 새 Identity/세대를 확인한다. 결과마다 원격 합성 참가자 0과 마지막 READY·미해결 회수 0을 확인한다.

연속 시험은 기존 합성 예산에서 BUDGET_EXHAUSTED로 차단되어, 로컬 자료만 5판과 중단 경기의 누적 예약을 감당하도록 조정했다. 제품의 40% public bucket·공식 대조 전 예약 유지·실제 운영 잔량은 변경하지 않았다.

기존 운영 시험의 60ms 제한이 준비 단계의 디스크 기록까지 포함해 간헐적으로 실패하므로, 해당 시간 초과 사례는 주입 시계로 제한 경과를 재현하도록 수정했다. 실제 운영 제한 시간은 변경하지 않았다.

정상 팀 6명·1방 내부 시험 예외와 SSO·초대·기본 차단·바인딩·회수·예산 정책을 유지한다. MP-06·EQ-06·EQ-07·EQ-08·EQ-09·EQ-12는 PRODUCT_DECISION_PENDING이다. 코드 완료·MR 병합·Jira 상태·배포 완료를 각각 확인한다.

따라서 !107~!110은 develop 병합 완료지만 현재 서비스에는 미반영이다. 배포 재시도 전에 운영자가 실제 Cloud 잔량·기간/version과 namespace 확인 근거를 재검증하여 공식 사용량, 연결된 runtime evidence의 digest·만료, DP-06 계획을 함께 갱신해야 한다. 이후 product-release의 check-only, 정상 제품 배포·복구·smoke와 실행 revision을 다시 확인한다. 날짜만 바꾸거나 수치를 복사해 유효한 증거로 만들지 않는다.

이번 확인에서는 운영 자료·권한·컨테이너를 변경하거나 Cloud 시험·재배포를 실행하지 않았다. 코드 CI 실패로 인한 차단과 운영 자료 만료로 인한 배포 차단을 구분해 기록한다.

최종 MR !111의 첫 원격 검사(kkakkung-mr #81, cfd70d6)는 별도 코드 문제로 실패했다. 확대된 연속 경기 시험의 다섯 번째 GAME_LOADING에서 SERVER_TICK_OVERLOAD로 중단되었다. 286ms 이벤트 루프 구간 중 CPU 사용이 282ms, GC가 약 2ms였으므로 단순 시험 대기 시간 초과로 처리하지 않았다.

같은 경로의 CPU 프로파일에서 `MediaCoordinator.durablyRevoked`가 종료된 세대마다 `OperationJournal.snapshot()`으로 전체 기록을 복사하는 것을 확인했다. 조회만 하는 회수 증거 검사와 운영 상태 검사에 기존 불변 `readSnapshot()`을 사용하도록 수정했다. 새 기록·압축 완료 시 조회 자료는 갱신되며, 쓰기 가능 여부와 예산 유효기간은 계속 현재 상태로 검사한다. 디스크 동기화 대기·실패·압축 시 관찰과 이전 경기의 영구 REVOKED 기록 전 신규 발급 거절을 회귀로 확인한다. 서버의 250ms 과부하 보호, 경기 횟수와 각 단계의 전환·정리 대기 제한은 유지한다.

이 추가 수정의 발급·회수·운영 집중 회귀 70건과 전체 `pnpm verify` 225파일 2,209건·브라우저 6건이 통과했다. 전체 검사에서는 같은 연속 경기 경로의 CPU 프로파일도 다시 수집했다. 이 기록은 로컬 검사이며 후속 원격 Jenkins 결과와 배포 완료는 별도로 확인한다.

후속 원격 검사 #82(4f96ffc)는 개별 단계 오류가 아니라 전체 시험의 기존 120초 한도에 도달했다. 실제 카운트다운을 포함해 순차 실행하는 5판 완주·1판 중단 시나리오에 전체 예산 180초를 적용한다. 각 단계의 15초 전환 대기, 8초 참가자 정리 확인, 서버의 250ms 과부하 판정은 변경하지 않는다. 한도 확대만으로 성공 처리하지 않고 마지막 RESULT·참가자 0·READY까지 확인하는 동일 검사를 다시 수행했으며 로컬에서 통과했다(전체 명령 75.85초).
