## 1. 제품 목표와 대상

### 1.1 한 문장 소개

까꿍은 웹캠의 얼굴·상체 동작으로 좁은 시야의 미로를 이동하며, 도망자 3명과 술래 3명이 3분 동안 탈출과 포획을 겨루는 웹 멀티플레이 숨바꼭질 게임이다.

### 1.2 핵심 경험

- **몸으로 조작한다:** 몸을 앞뒤로 기울여 이동하고 고개를 돌려 방향을 바꾼다. 키보드 보조 입력과 모드 전환을 제공한다.
- **상대가 가까워졌음을 느낀다:** 가공된 실제 얼굴, 근거리 음성, 발소리와 장비 소리로 사람의 존재를 전달한다.
- **불완전한 정보를 함께 사용한다:** 개인 지도와 역할별 지식이 다르고, 도망자끼리 지도를 교환하면 정보를 얻는 대신 술래에게 과거 흔적이 남는다.
- **짧은 경기 안에 역할별 목표를 수행한다:** 도망자는 자기 출구를 찾아 도전하고, 술래는 감지기·덫·추격으로 이를 막는다.

렌더링의 미술 완성도, 조작의 쾌적함, 실제 공포감과 재경기 의향은 아직 최종 인수를 거치지 않았다. 위 문장은 제품이 전달하려는 경험이며 현재 만족도 측정 결과가 아니다.

## 2. 문서 기준과 상태 구분

### 2.1 충돌을 처리하는 기준

1. 사용자의 최신 명시 결정과 [decisions.md](decisions.md)가 제품 승인 범위를 정한다.
2. 이 문서는 승인된 규칙과 현행 구현을 종합한다. **후속 제안은 승인 전까지 현재 규칙을 바꾸지 않는다.**
3. [requirements.md](../../requirements.md)는 기능별 구현·검증 상태, [protocol.md](../protocol.md)와 [실행 공통 원본](../execution/common.md)은 개발 연결 계약을 관리한다.
4. 구현이 확정 요구와 다르면 차이를 결함·미완료로 기록한다. 코드에 있다는 이유만으로 의도된 제품 규칙으로 정당화하지 않는다.
5. 원본 기획서, 기존 122개 작업 계획, 날짜별 인계·시험 기록은 당시 이력이다. 오래된 미구현·실패 문장을 현재 상태로 그대로 가져오지 않는다.

### 2.2 상태 용어

| 표기        | 의미                                                                 |
| ----------- | -------------------------------------------------------------------- |
| 확정 요구   | 사용자 결정 또는 유지되는 원본 범위의 제품 요구                      |
| 구현        | 기준 SHA에 실행 경로가 있음. 실제 장치·Cloud·사용성 인수 완료와 다름 |
| 검증 확인   | 특정 SHA·환경·시점의 실제 시험이나 운영 확인이 있음                  |
| 알려진 결함 | 현재 동작이 의도한 요구·자원 한계·오류 안내를 충족하지 못함          |
| 검증 대기   | 구현이나 도구는 있으나 요구 환경의 결과가 없음                       |
| 제안        | 다음 개발 방향. 승인된 현재 규칙으로 적용하지 않음                   |
| 결정 대기   | 선택이 필요한 제품 범위·운영 정책. 결정 전 임의 구현·완료 처리 금지  |

후속 과제 R01–R12와 결정 Q01–Q11은 **이 문서의 관리 번호**다. 기존 AC/RL/MP/EQ 등의 추적 ID와 실제 Jira 키를 대체하지 않는다.

## 3. 현재 제공 범위

### 3.1 제품 경로에 연결된 기능

| 영역        | 현재 구현                                                                 | 남은 인수 또는 제한                                       |
| ----------- | ------------------------------------------------------------------------- | --------------------------------------------------------- |

| 규칙        | 이동·회전·포획·장비·구속·출구 도전·3분 승패                               | 실제 사람 플레이의 밸런스·조작 품질 미검증                |

| 경기 이후   | 개인 결과, 전체 결과, 방장 위임, 같은 팀/역할 교환/로비 재경기            | 결과 설명·대기 상태·연결 단절 경험 보완                   |
| 운영        | Jenkins 검사·제품 배포, 상시 운영, 영속 기록·회수·부팅 복구               | 공개 배포 격리·장애 알림·용량·복원 인수 필요              |

### 3.2 현재 제공하지 않는 기능

진행 중 중도 참가·인원 충원, 자유 관전·생존자의 비공개 화면 관전, 게임 소켓 재접속 복구, 개인 전적·랭킹·친구 시스템, 자동 매칭, AI 봇, 리플레이·녹화, 사용자 제작 맵 저장, 완전 절차 생성 맵, 모바일 최적화, 다중 게임 서버 확장은 현재 제품 제공 범위가 아니다. GitLab 접근 인증이 있다는 사실을 게임 계정·전적 시스템 구현으로 해석하지 않는다.

대시·자동 가속·좌우 평행 이동은 현 조작 규칙에 없다. 현재 A/D는 방향 회전이다.

### 3.3 도망자 아이템

MP-06·EQ-06·EQ-07·EQ-08·EQ-09·EQ-12는 **PRODUCT_DECISION_PENDING**이다. 종류·효과·수량·배치·획득·소지·사용 방법을 임의로 채우지 않는다. 원본의 미끼·해제 도구를 현재 제공 기능으로 소개하지 않는다. 이는 영구 제외 결정도 아니다. 술래 감지기·덫, 구속·자연 해제·면역·포획·탈출 포즈는 확정 범위에 남는다.

## 4. 사용자 흐름과 화면

### 4.1 현재 서비스 진입

서비스 메인 주소 → GitLab 프로젝트 멤버 확인 → 닉네임 입력 → 방 생성 또는 6자리 코드 참가 → 6인 로비로 진행한다. 현재 팀원은 별도 운영 초대 링크를 매번 발급받지 않는다.

방 코드는 방 식별자다. 기본 invitation 모드에서는 코드만 알아도 인증되는 것이 아니며 유효한 초대가 함께 필요하다. 세션 발급 후 첫 게임 연결 예약은 60초다. 연결 실패·사용자 취소·미접속 만료 시 소유 예약을 반환한다.

## 5. 경기 규칙과 시간

### 5.1 인원과 승패

- 도망자 3명, 술래 3명으로 시작한다. 최초 역할은 서버가 섞어 배정하며 재경기 역할 계획은 서버가 적용한다.
- 도망자 2명이 탈출하면 도망자 팀이 즉시 승리한다.
- 도망자 2명이 포획되면 술래 팀이 즉시 승리한다.
- 180초 종료 시 탈출자가 2명 미만이면 술래 팀이 승리한다.
- 도망자의 ACTIVE → ESCAPED 또는 CAPTURED는 배타적이며 결과·누계를 한 번만 확정한다. 승패 이후 새 행동·판정을 만들지 않는다.

### 5.2 시간과 행동

| 항목             | 현재 구현값                                                                                           |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| 서버 권위 시간   | 50ms Tick, 초당 20회                                                                                  |
| 경기 길이        | 3,600Tick = 180초                                                                                     |
| 한 칸 전진·후진  | 9Tick = 450ms                                                                                         |
| 좌우 90도 회전   | 6Tick = 300ms                                                                                         |
| 이동 의도 유지   | 클라이언트 100ms 간격 갱신, 서버 TTL 500ms                                                            |
| 행동 버퍼        | 대기 회전 1개. 긴 입력 큐를 쌓지 않음                                                                 |
| 서버 과부하 보호 | 한 번의 스케줄 실행에서 catch-up 최대 4회. 다음 Tick 예정 시각보다 250ms 넘게 늦어지면 경기 무효 정책 |

이동과 회전은 동시에 실행되지 않는다. 진행 중 행동을 끝낸 뒤 대기 회전을 우선 처리하고 유지 이동이 있으면 다음 한 칸을 시작한다. 키를 놓아도 이미 시작한 한 칸 이동은 완료한다. 벽·격자 밖은 이동할 수 없으며 아군의 같은 칸 점유는 이동을 막지 않는다.

논리 칸·방향은 행동 종료 Tick에 확정하고 중간 화면은 보간한다. 서버 시계와 판정을 브라우저 타이머·로컬 위치로 대체하지 않는다. 입력 인식에 필요한 유지 시간과 서버 행동 시간은 서로 다르다.

### 5.3 포획

이동 완료 후 술래와 도망자가 같은 칸에 있거나, 같은 Tick에 서로의 칸을 맞바꿔 지나가면 포획한다. 옆 칸·대각선·벽 너머 포획은 없다. 같은 Tick에서 포획은 장비 발동·출구 완료 명령보다 먼저 확정한다. 구속 면역은 포획 면역이 아니다.

E는 들어온 지도 교환 수락 → 유효한 자기 출구 도전 → 선택 대상에게 지도 교환 요청 순으로 현재 문맥을 해석한다. 입력창·IME 조합 중에는 게임 단축키를 만들지 않는다. 숨긴 탭·개인 종료·권위 상실·모드 변경 시 유지 입력을 정리한다. 도망자의 F/V 아이템 행동은 미정이며 현재 제공하지 않는다.

### 6.2 최초 장치 준비

카메라·vision·calibration·audioPlayback이 모두 ready여야 한다. 마이크는 기본 꺼짐이며 선택적으로 켠다. 초기 카메라 필수와 경기 중 카메라 장애의 키보드 폴백은 다른 조건이다.

- 카메라 요청은 640×480 ideal, 최대 30fps이며 실제 획득 해상도를 보장하지 않는다.
- 정면 얼굴과 양쪽 어깨·팔꿈치·손목이 보여야 한다. 골반·다리는 필수 관절이 아니다.
- vision ready는 모델 로드만 의미하지 않는다. 현재 유효 얼굴·첫 안전 가공 프레임·살아 있는 가공 트랙을 요구한다.
- 보정은 모델 준비 이후 새 표본 8개를 2초 창에서 수집한다. yaw/lean 산포 한계와 중앙값으로 중립을 계산한다.
- 오디오 준비는 실제 출력과 같은 AudioContext를 사용자 동작으로 재개하여 running인지 확인한다. 시험음·마이크 레벨·마스터 음량 UI는 아직 없다.

## 7. 맵·시야·개인 지도

### 7.1 논리 맵

현재 master-v1은 32×32 격자다. 서버가 검증된 고정 맵의 변형·시작점·출구 조합을 선택하고 실패 시 검증된 fallback 경로를 사용한다. 전체 맵·출구 배치·seed·튜닝을 브라우저에 보내지 않는다. 연습 맵과 본경기 맵은 분리되며 연습의 탐색·설치·좌표는 본경기에 이월하지 않는다.

### 7.2 정보 비대칭

- 서버 시야는 수평 80도이며 셀 단위 거리 상한은 3.5다. 원본의 “전방 3셀”을 코드의 정확한 절단값으로 설명하지 않는다.
- 벽 차폐·벽 뒷면을 고려하며 실제 관찰한 바닥·벽면을 개인 지도에 누적한다.
- 도망자는 자기 칸, 술래는 자기 담당 구역의 바닥·접한 벽면에서 초기 지식을 갖고 첫 실제 시야를 더한다. 술래도 전체 맵을 받지 않는다.
- 현재 보이는 참가자·장비와 과거에 탐색한 지도는 구분한다. 시야 밖 참가자의 현재 좌표를 지도에 계속 표시하지 않는다.
- 출구는 정확한 벽면을 실제 관찰한 도망자만 발견한다. 접근 칸만 보인다고 발견되는 것이 아니다.
- 술래에게 출구 존재·위치 목록을 보내지 않는다. 발견한 도망자는 소유자를 알 수 있지만 도전 포즈는 자기 도전 시작 시에 공개된다.
- 3D 포털은 현재 관찰 중인 출구 벽면에만 표현한다. 개인 종료로 닫힌 출구는 지도에서도 닫힌 것으로 반영한다.

### 7.3 렌더링 개선 범위

현재 단일 R3F Canvas와 서버의 개인 뷰를 연결한 맵·플레이어·출구·장비 표현 경로가 있다. **현재 시각 품질을 최종 승인하지 않았으며 맵 렌더링 개선은 남은 작업이다.**

최종 공간 콘셉트, 조명·재질·대비, 얼굴 가독성, 출구/장비 시각 언어, HUD와 공포 연출의 방향은 Q11에서 정한다. 개선 시 논리 벽 방향·충돌·가시성·출구 은폐를 유지해야 한다. 화면을 풍부하게 하려고 서버 비공개 맵을 클라이언트로 옮기지 않는다. 이번 문서 작성은 렌더링 실행·미술 인수 기록이 아니다.

## 8. 지도 교환

지도 교환은 **ACTIVE 도망자끼리** 한다. 같은 칸 또는 상하좌우로 인접한 통로 칸이어야 하며 대각선은 허용하지 않는다. 서로 아는 지형·열린 출구 정보가 완전히 같으면 교환하지 않는다.

1. 요청자가 화면의 가시 아군 후보에게 요청한다. 서버는 역할·거리·상태·새 정보 조건을 별도로 검사한다.
2. 수신자가 2초 안에 수락한다. 각 참가자는 한 교환 세션만 가질 수 있다.
3. 성공 시 그 순간의 탐색 지형과 발견한 활성 출구 정보를 합친다. 이후의 이동·발견을 계속 실시간 공유하는 기능은 아니다.
4. 구속·출구 도전·개인 종료·범위 이탈·취소·시간 만료로 교환을 끝낸다.
5. 성공 지점의 두 사람 좌표 중간점이 1초 뒤 ACTIVE 술래에게 2초간 과거 흔적으로 보인다. 신원·현재 이동을 추적하지 않는다.

현재 UI의 “아군 교환” 안내는 코어의 도망자 전용 조건보다 넓게 읽힐 수 있다. 튜토리얼·도움말은 실제 역할 조건을 설명해야 한다. 서버가 상호 시선까지 검사하는 것으로 새 조건을 덧붙이지 않는다.

근거: [교환 세션](../../packages/game-core/src/match/exchange/session.ts), [지식 병합](../../packages/game-core/src/match/exchange/merge.ts), [흔적](../../packages/game-core/src/match/exchange/trace.ts).

## 9. 술래 장비와 구속

### 9.1 설치

술래는 경기마다 감지기 1개와 덫 1개를 가진다. 정지 상태에서 감지기는 자기 칸 앞 내부 벽면, 덫은 자기 통로 칸에 설치한다.

모든 참가자의 시작 칸, 외곽 벽, 기존 장비·설치 예약이 있는 칸 등 금지 조건을 검사한다. 출구 존재를 설치 허용/거절로 유출하지 않는다. 설치에 0.5초가 걸리고 설치 완료 후 1초가 지나야 무장된다. 완료 전에 이동·회전·개인 종료·명시 취소가 발생하면 재고를 쓰지 않는다. 설치 완료 시 재고를 1개 소비한다.

### 9.2 발동과 흔적

| 장비   | 발동                                                           | 결과                                               |
| ------ | -------------------------------------------------------------- | -------------------------------------------------- |
| 감지기 | 무장 후 ACTIVE 도망자가 접근 칸에 새로 진입한 이동 완료        | 단발 작동, 위치 흔적과 소리. 구속 면역도 감지 가능 |
| 덫     | 무장 후 구속·재구속 면역이 없는 ACTIVE 도망자가 칸에 새로 진입 | 후보 중 정확히 한 명을 선택해 1.5초 구속           |

무장 시 이미 서 있거나 면역이 정지 중 끝났다는 이유만으로 새 진입을 만들지 않는다. 덫에 동시에 들어온 유효 후보가 여러 명이면 경기별 기본 순서를 Tick마다 순환하는 공통 우선순위로 한 명을 고른다.

장비는 한 번 작동하면 소모된다. 발동 위치는 즉시 ACTIVE 술래에게 2초간 과거 흔적으로 전달하고 효과음 사건을 발생시킨다. 감지된 도망자의 신원이나 이후 현재 좌표는 붙이지 않는다.

### 9.3 구속

구속은 새 이동·지도 교환·출구 도전을 막고 진행 중 출구 도전을 종료한다. **구속 중 회전은 가능하다.** 1.5초 후 자연 해제되며 이후 2초간 재구속 면역을 갖는다. 감지기·포획에 대한 면역은 아니다. 해제 아이템은 현재 미정이다.

근거: [설치](../../packages/game-core/src/match/equipment/install.ts), [감지기](../../packages/game-core/src/match/equipment/sensor.ts), [덫](../../packages/game-core/src/match/equipment/trap-activate.ts), [구속](../../packages/game-core/src/match/equipment/restraint.ts).

## 10. 개인 출구와 탈출

도망자는 자기 전용 출구 하나를 가진다. 접근 칸에 서서 정확한 벽 방향을 바라보고, 진행 중 행동·구속·재시도 대기가 없을 때 버튼/E로 도전을 시작한다. 출구 앞에 도착한 것만으로 자동 시작하거나 이동을 잠그지 않는다.

- 포즈는 내 왼팔 들기, 내 오른팔 들기, 양팔 Y자 중 하나다. 같은 출구 도전의 재시도에서 포즈가 다시 무작위로 바뀌지 않는다.
- 모션 모드에서는 유효한 얼굴·상체 표본으로 지정 자세 1.2초 유지를 확인한다.
- 키보드 모드에서는 challengeId로 고정된 방향키 4개 순서를 제시한다. 오입력은 처음부터 다시 하며 자동 반복은 인정하지 않는다.
- 두 방식 모두 서버 기준 시작 후 최소 2초, 8초 미만에서만 성공한다. 실패·취소 후 0.5초 재시도 대기가 있다.
- 도전 중 이동·회전·지도 교환을 잠그며 취소는 가능하다. 도전 중에도 포획될 수 있다.
- 성공·포획 후 개인 출구는 닫히고 재배정하지 않는다.

**판정 경계:** 서버는 자기 도전·위치·방향·시간·중복 완료를 검사한다. 카메라의 실제 신체 수행 1.2초나 키 입력의 진실성을 서버가 독립적으로 증명하는 구조는 아니다. 카메라는 게임 경험의 입력 장치이며 신체 인증 장치로 설명하지 않는다.

## 11. 얼굴·음성·효과음

### 11.1 실제 얼굴과 로컬 처리

정상 앱은 원본 웹캠을 로컬 미리보기·추론에 사용하고, 얼굴 윤곽을 마스킹한 실제 얼굴 픽셀을 흑백으로 만들어 게시한다. 마스크 바깥은 검정으로 채운다. 이는 익명 아바타로의 변환이 아니다.

| 항목           | 현재 구현                                                                  |
| -------------- | -------------------------------------------------------------------------- |
| 출력 Canvas    | 160×160, captureStream 10fps                                               |
| 기본 얼굴 송출 | 인코딩 상한 100kbps·10fps, simulcast off                                   |
| low 품질       | 다음 게시부터 인코딩 상한 50kbps·8fps                                      |
| low의 제한     | Canvas는 160×160·10fps 유지. 128×128 전환이나 현재 게시 즉시 재설정이 아님 |
| 안전 얼굴      | 마지막 안전 관측 기준 최대 1,200ms 유지 후 코드 생성 기본 얼굴             |
| 모델           | 얼굴 1명·자세 1명·손 2개. 고정 로컬 모델·WASM, 모델 바이트 해시 검사       |
| 추론           | Worker에서 선택된 모델을 순서대로 실행, 진행 중 프레임 하나                |

본경기는 다른 활동 참가자 최대 5명의 얼굴 트랙을 사전 수신하고 시야에 들어온 캐릭터에 표시한다. 연습은 같은 팀 인스턴스 최대 2명이다. **현재 보이지 않는 참가자의 얼굴 스트림도 기기에 먼저 도착할 수 있다.** 화면 가시성 통제가 얼굴 bytes의 수신 차단과 같은 것은 아니다.

### 11.2 근거리 음성

본경기 음성은 팀 구분 없이 근거리에서 들린다. 자기 음성·전역 음성·팀 무전·전역 텍스트 채팅은 제공하지 않는다. 연습에서는 같은 팀의 별도 인스턴스 안에서만 연결한다.

거리는 통과 가능한 통로의 최단 셀 거리이며, 같은 거리면 코너가 적은 경로를 고른다. 새로운 청취 관계는 거리 5 이하에서 허용하고 기존 허용 관계는 6까지 유지하다 6을 넘으면 해제한다. 5→6→7→6→5 이동은 허용→유지→해제→미허용→허용이다.

현재 초기 음향은 거리·코너 수에 따라 볼륨과 저역 통과 필터를 적용한다. 방향은 상대 방위각의 좌우 StereoPanner다. 전후를 구분하는 완전한 3D 공간음향이 검증됐다고 표현하지 않는다. 로딩·카운트다운·개인 종료·페이지 숨김/권위 상실 때는 실제 출력을 잠근다.

### 11.3 효과음과 제어

발소리는 한 칸 이동 완료 시 발생하며 가청 거리 4셀이다. 감지기·덫 효과음은 6셀이다. 현재 세 효과음은 코드 생성 PCM이며, 같은 서버 사건을 중복 재생하지 않는다. 회전이나 이동 중간 상태만으로 발소리를 만들지 않는다.

현재 제공 제어는 모드 전환, 재보정·장치 재점검, 자기 마이크 끄기/재시도, 품질 선택, 나가기다. 시험음·마이크 레벨·마스터 음량·상대별 음소거·신고·차단·카메라 게시 끄기는 구현 완료로 표시하지 않는다.

### 11.4 공개 권한·처리 안내

현재 publisher-permissions는 서버가 정한 허용 목록을 정상 송신 앱이 적용하는 내부 1방·6명 예외다. 정상 앱 상대의 실제 Cloud 수신·철회 시험과 변조 송신자까지 막는 공개 서버 단독 통제는 구분한다.

공개 전에는 가공 얼굴·선택 음성의 Cloud 전송, 사전 수신, 서비스의 저장/녹화 방침, 문의·퇴장·차단 경로를 실제 동작에 맞게 안내해야 한다. 서비스 녹화 기능이 없다는 사실을 상대 단말의 녹화 불가능으로 설명하지 않는다. 모델별 라이선스는 현재 pending이며 공식 조건 확인이 필요하다.

### 13.2 입장과 접근 경계

제품은 초대 또는 명시적 gitlab-sso 모드로 세션을 발급한다. SSO에서는 호스트 프록시가 인증해 덮어쓴 신원만 신뢰한다. 게임 서버 포트는 비공개, 웹 프록시는 loopback에 바인딩하며 클라이언트가 신원을 지정하지 않는다. 운영 API는 별도 운영 인증을 유지한다.

현재 운영값은 MAX_ROOMS=1, MAX_SLOTS=6, publisher-permissions다. 이 모드에서는 1방을 강제하므로 방 수 설정만 늘려 공개 부하를 받을 수 없다. 세션 활동 lease·최대 수명과 미접속 예약 60초는 다른 정책이며, 연결된 AFK·결과 방 정리에는 R03 결함이 남아 있다.

### 13.3 상시 운영

사용자가 승인한 continuous 모드는 서비스 종료 날짜·일일 증거 갱신·수동 공식 잔량 입력에 의존하지 않는다. service-operations.json의 scope·무결성, 실제 capability, 영속 저널·예약·회수·부팅 복구, 인증·방 상한·API 예산은 유지한다.

공식 월간 잔량·확인 시각은 알 수 없음을 나타내는 null이다. 이를 무한 잔량으로 해석하지 않는다. continuous는 해당 예약의 모든 미디어 세대의 실제 회수가 확인되면 예약을 반환하고, 과거 attested 모드는 공식 checkpoint 대조 조건도 유지한다. 최초 초기화 marker나 기존 기록을 지워 준비를 통과시키지 않는다.

현재 자동 월간 청구 잔량 조회와 유료 플랜 금액 상한은 없다. 공급자의 무료 할당량 소진·오류를 따르며, 공개 전 비용·정원·경보 정책은 Q09/R09에서 정한다. [LiveKit 공식 할당량](https://docs.livekit.io/deploy/admin/quotas-and-limits/)과 실제 프로젝트 설정을 함께 확인한다.

### 13.4 배포와 관측

제품 배포는 검증 SHA·이미지 확인 → SSO 격리 확인 → 기존 경기 drain → 이미지 교체 → 초기화·복구 → READY → resume/OPEN → 실제 Cloud 합성 6인 DP-06 → 시험 정리 → 최종 재검사 → last-good 기록 순서다. 실패 시 확인된 장벽으로만 롤백하며 회수 불명·손상 상태를 강제로 재개하지 않는다.

continuous DP-06은 SHA/lockfile에 묶인 1방·6명, 최대 600초 시험+60초 정리 계획을 자동 생성한다. 계획의 30분 유효기간은 해당 자동 시험에만 적용하며 서비스 일일 만료가 아니다. 다른 Cloud·실장치·부하 시험을 자동 승인하는 것도 아니다.

Jenkins는 develop을 배포 대상으로 사용하며 게임과 같은 호스트에서 빌드한다. 로그·지표·로컬 경고는 구현되어 있고 빌드 실패 알림도 있다. 런타임 외부 장애 알림, 공개 상태의 배포 격리, 호스트 외부 백업·실제 복원 인수는 별도 과제다. 현재 Trivy HIGH/CRITICAL 검출은 기록만 하고 배포를 차단하지 않는다.

## 17. 좋은 첫 경험과 평가 기준

### 17.1 목표 사용자 여정 — 제안

홈에서 6인·장치 조건 이해 → 혼자 카메라/오디오 점검 → 한 칸 이동·회전·역할 행동 연습 → 친구에게 방 링크 공유 → 준비 실패를 각자 해결 → 경기 완주 → 승패 이유 이해 → 역할을 바꿔 재경기로 이어지는 경험을 목표로 한다.

추천 첫 범위에서는 혼자 방문한 평가자도 핵심 모션을 체험할 수 있어야 한다. 이를 위해 자동 매칭·봇·랭킹이 먼저 필요한 것은 아니다. 연습에서는 안내를 읽었는지보다 실제 행동을 성공했는지 확인한다.

| ----------- | ---------------------------------------------------------------------------------------------- |

| 조작        | 중립 오입력, 의도한 전후 이동/단발 회전 성공, 보정 시도 수, 모드 전환·손 가림·카메라 각도 영향 |
| 소리        | 실제 출력 확인, 발소리/장비 소리 구분, 거리·방향 인지, 기본 음량 불편                          |
| 완주        | 장치/네트워크로 무효가 된 판, 원인·복귀 성공, 반복 경기 후 자원 증가                           |
| 협업·밸런스 | 지도 교환·장비 활용, 역할별 승률과 종료 시간, 아무 행동 없이 대기한 시간                       |
| 만족        | 무엇이 무서웠는지, 조작 때문에 억울했는지, 규칙·승패를 이해했는지, 자발적 재경기 의향          |

최초 목표 예시는 혼자 방문 후 1분 안에 체험 진입, 지원 환경에서 두 번 안에 보정 성공, 6명 입장 완료 후 5분 안에 첫 경기 시작이다. **새로 합의할 제안 목표이며 달성 실적이 아니다.** 여러 신규 그룹의 성공률·시간 분포를 측정해 조정한다.

G5의 실기기 5판은 장치·통합 검증 최소 조건이다. 그 표본만으로 재미·역할 밸런스가 검증됐다고 결론 내리지 않는다. 보정 실패·연결 중단 판은 정상 밸런스 표본과 구분한다. 평가 자료는 실제 장치 플레이와 개선 전후의 근거를 사용하며 합성 Cloud 결과를 실제 사람 영상으로 설명하지 않는다.

### 18.2 공개 전 통과 조건

기존 확정 관문과 후속 권고를 함께 정리한 검수 목록이다. Q 항목에 따른 새 정책·범위는 승인 후 적용하며 이 목록 작성만으로 제품 승인을 대신하지 않는다.

- [ ] 일반 이용자가 정의된 인증·방 참가 경로로 들어오고 운영 API·개발 도구는 보호된다.
- [ ] 변조 송신·수신 앱에서도 금지 음성·비공개 게임 정보가 노출되지 않는다.
- [ ] AFK·결과 탭의 무기한 점유와 요청 폭주가 정상 이용을 막지 않는다.
- [ ] 완료 캐시와 반복 경기 자원이 안정되며 옛 요청이 새 발급으로 바뀌지 않는다.
- [ ] 개인 장치 점검·조작 연습과 실패별 다음 행동이 제공된다.
- [ ] 실제 대표 장치 6대로 5판을 완료하고 장치·네트워크·모션·오디오 결과를 기록했다.
- [ ] 게임 연결 상실·미디어 장애·카메라 오류의 서로 다른 복구/중단 정책이 구현과 안내에 일치한다.
- [ ] 검증한 방 수만 열고 정원·할당량·점검 상태를 설명한다.
- [ ] 런타임 장애 경고가 담당자에게 도착하고 배포/롤백·운영 기록 복원을 확인했다.
- [ ] 이미지 취약점 평가·조치와 모델 권리·고지를 완료했다.
- [ ] 얼굴·음성 전송을 이해하고 참가하며 불편한 상황에서 즉시 음소거·퇴장할 수 있다.
- [ ] 신규 그룹이 목표·승패를 이해하고 렌더링·조작·협업·재경기 경험을 검수했다.

공개 미디어 관문이 미충족이면 일반 공개하지 않는다. 10방 관문만 남았을 때는 나머지 공개 조건을 만족하고 Q09에서 축소 공개 범위를 승인한 경우에 **실제로 인수한 방 수에 한해** 범위를 명시한다. 기존 G2/G6의 10방 요구를 통과·면제한 것으로 기록하지 않는다. CI 통과·MR 병합·배포 READY·G5·공개 보안·만족도는 각각 별도 상태다.

## 20. 갱신 규칙

1. 기능 변경 시 해당 현행 규칙, requirements의 상태, 관련 코드·검증 근거를 같은 변경에서 갱신한다.
2. 제품 선택을 바꾸면 decisions.md에 실제 승인 내용을 먼저 기록한다. R/Q 제안을 승인 없이 확정 요구로 승격하지 않는다.
3. 공개 계약 변경은 protocol과 EXEC-CONTRACT-3 원본·타입·fixture·생산자/소비자를 함께 갱신한다. 기획서에만 다른 wire를 만들지 않는다.
4. 배포 상태는 날짜·소스 SHA·이미지·release·시험 범위를 남긴다. 실제 기기·Cloud·부하 완료를 자동 시험 개수로 대체하지 않는다.
5. 원본 HTML/DOCX와 날짜별 실패 이력은 보존한다. 현행 문서가 과거 자료를 참조할 때 적용 범위를 명시한다.
6. 문서만 바뀌면 포맷·링크·내용 정합성과 필요한 check:execution을 확인한다. 게임 규칙을 바꾸지 않은 문서 작업 때문에 앱 전체 시험을 재실행하지 않는다.

최종 기능 범위 인수 문구는 기존 결정에 따라 **“D-2026-09-08-01 적용 확정 범위 완료”**다. 원본 v0.0.8의 미정 아이템까지 모두 완성됐다는 표현으로 바꾸지 않는다.
