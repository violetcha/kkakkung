## 1. 제품 목표와 대상

### 1.1 한 문장 소개

까꿍은 웹캠의 얼굴·상체 동작으로 좁은 시야의 미로를 이동하며, 도망자 3명과 술래 3명이 3분 동안 탈출과 포획을 겨루는 웹 멀티플레이 숨바꼭질 게임이다.

### 1.2 핵심 경험

- **몸으로 조작한다:** 몸을 앞뒤로 기울여 이동하고 고개를 돌려 방향을 바꾼다. 키보드 보조 입력과 모드 전환을 제공한다.
- **상대가 가까워졌음을 느낀다:** 가공된 실제 얼굴, 근거리 음성, 발소리와 장비 소리로 사람의 존재를 전달한다.
- **불완전한 정보를 함께 사용한다:** 개인 지도와 역할별 지식이 다르고, 도망자끼리 지도를 교환하면 정보를 얻는 대신 술래에게 과거 흔적이 남는다.
- **짧은 경기 안에 역할별 목표를 수행한다:** 도망자는 자기 출구를 찾아 도전하고, 술래는 감지기·덫·추격으로 막는다.

렌더링 완성도, 조작 쾌적함, 실제 공포감과 재경기 의향은 아직 실제 사용자 인수를 거치지 않았다.

## 4. 사용자 흐름과 화면

### 4.1 서비스 진입

**현재(팀원):** 서비스 주소 → GitLab 프로젝트 멤버 확인 → (선택) 혼자 장치 점검·조작 체험 → 닉네임 → 방 생성 또는 6자리 코드 참가 → 6인 로비.

**공개 준비(비활성):** 닉네임만으로 서버가 독립 게스트 세션을 발급한다. 게스트는 방을 만들고, 친구는 현재 방장이 만든 초대 링크로만 참가한다. 서버는 `SERVICE_AUDIENCE=public`과 `publisher-permissions` 미디어 조합으로 부팅하며(server-controlled는 거절), 게스트 6명의 초대 참가·미디어 발급·경기 진입을 제품 통합 시험으로 확인했다. 방장 초대는 현 방 전용·최대 10분이며 재발급·회수할 수 있다. 공유 URL에는 세션 토큰이 없다.

세션 발급 후 첫 게임 연결 예약은 60초다. 연결 실패·취소·미접속 만료 시 소유 예약을 반환한다. 홈 화면은 오픈소스 고지 페이지로 연결되고, 로비는 장치 사용 전 개인정보 처리 안내를 보여 준다.

홈은 시설 재질을 공유하는 장식용 긴 복도를 배경으로 사용한다. 벽 가까이에서 비스듬히
엿보는 카메라와 간헐적인 형광등 감광을 사용하며, 홈 배경에는 거리 안개가 없다.
배경은 실제 경기 맵·세션·장치를 사용하지 않는다. 끝벽 없는 80칸 복도와 먼 형광등으로
깊이를 표현한다. 첫 화면은 큰 로고와 시작하기·옵션만 표시한다. 시작하기 뒤에 입장 폼과
개인 체험을 보여 주며 초대 링크는 입장 폼으로 바로 연결한다. 옵션에서 배경 움직임을
멈출 수 있고 운영체제의 동작 줄이기를 따른다. 탭이 숨겨지면 연속 렌더링을 멈춘다.
실제 경기의 서버 시야 3.5셀과 안개는 유지한다.

| ABORTED / 무효             | 무효 사유 확인, 다시 모이기·재경기                                                                                       | 연결 상실·서버 과부하·미디어 장애 등 규정 원인. 정상 승패와 구분. 5분 기한                                         |

장치 미준비·일반 로딩 실패와 미디어 발급/회수 불명은 다른 실패다. 후자는 `MEDIA_UNAVAILABLE`로 경기를 중단한다. 실패를 준비 완료로 바꾸거나 회수 중 좌석을 즉시 재사용하지 않는다. 준비 실패는 안전한 코드(`SERVICE_NOT_READY`, `LAYOUT_UNAVAILABLE`, `DEVICE_LOADING_TIMEOUT`, `MEDIA_NOT_READY`, `PREPARATION_UNAVAILABLE`)로만 화면에 전달하고, 세부 원인은 서버 구조화 로그에 남긴다.

개인 체험은 방·좌석·미디어 grant 없이 별도 3×5 공간과 실제 입력 Runtime을 쓴다. 체험 결과·보정은 방에 넘기지 않으며 탭을 숨기면 장치·Worker·오디오를 모두 정리한다.

**관리자 데모 방(258·259·260, 사용자 비노출).** 6명을 모으지 않고 덫·포획·탈출 도전·결과 화면을 보여 주기 위한 시연 도구다. 운영 토큰으로만 열리고 홈에는 어떤 진입점도 없다. `DEMO_ROOMS`를 끄면 같은 경로가 503으로 답한다(운영은 켜 둔다). 방은 관리자 좌석 하나만 쓰고 나머지 다섯 자리는 서버가 소유한 인형이 채운다. 인형은 준비·연습·로딩 신고를 대신 마치고, 시나리오 버튼이 넣어 준 명령만 수행한다. 판정은 전부 규칙 코어가 하므로 화면·결과는 실제 경기와 같다. 미디어는 발급하지 않아 인형 얼굴은 화면에서 그린 대역 얼굴로 보이고 근거리 음성은 없으며, 관리자 화면도 그 방에서는 미디어 발급을 요청하지 않고 카메라 연결·얼굴 게시 없이 로딩을 마친다. 라운드는 규칙대로 3분이며(시간 종료 승패도 그대로 발생) 반복 시연은 결과·무효 화면의 재경기로 한다. 재경기에서도 관리자의 역할은 유지되고 인형은 준비 신고를 다시 대신한다.

시나리오는 덫·감지기(관리자가 술래면 인형 도망자가 밟아 흔적·효과음을 만든다), 술래 접근, 관리자 포획, 인형끼리 포획(누계 +1), 인형 탈출(누계 +1), 지도 교환 요청·요청 뒤 취소(관리자=도망자), 교환 흔적(관리자=술래, 인형 도망자 둘이 교환), 술래·도망자 승리 결과, 인형 연결 상실로 인한 `GAME_CONNECTION_LOST` 무효다. 목록은 경기 중 관리자 역할과 살아 있는 인형으로 성립하는 것만 보여 준다. 시나리오는 그 장면에서 끝나므로 관리자는 원하는 만큼 화면을 볼 수 있다. 관리자 본인의 출구 도전·미디어/카메라 장애·서버 과부하 무효는 이 도구의 범위 밖이다.

### 4.3 연습방과 시작 전 대기 화면

**연습방(TEAM_PRACTICE).** 장치 점검(6.3)에서 이미 읽은 것을 다시 보여 주지 않는다. 장치 단추
네 개(키보드로 조작·보정 후 모션·장치 다시 연결·마이크), 반복되는 조작 안내, 자세 안내는 이
화면에 없다. 남는 것은 작은 웹캠 미리보기, 역할별 실제 연습(도망자 포즈 연습, 술래 장비 설치),
연습 준비 완료, 그리고 카메라·추적·보정이 실제로 끊겼을 때만 뜨는 복구 배너다. 배너는 끊긴
사실과 키보드로 계속할 수 있다는 것을 알리고 그 자리에서 다시 점검하게 한다. 마이크는 선택이라
끊겨도 배너를 띄우지 않는다.

**시작 전 대기(MAP_FINALIZING·GAME_LOADING·COUNTDOWN).** 세 단계를 각각 다른 화면으로 보여 주지
않고 한 화면의 진행표시 하나로 합친다. 미로 준비 → 화면·연결 확인 → 시작 순이며 지나온 단계는
통과로 표시한다. 내 준비 대기 항목과 막힌 단계·원인·경과 시간(6.2)은 확인 단계에서 그대로
보여 주고, 카운트다운 숫자는 시작 단계에 놓는다. 준비가 제한 시간을 넘겨 실패하면 그 복귀
안내(`DEVICE_LOADING_TIMEOUT` 등)를 같은 화면 안에서 보여 주며, 그때는 "자동으로 시작합니다"
문구를 대신한다.

### 4.4 경기 화면 배치

경기 화면은 3D 가 무대 전체를 차지하고 나머지는 모두 그 위의 오버레이다. 옆 칸에 패널을 세우던
배치는 없앴다. 네 모서리의 캠코더 프레임과 왼쪽 위 `REC`·녹화 경과 시간은 화면 안쪽 안전 영역을
표시한다. 오른쪽 가운데는 캔버스 안에서 그리는 든 도구(HeldTool) 자리라 비워 둔다.

| 자리          | 내용                                                            |
| ------------- | --------------------------------------------------------------- |
| 왼쪽 위       | 캠코더 상태 — `REC`와 현재 경기 기준 녹화 경과 시간             |
| 가운데        | 십자선                                                          |
| 왼쪽 위 안쪽  | 필요한 경우에만 접히는 오버레이 — 교환·도전·장치·소리·연습·데모 |
| 아래 가운데   | 5칸 핫바 — 기존 역할 행동을 유지하고 비어 있는 칸은 잠금 처리   |
| 오른쪽 아래   | 미니맵                                                          |
| 오른쪽 가운데 | 비움(든 도구)                                                   |

핫바는 역할별 기존 행동 순서를 바꾸지 않고 항상 다섯 칸을 유지한다. 아직 기획되지 않은 도망자
아이템은 새로 만들지 않으며 남는 칸은 잠금 상태로 표시해 배치만 고정한다. 기존 상단 상태 줄과
왼쪽 아래 사건 로그는 시야를 가리지 않도록 보이는 HUD에서 제거하고, 필요한 상태 정보는 접근성
레이어와 기존 상호작용 오버레이에 남긴다. 좁은 화면(400px)에서는 핫바 칸과 미니맵을 줄이고 안전
영역 안에서 같은 상대 위치를 지킨다.

**장비 발견성(W4).** 술래가 첫 경기에서 장비를 한 번도 안 쓰고 끝나지 않게, 쓸 수 있다는 것을
화면이 먼저 알린다. 고른 칸은 테두리를 두껍게 하고 바탕과 키 표시를 올려 한눈에 잡히게 하고,
지금 서 있는 칸에 선택한 장비를 놓을 수 있으면 십자선이 커지며 성공색으로 바뀐다. 핫바 위 한 줄은
같은 것을 문구로 말하고, 막혀 있으면 이유 하나만 말한다(움직이는 중 · 설치 중 · 구속 중 · 남은
개수 없음 · 벽을 안 봄 · 이미 장비 있음). 이 판정은 내 화면이 아는 것만 보는 예고이며 최종 판정은
서버(EQ-01)가 한다. 시작 칸 금지처럼 화면이 모르는 조건은 확인하지 않는다.

장비를 한 번도 놓지 않은 술래가 실제로 놓을 수 있게 된 순간에는 한 경기 한 번만 접근성 사건
기록으로 안내한다. 화면에는 핫바 안내 줄만 남겨 왼쪽 아래 HUD를 다시 만들지 않는다. 팀 연습에서는
술래에게 아직 설치해 보지 않았음을 알려 경기 전에 한 번 놓아 보게 한다.

### 4.5 미니맵 표시

미니맵은 한 장에 세 가지를 서로 다른 **모양**으로 담아, 색을 못 가려도 구분되게 한다.

| 상태            | 그리는 법                                               |
| --------------- | ------------------------------------------------------- |
| 안 가 본 칸     | 채우지 않고 옅은 격자선만(`--color-seam`)               |
| 가 본 바닥      | 칸을 가득 채움(`--color-border`)                        |
| 벽              | 그 칸의 해당 모서리에 두꺼운 밝은 띠(`--color-text`)    |
| 내 위치         | 역할 색 삼각형 — 3D 옷 색(`role-colors.ts`)과 같은 hex  |
| 내 출구·남 출구 | 칸 테두리와 번호(`--color-success` / `--color-warning`) |

칸 크기는 항상 정수 픽셀이고 남는 여백은 반씩 나눠 가운데 둔다. 도트가 흐려지지 않게 배율도
정수로 고르고 이미지 보간을 끈다. 칸이 6px 미만으로 작아지면(경기 화면 오버레이 크기) 격자를 네
칸마다 성기게 그어 그물처럼 보이지 않게 하고, 벽 띠는 최소 2px 를 지켜 사라지지 않게 한다.

지도 교환(8장)으로 알게 된 칸은 같은 규칙으로 바닥·벽이 채워진다. 교환 전후로 격자만 있던 자리가
채워지는 것이 미니맵에서 그대로 보인다.

## 5. 경기 규칙과 시간

### 5.1 인원과 승패

- 도망자 3명, 술래 3명. 최초 역할은 서버가 섞어 배정하고 재경기 역할 계획도 서버가 적용한다.
- 도망자 2명이 탈출하면 도망자 팀 즉시 승리. 도망자 2명이 포획되면 술래 팀 즉시 승리.
- 180초 종료 시 탈출자가 2명 미만이면 술래 팀 승리.
- 도망자의 ACTIVE → ESCAPED 또는 CAPTURED는 배타적이며 결과·누계를 한 번만 확정한다.

### 5.2 시간과 행동

| 항목             | 값                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| 서버 권위 시간   | 50ms Tick, 초당 20회. 한 프로세스가 모든 방의 Tick을 돌림                                      |
| 경기 길이        | 3,600 Tick = 180초                                                                             |
| 한 칸 전진·후진  | 12 Tick = 600ms(튜닝 `moveTicks`, 4–40 정수. 270 임시값, 6인 세션 뒤 확정)                     |
| 좌우 90도 회전   | 8 Tick = 400ms(튜닝 `turnTicks`, 2–40 정수, 이동보다 길 수 없음)                               |
| 이동 의도 유지   | 클라이언트 100ms 간격 갱신, 서버 TTL 500ms                                                     |
| 행동 버퍼        | 대기 회전 1개                                                                                  |
| 서버 과부하 보호 | catch-up 최대 4회. 예정 시각보다 250ms 넘게 늦으면 경기 무효. 한 방의 Tick 예외는 그 방만 무효 |

이동·회전 시간은 `server/config/tuning/mvp-v1.json`(`tuningVersion` mvp-v2)의 값이고 규칙 코어는 범위만 검증한다(`MATCH_TUNING_RANGES`). 화면·개인 체험·데모 인형은 행동의 `startTick·endTick`에서 길이를 읽으며, 서버 없는 개인 체험만 프로토콜의 미러 상수(`PRODUCT_ACTION_TICKS`)를 쓰고 그 값은 서버 시험이 튜닝과 같게 고정한다. 값을 바꾸려면 JSON과 미러 상수 두 곳을 함께 바꾼다.

이동과 회전은 동시에 실행되지 않는다. 진행 중 행동을 끝낸 뒤 대기 회전을 먼저 처리하고, 유지 이동이 있으면 다음 한 칸을 시작한다. 키를 놓아도 시작한 한 칸은 완료한다.

**탭·홀드(281).** 서버는 한 칸이 끝나는 Tick에만 유지 의도를 보므로, 칸 도중의 해제·재발동은 진행 중인 칸에 영향을 주지 않는다. 클라이언트는 이 성질을 써서 짧게 기울인 입력을 **정확히 한 칸**으로 만든다. 의도를 한 번 보낸 뒤 100ms 안에 해제하면 시작한 칸만 남고 다음 칸이 시작되지 않으며, 같은 방향을 `holdToContinuousMs`(현재 400ms, 281 임시값) 넘게 유지하면 다음 칸이 시작되기 전에 연속 이동으로 올라가 끊김이 없다. 모션과 키보드가 같은 규칙을 쓴다. 서버 규칙과 프로토콜은 바뀌지 않는다. 벽·격자 밖은 이동할 수 없고 아군의 같은 칸 점유는 이동을 막지 않는다. 논리 칸·방향은 행동 종료 Tick에 확정하고 중간 화면은 보간한다.

### 5.3 포획

이동 완료 후 술래와 도망자가 같은 칸에 있거나 같은 Tick에 서로의 칸을 맞바꿔 지나가면 포획한다. 옆 칸·대각선·벽 너머 포획은 없다. 같은 Tick에서 포획은 장비 발동·출구 완료보다 먼저 확정한다. 구속 면역은 포획 면역이 아니다.

**개인 종료 뒤 관전(269).** 포획되거나 탈출한 도망자는 라운드가 끝날 때까지 생존 도망자 한 명의 시점을 관전한다. 관전자가 받는 지형·출구·시야·보이는 개체·얼굴·음성은 대상이 받는 것과 같고, 대상 본인의 목소리는 대상이 듣지 않으므로 관전자도 듣지 않는다. 대상은 `SPECTATE`로 생존 도망자 사이에서 바꿀 수 있고 기본은 명단 순서의 첫 생존자다. 대상이 종료되면 다음 생존자로 넘어간다. 관전자는 어떤 게임 명령도 낼 수 없고 규칙 코어는 관전을 모른다(서버가 대상의 뷰를 투영). 관전자의 얼굴·음성은 누구에게도 들리거나 보이지 않는다. 술래는 개인 종료가 없어 관전이 없다.

## 6. 조작·장치·모션

### 6.1 플레이어 조작표

| 행동                | 모션·기본 방식                | 보조 입력·조건                                                                               |
| ------------------- | ----------------------------- | -------------------------------------------------------------------------------------------- |
| 전진/후진           | 몸을 앞/뒤로 기울임           | 키보드 모드에서만 W/S 또는 ↑/↓. 전진 180ms·후진 320ms 유지 뒤 한 칸, 400ms 더 유지하면 연속  |
| 좌/우 90도 회전     | 고개를 돌린 뒤 정면 중립 복귀 | 키보드 모드에서만 A/D 또는 ←/→. 150ms 유지 뒤 1회, 놓고 150ms 지나야 다음 회전. 키 반복 무시 |
| 지도 교환 요청/수락 | 손바닥 600ms 유지             | 화면 버튼 또는 E. ACTIVE 도망자끼리만                                                        |
| 감지기/덫 선택      | 현재 선택 장비 사용           | 1=감지기, 2=덫. 기본 감지기                                                                  |
| 술래 장비 설치/취소 | V 손동작 600ms 유지           | F 또는 화면 행동. 설치 중 다시 발동하면 취소                                                 |
| 자기 출구 도전 시작 | 출구를 향해 명시적으로 시작   | 버튼/E. 손바닥으로 도전을 시작하지 않음                                                      |
| 탈출 도전 수행      | 지정 상체 포즈 유지           | 키보드 모드에서는 제시된 방향키 순서                                                         |
| 도전 취소           | 화면 취소                     | Esc                                                                                          |

**키보드는 보조 입력이다(265).** 모션 모드에서 이동·회전 키는 무시되고 웹캠으로만 움직인다. 키보드 모드(장애 폴백 또는 사용자 선택)에서는 모션과 같은 유지 시간(`INPUT_TUNING`의 전진 180ms·후진 320ms·회전 150ms·중립 150ms)을 채워야 명령이 나가므로 키보드로 바꿔도 반응 시간에서 이득이 없다. 서버는 입력 방식을 구분하지 않으며 최대 속도만 같게 한다(튜닝의 `moveTicks`·`turnTicks`, 현재 600ms/칸·400ms/회전). 유지 시간은 타이머 발화가 아니라 시계로 판정하므로, 메인 스레드가 막혀 키를 놓는 처리가 유지 타이머보다 먼저 돌아도 실제로 채운 유지 시간은 놓는 시점에 명령이 된다(모션이 표본 시각으로 재는 것과 같다). 이 규칙은 정상 클라이언트의 것이며 변조 클라이언트를 막지는 않는다. E/F/1/2/Esc 단축키와 화면 버튼의 반응 시간은 바꾸지 않았다.

E는 들어온 교환 수락 → 유효한 자기 출구 도전 → 선택 대상에게 교환 요청 순으로 해석한다. 입력창·IME 조합 중에는 게임 단축키를 만들지 않는다. 숨긴 탭·개인 종료·권위 상실·모드 변경 시 유지 입력을 정리한다.

### 6.2 최초 장치 준비

카메라·vision·calibration·audioPlayback이 모두 ready여야 한다. 마이크는 기본 꺼짐이며 선택으로 켠다.

- 카메라 요청은 640×480 ideal, 최대 30fps. 정면 얼굴과 양쪽 어깨가 보여야 한다. 팔은 탈출 포즈 도전 때만 판정에 쓴다.
- vision ready = 모델 로드 + 유효 얼굴 + 첫 안전 가공 프레임 + 살아 있는 가공 트랙.
- 보정은 모델 준비 뒤 새 표본 8개를 2초 창에서 모아 yaw·기울임 중립을 계산한다.
- 오디오 준비는 실제 출력과 같은 AudioContext를 사용자 동작으로 재개해 running인지 확인한다. 확인음(660Hz·350ms)과 선택 마이크 입력 막대로 점검한다.
- 얼굴 조건 안내: 장치 점검·팀 연습·경기 화면에 고개 돌림·안경 반사·역광·가림을 서로 다른 조치 문구로 보여 준다(800ms 지속 시 표시, 풀린 뒤 2초 후 해제, 같은 조건 10초 재표시 억제).
- 준비 대기 계측: 권한·장치 열기·모델 적재·첫 게시 단계별 시간과 원인을 기록한다. 로딩 화면의 대기 항목 옆에 막힌 단계·원인·경과 시간을 함께 보여 준다(예: “카메라 연결(권한 확인 중 12초)”). 모든 클라이언트 단계가 끝났는데 대기가 남으면 서버·연결 쪽이다.

### 6.3 장치 점검 화면(네 단계)

장치 점검은 네 단계 캐러셀이며 한 번에 한 단계만 보여 준다. 단계 판정은 위 다섯 상태를 나눠
읽기만 하고 새 상태를 만들지 않는다. 점 진행표시는 단계별로 통과·진행 중·막힘을 구분하고,
지나온 단계로는 돌아갈 수 있으나 아직 닿지 않은 단계로는 건너뛸 수 없다.

| 단계     | 읽는 상태                    | 통과 조건                                        |
| -------- | ---------------------------- | ------------------------------------------------ |
| 1 카메라 | `camera`·`vision`            | 둘 다 ready                                      |
| 2 자세   | `calibration` (+ 동작 확인)  | calibration ready, 기울이기·고개 돌리기 각 1회   |
| 3 소리   | `audioPlayback`·`microphone` | audioPlayback ready. 마이크는 선택이라 막지 않음 |
| 4 완료   | 위 네 값                     | 6.2의 준비 조건을 모두 만족                      |

동작 확인은 보정 뒤 상대 기울임·상대 yaw가 입력 층이 그때 쓰던 진입 임계(6.4)를 한 번 넘었는지만
기록한다. 임계값을 화면에서 새로 정하지 않으며 조작 판정에는 쓰지 않는다. 다시 보정하면 확인도
처음부터 다시 받는다. 동작 신호가 없는 화면(검수·키보드 조작)에서는 확인을 요구하지 않는다.

오류 문구는 그 code 를 낸 단계 안에서만 보여 준다. `CALIBRATION_*`은 자세, `MICROPHONE_*`·
`AUDIO_*`는 소리, 나머지는 카메라 단계가 맡는다. 준비 완료 단추는 6.2의 준비 조건만 보며, 동작
확인이 없다고 준비를 막지는 않는다. 같은 화면을 개인 체험에서도 그대로 쓰고, 그때는 보고할
준비 상태가 없어 준비 단추를 그리지 않는다.

기울임은 양어깨 화면 거리와 뺨 거리를 각각 자연로그로 만들어 중립값을 뺀 평균이다. 고개가 해제 임계(12°) 이상 돌아간 동안은 이동 판정을 만들지 않는다. 표본별 One Euro Filter를 적용하고, 만료·장치 세대·모드·보정 변경 때 필터와 유지 상태를 정리한다. 내 미리보기는 거울처럼 뒤집는다.

**해제 지연 실측(280).** 기울임이 해제 임계 아래로 내려온 **표본 시각**과 그 표본을 받아 이동 의도를 끊은 시각의 차이를 최근 10회까지 모아 디버그 오버레이에 최근·중앙값·최대로 보여 준다. 추론·필터·전달에 걸린 시간이며 **몸이 돌아오는 시간은 이 값 앞이라 들어 있지 않다**. 판정에는 쓰지 않고 키보드는 표본이 없어 재지 않는다. 이 값이 탭·홀드 경계(281)와 조기 해제(282)의 시간 상수 근거다.

## 7. 맵·시야·개인 지도

### 7.1 논리 맵

인증된 본경기 템플릿은 둘이다. 서버가 검증된 고정 맵의 8개 변형·시작점·출구 조합을 고르고 실패하면 인증된 fallback을 쓴다. 전체 맵·출구 배치·seed·튜닝을 브라우저에 보내지 않는다. 연습 맵과 본경기 맵은 분리되며 연습 정보는 이월하지 않는다.

- **master-v1**(기본): 32×32 개방 격자. 6칸마다 기둥 하나, 통로 폭 5칸.
- **maze-v1**(267): 31×31 홀수 격자 위의 **통로 폭 1칸** 미로. 교차점은 홀수 좌표, 짝수·짝수 칸은 항상 벽이라 2×2 열린 블록이 없다. 교차점 225·연결 250·순환 26, 막다른 길 0(생성 직후 24개를 전부 이웃으로 뚫고 단절점 2곳에 우회로를 냈다). 통로 전체가 하나의 이중 연결 core라 시작 후보·출구 접근 칸이 모두 core 안에 있다. 술래 구역은 가로 중간 띠 셋(서·중·동), 도망자 시작은 북서·북동 모서리와 남쪽 중앙. 출구 후보 340개는 접근 칸이 교차점인 안쪽 벽면만 골라 출구가 통로를 막지 않는다. `scripts/generate-maze-template.mjs`가 고정 seed 267로 맵과 fallback을 바이트 단위로 재생성하며(`pnpm maps:generate`, 검사는 `pnpm maps:check`), 구조 약속은 `maze-template.test.ts`가 고정한다.

템플릿 선택은 서버 환경 변수 `PRODUCT_MAP_TEMPLATE`(기본 `master-v1`)이다. 두 템플릿은 같은 배치 제약(`mvp-v1.json` layout)과 같은 로더·해시·fallback 인증을 거친다. 통로 1칸에서는 접촉 포획을 피할 수 없어 술래가 더 유리하므로 밸런스 조정(229)은 maze-v1 기준으로 진행한다.

### 7.2 정보 비대칭

- 서버 시야는 수평 80°, 거리 상한 3.5셀, 벽 차폐와 벽 뒷면을 고려한다. 실제 관찰한 바닥·벽면을 개인 지도에 누적한다.
- 초기 지식: 도망자는 자기 칸, 술래는 담당 구역의 통로·경계 벽면에 첫 시야를 더한다. 술래도 전체 맵을 받지 않는다.
- 현재 보이는 참가자·장비와 과거 탐색 지도는 구분한다. 시야 밖 참가자의 현재 좌표를 지도에 표시하지 않는다. 두 가지는 프로토콜에서 다른 필드(`visibleCells`·`visibleWallFaces`·`visibleEntities` / `knownTerrain`·`knownActiveExits`)로 나뉘어 오고, 클라이언트는 현재 시야를 더하거나 빼지 않는다(301). 시점 주인 본인만 그리지 않으며 관전 중에는 보고 있는 대상이 그 자리다.
- 출구는 정확한 벽면을 실제 관찰한 도망자만 발견한다. 술래에게 출구 목록을 보내지 않는다. 포즈는 자기 도전 시작 때 공개된다.
- 개인 종료로 닫힌 출구는 지도에서도 닫힌다.

### 7.3 렌더링 기준

단일 R3F Canvas. 테마는 둘이며 기본은 **백룸형 시설 복도**이고 `?theme=block`이나 저장된 선택으로 어두운 블록 테마를 고를 수 있다. 서버는 테마를 모른다.

- **백룸형 시설 복도**: 한 칸 폭 통로, 1.9셀 높이 벽, 낡은 노란 무늬 벽지, 얼룩진 카펫, 낮은 타일 천장과 형광등으로 구성한다. 두 품질 모두 사용자 제공 seamless 색상 맵을 가로 1회·세로 2회 반복한다. 원본 이미지의 위아래 무늬가 서로 맞지 않아 세로는 반사 반복(MirroredRepeatWrapping)으로 같은 가장자리가 맞닿게 한다. 이 이미지와 무늬 위치가 다른 원본 roughness·normal 맵은 결합하지 않는다. 저품질은 추가 표면 레이어와 보조 조명을 줄인다. 실제 경기의 시선 방향 근거리 조명과 1.7–3.2셀 안개는 유지한다.
- **어두운 블록**(대체 테마): 마인크래프트 1인칭에서 블록 형태·픽셀 텍스처·화면 배치만 가져오고 밝은 야외·먼 시야는 가져오지 않는다. 바닥·천장·벽면은 코드로 만든 16×16 픽셀 타일(`NearestFilter`, 밉맵 없음)이며 팔레트는 로고와 같다(검정, 갈라진 뼛빛 돌, 어두운 갈색 틈). 벽면 다섯 중 하나는 고정 규칙으로 이끼 타일. 광원은 **플레이어가 든 랜턴 한 점**(오른손, 도달 3.4셀)과 약한 앰비언트뿐이고 반구광·방향광은 없다. 안개 1.5–3.2셀. 시야 밖은 완전한 어둠. 화면 우하단에 **든 도구**(랜턴 + 술래는 선택 장비, 도망자는 지도 조각)가 카메라를 따라간다. HUD가 핫바 선택을 넘기기 전까지는 재고 순서(감지기→덫)로 정한다.

두 테마 모두 안개 끝이 서버 시야 3.5셀을 넘지 않는다(`block-theme.test`가 고정). 시설 벽 높이는 1.9셀, 블록 벽 높이는 1.2셀이고 카메라 높이 0.8셀, 가로 FOV 80°다. **거리 상한과 시야각은 `apps/web`가 코어를 import할 수 없어 손으로 복제한 값이므로**, 원본(`VIEW_RANGE`·`FOV_HALF_DEGREES`)과 같은지는 양쪽을 다 읽을 수 있는 계약 시험 `tests/contracts/view-geometry.test.ts`가 고정한다. **화면이 그리는 현재 시야는 서버가 승인한 집합 그대로이며 클라이언트가 다시 자르지 않는다**(301). 안개는 먼 것을 흐리게 할 뿐 셀을 빼지 않는다. 코어 출력과 화면에 도착한 집합이 같은지는 정지·사방·이동 중·회전 중·모서리·관전에서 `tests/contracts/server-sight-fidelity.test.ts`가 고정한다.

아바타는 **블록 비율**(정육면체 머리·상자 몸통·상자 팔다리)이며 실제 얼굴 평면은 머리 앞면에 그대로, 조명을 받지 않는 재질이라 어둠 속에서도 보인다. **역할별 색과 실루엣**(W1): 술래는 붉은 옷(`#b8402f`)·넓은 어깨·모자 챙, 도망자는 청록 옷(`#2f9f96`)·좁은 어깨·가방. 같은 hex가 HUD·미니맵 토큰(`--role-tagger`, `--role-runner`)에 들어가며, `styles.css`가 원본을 그대로 담고 있는지는 계약 시험 `tests/contracts/role-color-tokens.test.ts`가 고정한다. 역할을 모르는 개체는 회색·형태 단서 없음. 상대 몸·머리·얼굴은 한 그룹에서 서버 행동을 보간하고 미래 위치를 예측하지 않는다. 이동 중 팔다리 스윙과 몸 상하 흔들림은 같은 보간 진행도에서 파생한 장식이며(한 칸 = 두 걸음, 다리와 팔은 반대 위상) 위치·방향·얼굴 평면 회전을 바꾸지 않고 정지·회전에서는 기본 자세다. 감지기와 덫은 색에만 의존하지 않고 형상으로 구분한다. 바닥 덫은 카메라 높이와 세로 시야각 때문에 약 1.7셀 안의 바닥이 프레임 밖이므로 바닥판 위 지지대·표시등(높이 0.45)으로 인접 셀에서도 보인다. 눈은 시선 방향으로 1mm 앞당긴다(셀 중심에서 정확히 45° 회전할 때 자기 셀 벽 끝 꼭짓점이 카메라 평면에 놓여 벽이 한 프레임 평면으로 그려지는 클리핑 퇴화를 막음). 조명 값은 `LIGHTING` 상수에 있고 근접 벽 과다 노출과 원거리 가독성의 관계를 시험이 고정한다. HUD는 감지기(▣)·덫(▲), 무장(●)·대기(○)·소모(×), 구속(⛓)·면역(◈), 탈출(◇)·포획(◆)을 글리프와 `data-state`/`data-outcome`로 구분하고 색은 3D 표시등과 같은 값을 쓴다. 기본 DPR 1.5, 가벼운 품질 DPR 1이며 정보는 동일하다. 벽지 PBR 이미지를 제외한 형상·효과음은 코드로 만든다.

검수: `pnpm dev:web` → 개발 `/preview`의 렌더 검수에서 복도·코너·출구·장비·상대 5명을 네 방향·이동 시점별로 확인한다. **내 동작**을 회전으로 두고 8·10·12·15·20틱에서 옆 벽 질감이 유지되는지(10틱이 45°), 이동으로 두고 전진 중 상대 정렬과 셀 등장을 본다. 출구·장비 장면에서 바로 앞 셀 덫의 지지대가 화면 하단에 보여야 한다. 실제 얼굴 가독성, 길찾기·공포/불편, 저사양 성능은 실제 플레이로 판정한다. 화면을 풍부하게 하려고 서버 비공개 맵을 클라이언트로 옮기지 않는다.

## 8. 지도 교환

**ACTIVE 도망자끼리** 같은 칸 또는 상하좌우로 붙은 통로 칸에서 한다. 서로의 지형·열린 출구 정보가 같으면 교환하지 않는다.

1. 요청자가 가시 아군 후보에게 요청한다. 서버가 역할·거리·상태·새 정보 조건을 따로 검사한다.
2. 수신자가 2초 안에 수락한다. 참가자는 한 교환 세션만 가진다.
3. 성공 시 그 순간의 탐색 지형과 발견한 활성 출구를 합친다. 이후 실시간 공유는 아니다.
4. 구속·출구 도전·개인 종료·범위 이탈·취소·만료로 끝난다.
5. 성공 지점 두 좌표의 중간점이 1초 뒤 ACTIVE 술래에게 2초간 과거 흔적으로 보인다. 신원·현재 이동은 추적하지 않는다.

연습 화면의 안내는 역할별로 다르다(술래에게 지도 교환을 안내하지 않음).

근거: [교환 세션](../../packages/game-core/src/match/exchange/session.ts), [지식 병합](../../packages/game-core/src/match/exchange/merge.ts), [흔적](../../packages/game-core/src/match/exchange/trace.ts).

## 9. 술래 장비와 구속

### 9.1 설치

술래는 경기마다 감지기 1개와 덫 1개를 가진다. 정지 상태에서 감지기는 앞 내부 벽면, 덫은 자기 통로 칸에 설치한다. 시작 칸·외곽 벽·기존 장비·설치 예약 칸은 금지하며 출구 존재를 허용/거절로 유출하지 않는다. 설치 0.5초, 완료 후 1초 뒤 무장. 완료 전 이동·회전·개인 종료·취소가 있으면 재고를 쓰지 않는다.

### 9.2 발동과 흔적

| 장비   | 발동                                                           | 결과                                            |
| ------ | -------------------------------------------------------------- | ----------------------------------------------- |
| 감지기 | 무장 후 ACTIVE 도망자가 접근 칸에 새로 진입                    | 단발 작동, 위치 흔적과 소리. 구속 면역자도 감지 |
| 덫     | 무장 후 구속·재구속 면역이 없는 ACTIVE 도망자가 칸에 새로 진입 | 후보 중 정확히 한 명을 골라 1.5초 구속          |

무장 시 이미 서 있거나 면역이 끝났다는 이유만으로 새 진입을 만들지 않는다. 덫 동시 후보는 경기별 기본 순서를 Tick마다 순환하는 우선순위로 한 명을 고른다. 장비는 한 번 작동하면 소모되고, 발동 위치는 즉시 ACTIVE 술래에게 2초간 흔적으로 보이며 효과음이 난다.

### 9.3 구속

구속은 새 이동·지도 교환·출구 도전을 막고 진행 중 출구 도전을 끝낸다. **구속 중 회전은 가능하다.** 1.5초 뒤 자연 해제되고 2초간 재구속 면역을 갖는다. 감지기·포획 면역은 아니다.

## 10. 개인 출구와 탈출

도망자는 자기 전용 출구 하나를 가진다. 접근 칸에서 정확한 벽 방향을 바라보고, 진행 중 행동·구속·재시도 대기가 없을 때 버튼/E로 도전을 시작한다. 도착만으로 자동 시작하지 않는다.

- 포즈는 왼팔 들기, 오른팔 들기, 양팔 Y자 중 하나이며 같은 출구의 재시도에서 바뀌지 않는다.
- 모션 모드는 유효한 얼굴·상체 표본으로 지정 자세 1.2초 유지. 키보드 모드는 challengeId로 고정된 방향키 4개 순서(오입력 시 처음부터, 자동 반복 불인정).
- 서버 기준 시작 후 최소 2초, 8초 미만에서만 성공. 실패·취소 후 0.5초 재시도 대기.
- 도전 중 이동·회전·교환은 잠기고 취소는 가능하다. 도전 중에도 포획될 수 있다. 성공·포획 뒤 출구는 닫히고 재배정하지 않는다.

**판정 경계:** 서버는 도전·위치·방향·시간·중복을 검사한다. 카메라 앞 실제 신체 수행이나 키 입력의 진위를 서버가 독립적으로 증명하지는 않는다.

## 11. 얼굴·음성·효과음

### 11.1 실제 얼굴과 로컬 처리

정상 앱은 원본 웹캠을 로컬 미리보기·추론에만 쓰고, 얼굴 윤곽을 마스킹한 실제 얼굴 픽셀을 흑백으로 만들어 게시한다. 마스크 바깥은 검정이다. **익명 아바타가 아니다.**

| 항목           | 구현                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| 출력 Canvas    | 160×160, captureStream 10fps                                               |
| 기본 얼굴 송출 | 인코딩 상한 100kbps·10fps, simulcast off                                   |
| low 품질       | 다음 게시부터 50kbps·8fps. Canvas 크기는 유지. 재경기 뒤에도 선택 유지     |
| 안전 얼굴      | 마지막 안전 관측 기준 최대 1,200ms 유지 후 기본 얼굴. 탭 숨김 시 즉시 전환 |
| 모델           | 얼굴 1명·자세 1명·손 2개. 고정 로컬 모델·WASM, 바이트 해시 검사            |
| 추론           | Worker에서 순서대로 실행, 진행 중 프레임 하나                              |

경기에서는 다른 참가자 최대 5명의 얼굴 트랙을 미리 수신하고 시야에 들어온 캐릭터에 표시한다. 연습은 같은 팀 최대 2명이다. **보이지 않는 참가자의 얼굴 스트림도 기기에 먼저 도착할 수 있다.**

### 11.2 근거리 음성

경기 음성은 팀 구분 없이 근거리에서 들린다. 자기 음성·전역 음성·팀 무전·텍스트 채팅은 없다. 연습은 같은 팀 인스턴스 안에서만 연결한다.

거리는 통과 가능한 통로의 최단 셀 거리(같으면 코너가 적은 경로)다. 새 청취는 거리 5 이하에서 허용, 기존 허용은 6까지 유지, 6을 넘으면 해제한다. 거리·코너 수에 따라 볼륨과 저역 필터, 좌우 StereoPanner로 방향을 준다. 완전한 3D 공간음향은 아니다. 로딩·카운트다운·개인 종료·탭 숨김·권위 상실 때 출력을 잠근다. 잠금은 서버가 허용한 소리(음성·위치 효과음)에 적용되며, 아래 자기 상태 안내음은 잠금과 무관하게 음소거·음량만 따른다.

### 11.3 효과음과 사용자 제어

발소리는 한 칸 이동 완료 시 4셀, 감지기·덫은 6셀. 코드 생성 PCM이며 같은 서버 사건을 한 번만 재생한다. 감지기·덫은 소리와 함께 전면 플래시와 문구도 낸다(발소리는 소리만). 서버가 들려주기로 한 효과음만 그대로 옮기고 거리를 다시 재지 않으며, 같은 `eventId`는 한 번만 낸다. 자기 상태 플래시가 아직 떠 있으면 더 구체적인 그 문구를 덮지 않는다.

자기 상태 안내음은 내 화면에 이미 있는 사실만 알린다: 카운트다운 초·시작, 구속, 포획당함, 탈출 성공, 탈출 실패, 교환 요청 수신·완료, 공개 누계 변화(내 팀 유리/불리), 승리·패배·무효. 공개 라운드·자기 개인 뷰·private 사건의 변화로 클라이언트가 판정하며 서버 계약을 늘리지 않는다. 포획당함·탈출·실패·구속·승패는 전면 플래시와 문구를 함께 내고, 구속 중에는 화면 가장자리를 어둡게 유지한다. 움직임 축소 설정에서는 플래시 없이 문구만 보인다. 누계 안내음은 자기 종료 안내음과 겹치지 않도록 0.3초 미뤄 낸다.

사용자 제어: 모드 전환, 재보정·장치 점검, 마이크 끄기/재시도(카메라 재취득 없음), 품질 선택, 확인음, 마이크 입력 막대, 듣는 음량(기본 70%), 전체 소리 끄기, 친구별 목소리 끄기, 나가기. 음량은 서버가 허용한 소리에만 적용하고 출력 잠금을 열지 않는다. 같은 방 재경기에서 유지하고 퇴장 시 초기화한다.

### 11.4 권한과 개인정보 안내

- 미디어 권한은 `publisher-permissions`다. 서버가 허용 목록을 계산하고 정상 송신 앱이 SFU에 적용한다. 실제 Cloud에서 허용 수신·금지 직접 구독 차단·허용 철회·옛 토큰 거절을 확인했다(MC-01 R9).
- **수용한 위험:** 변조한 송신 앱은 허용 목록을 넓혀 금지 수신자에게 트랙을 보낼 수 있다. 친구 초대방 범위에서 수용하고 공개 안내로 보완한다(D-2026-09-15-01). 서버 단독 통제 후보(split)는 보류했다.
- 개인정보 처리 안내는 실제 코드 경로에서 확인한 사실만 쓴다: 기기 안 추론과 얼굴 좌표 미전송, 가공 얼굴만 게시, 선택 마이크의 원본 음성 전달, LiveKit 중계로 같은 방 참가자에게만 전달, 사전 수신과 출력 제어, **가공을 각 기기가 하므로 변조된 클라이언트는 가공되지 않은 영상을 보낼 수 있다는 것**, 서비스 저장·녹화 없음과 메모리 방 상태의 만료 삭제. 서비스에 녹화 기능이 없다는 사실을 상대 단말의 녹화 불가능으로 설명하지 않는다. 문의처는 미확정이라 넣지 않았다.
- **카메라를 켜기 전에 동의 게이트를 지난다**(S15P21C204-292). 장치 점검 화면은 동의 전에는 장치 제어 대신 안내 전문과 두 확인(읽고 동의·만 14세 이상)을 보여 주고, 둘 다 받아야 진행한다. 동의는 안내문 판과 함께 기기에 남고 판이 올라가면 다시 묻는다. 저장소가 막힌 브라우저에서는 매번 묻는다. 로비의 안내 표시는 그대로 둔다.
- 권리: 얼굴·자세·손 추적 구성 모델은 Apache-2.0 확인, 홈에서 원문 고지. 손동작 임베더·분류기 2개와 SDK 번들 제3자 고지(XNNPACK BSD-3-Clause 등)는 미완료다. [제3자 자산](../third-party-assets.md).

### 13.2 입장과 접근 경계

- 입장 방식은 `SERVICE_AUDIENCE=team`(gitlab-sso) 또는 `public`(guest)로 고르고 두 설정이 어긋나면 부팅을 거절한다. public+LiveKit은 `publisher-permissions`에서만 부팅한다. 운영은 team이다. 호스트 프록시가 인증해 덮어쓴 신원만 신뢰하고 클라이언트가 신원을 지정하지 않는다. 게스트 방 생성은 신원을 바꿔도 같은 IP 제한을 받는다. 제한과 방 상한은 주소 원본이 아니라 **접힌 출처 키**로 센다(300). IPv6는 /64로 접어 임시 주소 회전을 한 출처로 묶고, IPv4-mapped IPv6는 IPv4와 같은 출처로 본다. 한 출처가 동시에 열 수 있는 방은 `MAX_ROOMS_PER_ORIGIN`(기본 2)이며 공유 NAT 뒤 여러 사람은 한 출처로 묶인다. 내 상한 초과(`TOO_MANY_ROOMS`)와 서비스 포화(`CAPACITY`)는 다르게 답하고, 좌석 레지스트리 내부 코드는 밖으로 내보내지 않는다.
- 게임 서버 포트는 비공개, web-proxy는 loopback. 운영 API는 별도 OPS_TOKEN.
- 방 수: 스키마 1–10방, 방당 6석(`MAX_SLOTS = MAX_ROOMS × 6`). 값의 원본은 제품 Compose overlay이며 배포 사전 검사가 실제 값으로 검증한다. 운영은 10방이며, 게임 단독 60클라이언트 30분(QA-10)까지 검증했고 실제 미디어 단계 부하(QA-11/12)는 미실행이다.
- 요청 상한: 운영·미디어 HTTP는 파싱 전에 인증 종류별 초당·동시 상한, 본문 2,048B·5초. 운영 명령 대기 64, 감사 오류 표본 24시간·4,096개.
- 체류 기한: 로비 무활동 10분, 장치 준비·결과·중단 5분, 종료 60초 전 안내. 하트비트·준비 반복으로 연장하지 않는다.

### 13.3 상시 운영

승인된 continuous 모드는 서비스 종료 날짜·일일 증거 갱신·수동 잔량 입력에 의존하지 않는다. 설정 무결성, capability, 영속 저널·예약·회수·부팅 복구, 인증·방 상한·API 예산은 유지한다. 공식 월간 잔량은 알 수 없음(`null`)으로 보고하며 무한으로 해석하지 않는다. LiveKit Build 플랜 한도: 동시 참가자 100, API 분당 10,000, 월 5,000 참가자-분·50GB(초과 시 차단). 미디어 API 서버 예산의 설정 상한은 60초 정상 6,000 / 전체 9,000이며 운영 값은 별도다. 월 사용량 경보는 남은 과제다. [운영](../operations.md).

### 13.4 배포와 관측

배포: 매니페스트 → SSO 격리 확인 → drain → 이미지 교체 → READY → resume/OPEN → 실제 Cloud 합성 6인 DP-06 → 공개 재검사 → last-good. 실패는 확인된 장벽으로만 롤백하며 회수 불명·손상 상태를 강제로 재개하지 않는다. CI 성공·MR 병합·배포 성공은 각각 확인한다. 로그·지표·로컬 경고·빌드 실패 알림은 있고, 런타임 외부 장애 알림·호스트 외부 백업·자원 상한은 남아 있다. Trivy 결과는 기록만 한다. [인프라](../../infra/README.md).

## 17. 좋은 첫 경험과 평가 기준

**목표 여정(제안):** 홈에서 6인·장치 조건 이해 → 혼자 카메라/오디오 점검 → 한 칸 이동·회전·역할 행동 연습 → 친구에게 방 링크 공유 → 준비 실패를 각자 해결 → 경기 완주 → 승패 이유 이해 → 역할을 바꿔 재경기.

| 목적        | 측정                                                                                 |
| ----------- | ------------------------------------------------------------------------------------ |
| 첫 진입     | 홈→체험→장치 준비→방 참가→첫 경기 소요 시간·단계별 이탈·실패 코드                    |
| 조작        | 중립 오입력, 의도한 전후 이동/단발 회전 성공, 보정 시도 수, 손 가림·카메라 각도 영향 |
| 소리        | 실제 출력 확인, 발소리/장비 소리 구분, 거리·방향 인지, 기본 음량 불편                |
| 완주        | 장치/네트워크로 무효가 된 판, 원인·복귀 성공, 반복 경기 뒤 자원 증가                 |
| 협업·밸런스 | 지도 교환·장비 활용, 역할별 승률과 종료 시간, 행동 없이 대기한 시간                  |
| 만족        | 무서웠던 순간, 조작 때문에 억울했는지, 규칙·승패 이해, 자발적 재경기 의향            |

초기 목표 예시(합의 전 제안): 혼자 방문 후 1분 안에 체험 진입, 두 번 안에 보정 성공, 6명 입장 후 5분 안에 첫 경기 시작. G5의 5판은 장치·통합 최소 조건이며 재미·밸런스 검증으로 결론 내리지 않는다.

### 18.2 공개 전 통과 조건

실제 증거가 있을 때만 체크한다. 모두 충족해도 운영은 팀원 전용을 유지하고, 실제 공개는 별도 전환 작업이다.

- [ ] 게스트가 정의된 인증·방 참가 경로로 들어오고 운영 API·개발 도구는 보호된다.
- [ ] 정상 앱에서 금지 음성·비공개 게임 정보가 노출되지 않는다(G1·G4). 변조 송신 위험은 안내에 명시한다.
- [ ] AFK·결과 화면의 무기한 점유와 요청 폭주가 정상 이용을 막지 않는다.
- [ ] 반복 경기 뒤 자원이 안정되고 옛 요청이 새 발급으로 바뀌지 않는다.
- [ ] 개인 장치 점검·조작 연습과 실패별 다음 행동이 제공된다.
- [ ] 대표 장치 6대로 5판을 완료하고 장치·네트워크·모션·오디오 결과를 기록했다(G5).
- [ ] 연결 상실·미디어 장애·카메라 오류의 복구/중단 정책이 구현과 안내에 일치한다.
- [ ] 검증한 방 수만 열었고 1→3→5→10방 결과가 있다(G2·G6).
- [ ] 런타임 장애 경고가 담당자에게 도착하고 배포/롤백·운영 기록 복원을 확인했다.
- [ ] 이미지 취약점 기준과 모델·SDK 권리·고지를 완료했다.
- [ ] 얼굴·음성 전송을 이해하고 참가하며 즉시 음소거·퇴장할 수 있고, 문의·보관 안내가 있다.
- [ ] 신규 그룹이 목표·승패를 이해하고 렌더링·조작·협업·재경기 경험을 검수했다.
- [ ] 같은 이미지로 team→public→team 리허설을 통과했다.

최종 기능 인수 문구는 **“D-2026-09-08-01 적용 확정 범위 완료”**다. 원본 v0.0.8의 미정 아이템까지 완성됐다는 표현으로 바꾸지 않는다.
