10방은 서버·미디어·브라우저 통합 부하 시험의 목표다. 시험 통과 전 운영 상한은 1방으로 시작하고, 통과한 단계만 3방 → 5방 → 10방으로 상향한다. 목표를 낮추거나 기능을 제거했다는 뜻은 아니다.

최대 60개 슬롯은 대기·연습·경기·결과 상태를 포함한 서비스 전체 동시 슬롯 예산이다. 실제 경기 10방에 별도 대기자 60명을 추가 수용하지 않는다. 운영 페이지는 LiveKit 참가자로 접속하지 않는다.

서버 자료의 해석

이미지 사양을 인용하되 EC2 인스턴스 타입이나 Ubuntu 버전은 만들어 쓰지 않는다. Lightsail이라면 해당 세대의 지속 CPU 기준·버스트·전송량을 콘솔에서 확인한다. 사양만으로 10방 처리 성능을 보장할 수 없다. [S5][S6]

제한 공개는 접근 통제와 공개 규모를 뜻한다. 계정 없는 초대 세션과 전용 권위 백엔드, 실시간 얼굴·근거리 음성·장비·포즈 탈출을 갖춘 MVP를 유지한다.

MATCH RULES

04. 인원·승패·개인 종료

한 판의 도망자는 정확히 3명이며 결과는 배타적이다.

조건결과
탈출 2명도망자 팀 즉시 승리
포획 2명술래 팀 즉시 승리
3분 종료, 탈출 2명 미만술래 팀 승리
탈출 1명 + 포획 1명 + 활동 1명마지막 활동자의 결과 또는 제한시간까지 진행

도망자 상태는 ACTIVE에서 ESCAPED 또는 CAPTURED 중 하나로만 전이한다. 이미 종료된 플레이어를 다시 포획하거나 탈출 처리하지 않는다. 승패 확정 뒤에는 새로운 입력·발동·점수 사건을 만들지 않는다.

탈출·포획 직후

해당 캐릭터는 맵에서 제거하고 이동·회전·지도 교환·장비·아이템·포즈 입력을 차단한다. 개인 출구는 일반 벽으로 닫고, 모든 도망자 지도에서 표식을 제거한다. 출구 재배정은 없다. 미디어 게시·구독을 종료하고 관련 트랙 권한을 서버에서 회수한다.

개인 대기 화면에는 자신의 결과, 남은 시간, 탈출·포획·활동 인원만 표시한다. 생존자 화면·지도·음성 및 위치를 새로 받지 않는다. 단말에 이미 도착한 과거 정보를 사용자가 기억하거나 별도로 복제한 것까지 회수할 수 있다고 주장하지 않는다.

개인 종료 이후 퇴장

CAPTURED·ESCAPED가 커밋된 도망자의 연결 종료는 남은 경기의 무효 사유가 아니다. 접속 세션과 미디어는 정리하되 해당 matchId의 플레이어 기록·탈출/포획 누계·출구 폐쇄는 유지한다. 진행 중인 판의 슬롯을 다른 사람으로 채우지 않으며 다음 라운드에서만 충원한다. 활동 술래 또는 ACTIVE 도망자의 연결 상실은 24장의 무효 정책을 따른다. 연결 객체 삭제로 경기 결과를 되돌리지 않는다.

결과와 재경기

팀 승패와 각 플레이어의 탈출·포획 결과, 선택적 세션 통계를 표시한다. 개인 점수로 승자를 다시 정하지 않는다. 같은 역할 재경기·역할 교대·로비 복귀를 제공한다. 서버가 준비 상태를 재확인하고 맵 변형·시작점·출구·지식·장비·아이템을 초기화한다.

불가능한 상태

도망자가 3명이고 결과가 배타적이면 “탈출 2명과 포획 2명”은 동시에 성립할 수 없다. 그런 누계는 무승부 규칙이 필요한 상황이 아니라 중복 판정 버그다. 같은 한 명의 포획·탈출 충돌만 명확한 우선순위로 해결한다.

07.1 한 Tick의 입력·획득 계약

개인 종료와 연결 상실이 같은 Tick에 확인되면 이미 예약된 유효 행동과 개인 종료를 먼저 커밋하고, 그 후 상태가 ACTIVE인 연결 상실자만 무효 대상으로 삼는다. 그 Tick에서 정상 승패가 먼저 확정됐다면 이후 연결 상실로 결과를 소급 무효화하지 않는다. 새로운 게임 연결로 진행 중 재접속하는 기능은 제공하지 않는다. 인프라 과부하는 아래 보호 단계에서 게임 처리를 시작하기 전에 차단한다.

08. 시야·차폐·미디어 정보 경계

같은 규칙으로 무엇을 전송하고 무엇을 그릴지 결정한다.

기본 시야는 전방 3셀, 수평 시야각 80도인 제한 원뿔로 시작한다. 셀 크기를 월드 1단위로 정규화한다. 서버는 이동·회전 행동에 따른 가상 카메라 위치·방향을 계산하며 클라이언트가 제출한 자유 좌표·시야값을 신뢰하지 않는다. 화면비가 넓어도 더 많은 수평 시야를 얻지 못하게 제한한다.

통로 타일은 중심과 안쪽 모서리 표본, 벽은 면별 중심과 가장자리 표본으로 가시성을 평가한다. 각 표본은 범위·시야각·그리드 DDA 시선 검사를 모두 통과해야 한다. 시선이 처음 만나는 벽면까지만 공개한다. 벽 칸 뒤 통로나 벽의 보이지 않는 뒷면 정보를 덤으로 보내지 않는다.

타일의 일부가 실제 관찰되면 해당 통로 셀을 기억할 수 있지만, 인접 벽은 별도 면 관찰이 필요하다. 출구는 지정된 벽면이 직접 보일 때 발견한다. 현재 보이는 엔티티만 위치를 전송하고, 가시성에서 이탈하면 엔티티 표시를 제거한다.

R3F 카메라는 동일 행동 시간과 공개 마스크를 사용한다. 다음 Tick의 미공개 지형이 보간 도중 노출되려 하면 안개로 가리고, 이를 없애려고 숨겨진 맵 전체를 미리 전송하지 않는다. 이동·회전 중 팝인, 코너 얇은 노출과 왕복 지연은 시각 정합 테스트의 필수 사례다.

아군과 얼굴

역할별 캐릭터 크기와 히트박스는 같고, 시야 안에서 확인된 아군에게만 작은 아군 표식을 표시한다. 적의 역할·이름표·벽 너머 윤곽선은 없다. 저해상도 얼굴을 미리 구독하더라도 게임 화면에는 가시 엔티티에만 붙인다.

3명이 동시에 요청하면 각 플레이어당 활성 교환 세션 1개만 유지한다. 먼저 서버가 승인한 쌍을 완료하고 나머지는 다시 요청한다. 초기 MVP에 다자 원자적 교환을 추가하지 않는다.

모든 술래에게 남기는 흔적

성공 1초 뒤 두 교환 셀 중심의 중점을 정확한 과거 사건 지점으로 보내고 2초간 표시한다. 안개 속에서도 점만 보이며 주변 지형·신원·진행 방향은 공개하지 않는다. 취소·새 정보 없음·동일 요청 재전송에는 알림이 없다.

EXIT CHALLENGE

11. 개인 출구와 포즈 탈출

출구 소유권·발견·폐쇄는 기존 규칙을 유지한다.

활성 출구는 시작 시 3개이며 도망자별 1개다. 일반 내부 벽면을 사용하고 위치 힌트는 없다. 다른 도망자도 발견·소유자 식별·지도 전달을 할 수 있지만 사용은 소유자만 가능하다. 술래에는 출구 데이터를 보내지 않는다. 소유자의 탈출·포획 이후 즉시 일반 벽이 되고 재배정하지 않는다.

위임 기본안: 단일 상체 포즈

포즈 풀은 왼팔 들기, 오른팔 들기, 양팔 Y자 3종으로 시작한다. 앉은 상태에서 얼굴과 상체가 카메라에 남는 범위를 사용한다. 화면 좌우 반전은 안내와 입력 좌표 모두 같은 해석을 적용한다. 준비 공간에서 사용 포즈를 시험한다.

소유자가 출구 접근 셀에 도착하면 포즈 안내가 나타나지만 자동으로 이동을 묶지는 않는다. 출구를 향한 명시적 상호작용으로 challengeId를 발급받아 수행을 시작한다. 수행 중 이동·회전·교환·아이템은 잠그며, 취소 버튼은 허용한다. 술래 접촉에는 포획된다.

감지기와 덫의 작동은 모든 술래에게 종류·정확한 과거 지점만 알린다. 신원·이동 방향·이후 현재 위치는 전송하지 않는다. 점은 2초 뒤 사라지고 미탐색 주변 지형은 공개하지 않는다. 덫에 걸린 본인에게는 구속 상태와 남은 시간을 표시한다.

구속은 새 이동 시작을 금지하며 이미 완료된 셀을 되돌리지 않는다. 회전과 덫 해제 도구 사용은 허용하되 다른 포즈·교환은 중지한다. 접촉 포획 면역은 없다. 해제 뒤 2초 동안 새 구속은 적용하지 않고, 같은 셀 장비 중복 설치를 금지해 연쇄 고정을 제한한다.

실제 시야에 들어온 장비는 양 팀 모두 볼 수 있다. 도망자 미니맵에는 설치물 자동 표시가 없고 일반 해체는 없다. 설치자는 자기 장비 위치를 개인 표시로 기억할 수 있으나 전체 술래의 설치 위치를 자동 공유하지 않는다. 팀 전체 공유는 작동 사건으로 한정한다.

13. 도망자 아이템

은신·순간이동·추가 이동 속도 없이 정보와 덫에 대응한다.

아이템사용 효과금지·실패 조건
소리 미끼현재 또는 정면의 이미 알려진 통로 2셀 이내 지점에 미끼를 둔다. 4초 동안 간헐적 가짜 발소리 발생.벽 관통 설치·정확한 타인 위치 핑·감지기와 덫의 가짜 발동 없음.
덫 해제 도구현재 자신의 구속을 해제하고 해당 구속의 연장 없이 즉시 종료.구속 중이 아니면 소모 안 함. 이미 성립한 포획 취소·포획 면역 없음.

첫 구현은 필드에 소리 미끼 3개와 해제 도구 3개, 총 6개를 배치한다. 활동 도망자만 주울 수 있고 소지 한도는 1개다. 빈 슬롯이면 진입 시 자동 획득하고, 슬롯이 차 있으면 교체하지 않고 남겨둔다. 버리기·거래·재생성은 없다.

스폰은 접근 가능한 서로 다른 통로 셀이고 시작 셀·출구 접근 셀에는 두지 않는다. 출구 위치에 따른 빈 공간을 술래에게 알려주지 않도록 미발견 아이템의 전체 스폰 테이블을 전송하지 않는다. 아이템 배치는 출구 접근성을 변경하지 않는다.

동일 Tick의 아이템 획득과 덫 대상 선정은 아래 공통 순환 우선순위를 사용한다. 동일 초기 상태와 입력이면 후보 순회 순서·패킷 배열 순서와 무관하게 같은 결과가 나와야 한다. 지급 성공은 서버 사건으로 확인한다.

게임 소리와 입력

획득·사용은 주변 가청 범위 안에서만 효과음을 낸다. 미끼 소리는 실제 플레이어와 동일한 공간 감쇠 규칙을 사용하지만 실제 사용자 ID를 효과음 payload에 붙이지 않는다. 시야에 보이면 작은 미끼 오브젝트를 알아볼 수 있다. 지도에 장거리 미끼 핑은 생성하지 않는다.

아이템은 브이 제스처 0.6초 또는 F·버튼으로 사용한다. 포즈 탈출 중에는 사용할 수 없으며 먼저 탈출을 취소해야 한다. 덫 해제는 구속 상태에서도 해당 입력만 허용한다. 사용·획득·잔량을 모두 서버가 검증한다.

밸런스는 검증 대상

종류와 사용 구조는 위임 기본안으로 채택하지만 배치 6개, 미끼 4초, 구속 1.5초를 최종 밸런스라고 주장하지 않는다. 발견·사용률과 덫 이후 포획률로 개정한다.

13.1 공통 순환 우선순위

매치 초기화 시 세 도망자의 서버 ID를 seeded shuffle한 baseOrder를 만든다. Tick T의 우선순위는 rotateLeft(baseOrder, (T - startTick) mod 3)로 정한다. 각 아이템·덫은 그 Tick의 유효 후보만 필터링한 뒤 첫 후보를 선택한다. 항상 같은 슬롯이나 수신 순서를 쓰지 않는다. 테스트는 서버 seed·Tick·후보 집합을 고정한다. 참가자에게 이를 장거리 위치 정보로 전송하지 않는다.

13.2 자동 획득과 사용의 실행 계약

이동 완료로 새 셀에 진입한 ACTIVE 도망자 중 획득 단계에서 슬롯이 빈 사람만 후보가 된다. 포획된 사람은 제외하되 구속 상태만으로 획득을 금지하지는 않는다. 보유 중인 아이템을 같은 Tick에 사용해 비웠더라도 획득 단계가 먼저였으므로 해당 셀의 아이템을 뒤늦게 자동 획득하지 않는다. 다시 진입해야 한다.

획득은 필드 오브젝트 제거, 동일 itemInstanceId의 인벤토리 이전, acquiredTick = T 기록을 한 번에 커밋한다. USE_ITEM은 itemInstanceId를 필수로 보내며 T 시작 시 그 항목을 보유했고 acquiredTick < T일 때만 수용한다. 불일치·빈 슬롯 요청은 거절하고 다음 Tick으로 재예약하지 않는다.

덫과 해제 도구가 같은 셀에 있는 경우

이 배치를 금지하지 않는다. 빈손 도망자는 T에서 덫 발동 → 해제 도구 획득 순서로 처리되고 같은 T의 사용은 불가하다. T+1 이후 별도 사용 요청으로 해제할 수 있다. 원래 해제 도구를 보유한 도망자는 T에서 구속 직후 사용할 수 있으나 이미 소모된 덫은 되살아나지 않고 포획은 되돌릴 수 없다.

AUDIO RULES

14. 근거리 음성과 효과음

같은 팀이라는 이유로 멀리 있는 음성을 전달하지 않는다.

모든 플레이어에게 동일한 가청 규칙을 적용한다. 팀 무전·전역 음성·전역 텍스트·좌표 핑은 없다. 실제 마이크 소리에는 말·웃음·비명을 포함하고 마이크는 선택이다. 음소거·장애는 자연스럽게 음성 단서만 없애며 발소리·가시성을 없애지 않는다.

첫 가청 거리 모델은 통로 최단거리 5셀을 진입 기준, 6셀을 종료 기준으로 하는 완충 구간이다. 5~6셀에서도 감쇠된 근거리 소리로 정의하며, 6셀 밖은 구독 종료 대상이다. 벽 너머는 경로 우회·코너 수에 따른 감쇠와 로우패스 필터를 적용한다. 무제한 벽 투과 계산은 하지 않는다.

서버가 listener별 audible speaker 관계와 상대 방향·gain·필터 등 파생값을 계산한다. 시야 밖 발화자의 원본 월드 좌표는 보내지 않는다. 방향·음량 자체로 대략적인 위치를 추정할 수 있는 것은 게임이 허용하는 정보지만 정확한 위치 노출이 완전히 0이라고 표현하지 않는다.

발소리는 한 칸 완료 시 게임 사건으로 생성하고 초기 반경은 경로 4셀이다. 회전만 하면 발소리는 없다. 실발소리·미끼·장비 사용음은 별도 위치 사건으로 필터링하며 영구 맵 표식으로 바꾸지 않는다.

브라우저 재생

받은 오디오는 Web Audio의 Source → Filter → Gain → Panner → Destination 그래프로 처리한다. 동일 트랙을 audio 요소에도 연결해 두 번 재생하지 않는다. 사용자 제스처로 AudioContext를 시작하고 점검 화면에서 음량·헤드셋·재생 상태를 확인한다.

수신 제어와 표현의 차이

autoSubscribe=false나 gain=0만으로 접근 제어가 완성되지 않는다. 실제 SFU 수신 제한은 19장 검증 관문을 통과해야 한다. 전환 중 이미 버퍼링된 짧은 소리는 0ms 차단을 보장하지 않으며, 측정된 종료 지연 기준으로 관리한다. [S3][S4]

명령 payload 4KB, 지속 30개/초·짧은 burst 60개, Room 큐 상한을 초기 방어값으로 둔다. sequence 중복·역행은 무시하고 범위·역할·matchId 불일치는 거부한다. 게임 시작과 재경기 시 이전 matchId 명령은 전부 무효다.

서버시간은 monotonic clock 기반이고 각 클라이언트는 시각적 시간 오프셋만 추정한다. 이벤트는 적용 대상 stateVersion을 명시해 서로 다른 수신 경로의 순서를 검증한다. 재접속 기능 없이도 연결 중 상태 불일치에는 해당 플레이어 전체 뷰를 다시 전송할 수 있다.

IDENTITY & ACCESS

18. 로그인 없는 세션과 제한 공개

계정은 없지만 방 접근 자격은 서버가 검증한다.

운영자가 공유한 테스트 초대 토큰을 통과한 사용자만 방을 생성하거나 들어온다. 공개 방 목록은 제공하지 않는다. 기억하기 쉬운 방 코드는 탐색용 식별자이고, 별도 고엔트로피 초대 토큰은 URL fragment로 전달해 Referer·접근 로그에 남는 위험을 줄인다.

서버는 닉네임과 별개로 난수 playerId·sessionId를 발급하고 초대 범위·Room·만료·슬롯을 메모리에 묶는다. 같은 세션의 중복 입장은 새 슬롯을 만들지 않으며 기존 연결을 밀어낼지 거절할지 정책은 “거절”로 시작한다. 입장·장치·미디어 토큰 발급은 모두 이 세션을 검증한다.

접근 수단초기 정책
방 세션최대 2시간, 활동 중 갱신. 방 종료·강퇴 시 서버 레지스트리에서 무효화.
LiveKit JWT참가 직전에 5분 유효한 roomJoin 토큰 발급. roomAdmin·record·screen-share·data 권한 부여 안 함.

토큰 만료이미 연결된 세션을 exp 시각에 자동 종료한다고 가정하지 않음. 서버 퇴장·권한 회수 API 사용.
외부 공격HTTPS/WSS, 허용 Origin, 입력 검증·시도 제한, 토큰·raw SDP·미디어 원본 로그 금지.

LiveKit 자격은 백엔드가 발급한다. API Secret과 운영자 자격을 Vite 환경변수나 브라우저 번들에 넣지 않는다. JWT는 역할·게임 결과를 클라이언트가 주장하는 수단이 아니다. [S4]

방 생성 rate limit은 초대 토큰 단위 우선으로 적용하고 IP 제한은 학교 NAT 공유를 고려해 넓게 설정한다. 만료된 대기 방과 빈 방은 자동 제거한다. 운영자는 새 방 생성 중지·방 무효화·참가자 제거를 수행할 수 있지만 게임 중 은밀한 위치 공개 기능은 넣지 않는다.

18.1 미디어 토큰 발급·회수 장벽

서버별 serviceNamespace·serverEpoch·mediaRoomName·mediaIdentity를 관리한다. 서비스 전용 이름 공간은 다른 서비스의 방과 구분하되 역할·좌표·출구를 노출하지 않는다. 같은 논리 플레이어라도 전체 연결 재생성, 연습→본 경기, 새 매치는 새 원격 Identity를 사용한다. SDK의 짧은 동일 세션 재연결과 새 연결을 구분하고, 종료된 Identity에는 새 토큰을 발급하지 않는다.

발급 순서: 게임 세션·상태·미디어 예산 검증 → 정리 저널에 PREPARED(원격 식별자·세대·발급 시각·예정 만료) 기록 및 디스크 반영 → JWT 생성 → 현재 허용 상태 재확인 → 클라이언트 반환. 기록 실패 또는 중간 종료면 반환하지 않고 회수 대상으로 둔다. 응답 전 서버가 죽거나 토큰만 받고 아직 입장하지 않은 Identity도 저널로 추적한다. 원본 JWT와 Secret은 저장하지 않는다.

RemoveParticipant의 Cloud 토큰 회수와 종료 Identity 재발급 금지를 함께 적용한다. 공식 문서는 이탈한 Identity의 회수, revoke_token_ts 기준 및 60초 이내 시각 조건을 설명한다. 기본 회수 시각·버퍼를 사용하는 동작과 고정 SDK 지원을 G1에서 확인한다. 단순 room 삭제·JWT exp·로컬 레지스트리 삭제를 토큰 회수 증거로 삼지 않는다. [S4][S14]

반드시 실증할 경계

발급 후 한 번도 입장하지 않은 토큰, 연결 중 Cloud가 갱신한 토큰, 제거 직전 재접속 시도도 회수 후 거절되는지 시험한다. 공급자 문서의 일반 동작을 모든 경계의 재현 결과로 간주하지 않는다. 해당 세대의 회수가 확인되기 전에는 종료 장벽을 통과시키지 않는다.

MEDIA AUTHORIZATION

19. LiveKit 경계와 필수 검증 관문

Cloud 사용은 확정했지만 강한 근거리 접근 제어의 성공은 아직 검증되지 않았다.

게임: 브라우저 ↔ WSS ↔ Colyseus 미디어: 브라우저 ↔ WebRTC ↔ LiveKit Cloud 제어: 게임 서버 → HTTPS RoomService / 단기 토큰

LiveKit Cloud가 SFU·미디어 시그널링·ICE·STUN/TURN 경로를 담당한다. Nginx·Colyseus는 영상·음성 데이터를 중계하지 않는다. LiveKit Agents·Inference·SIP·Ingress·Egress 녹화는 사용하지 않는다. 브라우저는 마이크 1트랙(선택)과 가공 얼굴 1트랙만 게시한다.

기본 미디어 설계는 autoSubscribe=false, 서버가 계산한 청취 관계에 대한 선택 구독이다. 하지만 이것만으로 변조 클라이언트의 직접 subscribe를 차단했다고 쓰지 않는다. 참가자·트랙 권한과 관리 API가 실제로 어떤 조합에서 강제되는지 LiveKit Cloud에서 검증한다. [S3][S4]

G1: 구현 1일 차 차단 검증

canSubscribe=false인 참가자를 관리 API로 선택 구독시킬 수 있다는 전제를 먼저 시험한다. 공식 저장소 이슈 #4651에는 특정 서버/SDK 버전에서 이 동작이 실패했다는 보고가 있다. 이는 현 Cloud의 실패를 입증하지는 않지만 성공을 가정할 수 없게 한다. [S13]

합격 조건: 허용 오디오는 수신되고, 범위 밖 오디오의 직접 구독 시도는 거부되며, 탈락자의 재구독도 차단되고, 복구 후에도 이전 권한이 살아나지 않아야 한다. 이 기능이 조합상 지원되지 않으면 SDK 기능을 재검토한다. 단순 전체 음성+음소거 방식으로 몰래 격하하지 않으며 공개 완료를 보류한다.

G2: 무료 API 한도

Server API 기본 한도는 프로젝트당 분당 1,000회다. 게임 20Hz × 60명마다 API를 호출하면 72,000회/분이므로 사용할 수 없다. 가청 관계 계산은 로컬에서 수행하고 변경만 참가자별 묶음 요청으로 보낸다. 상한 600회/분을 운영 목표로 두고 퇴장·차단용 여유를 남긴다. [S1]

변경 작업은 최신 목표 상태로 합치고 아직 발송하지 않은 허용보다 차단을 우선한다. 이미 발송된 작업은 로컬에서 취소했다고 원격 적용까지 취소됐다고 볼 수 없다. 아래 계약을 따른다. 제어 강제 실패·결과 불명은 새 허용과 신규 경기 발급을 중지하고 종료 경로로 처리한다. 10방에서 호출량·권한 지연 기준을 넘으면 수용량 검증 실패다.

19.1 원격 변경을 직렬화하는 단위

정상 관리 변경의 키는 (mediaRoomName, receiverIdentity, mediaGeneration)이다. 동일 실제 원격 Identity를 건드리는 허용·차단·권한 변경을 하나의 제어기에 모으고 동시 일반 요청은 1개로 제한한다. 재시도·다른 Room 콜백이 별도 경로로 같은 대상을 변경하지 못하게 한다. 다른 수신자는 전역 호출 예산 내에서 병렬 처리할 수 있다.

desiredTracks(현재 허용 목표), acknowledgedTracks(API 응답으로 알려진 상태), inFlight, policyVersion을 따로 보관한다. acknowledged는 실제 수신 검증 완료를 뜻하지 않는다. 대기 중 변경은 최신 목표로 덮어쓰고, 실행 직전 역할·개인 종료·연결 세대·현재 SID를 다시 검사한다. 차단 목록을 먼저 완료한 뒤 허용 목록을 전송하고 각 응답 뒤 최신 목표와 다시 대조한다. UpdateSubscriptions에는 앱 정책 버전 비교 필드가 없으며, 한 요청의 subscribe 값은 공통이므로 추가·제거는 필요시 별도 요청이다. [S4]

19.2 타임아웃·오래된 허용·종료 경쟁

상태필수 처리
정상 변경 중 목표 변경이미 실행 중인 일반 요청의 확정 응답을 기다린 뒤 최신 목표로 수렴. 그 사이 추가 허용 병렬 실행 금지.
응답 불명첫 API 응답 기한 1,000ms. timeout·응답 유실 등 적용 여부 불명은 UNKNOWN으로 전환. AbortController/HTTP 취소가 Cloud 변경을 취소했다고 가정하지 않음.
UNKNOWN / 보안 차단 지연차단 목표 생성 후 1,000ms 안에 제어 완료를 확인하지 못한 경우도 포함. Identity를 RETIRING으로 고정하고 새 허용·자동 재입장 금지. 진행 매치는 MEDIA_POLICY_UNCERTAIN 무효 후 24장 회수.
단말 로컬 차단정상 클라이언트에 음향 출력·게시 중지 요청. 이는 임시 피해 완화일 뿐 변조 단말 차단의 근거는 아님.
종료 전용 예외불명 요청을 무한 대기하지 않고 종료 장벽에서 RemoveParticipant/회수·확인을 실행할 수 있음. 이 경우 일반 변경 직렬화의 예외지만 해당 Identity는 영구 폐기하며 다시 열지 않음.
지연 응답 도착세대·requestId 검증 후 진단 기록만 반영. RETIRING/CLOSED에서 ACTIVE로 복귀하거나 새 Identity 권한에 적용 금지.
회수 확인 실패신규 토큰 발급·공개 중지 유지. 재시도·운영자 확인 대상으로 남기며 정리 성공으로 표시하지 않음.

종료 장벽은 더 늦은 일반 구독 요청이 참가자를 되살리거나 옛 토큰으로 재입장시키지 못한다는 G1 시험을 전제로 한다. 성공 응답 하나만으로 타임아웃 이전 부작용이 모두 사라졌다고 단정하지 않는다. 429·재시도 소진·원격 상태 확인 불가도 안전한 차단을 “시도 중”으로 기록한다. 전체 시스템 중단 중의 강제 종료 보장 범위는 24.3에 한정한다.

19.3 트랙·연결 변경도 정책 입력이다

가청 거리 변경 외에도 TrackPublished/Unpublished, trackSid 변경, ParticipantConnected/Disconnected, 전체 미디어 재연결, room 전환, 탈출·포획이 재계산 조건이다. 개별 수신 클라이언트의 보고만 신뢰하지 않고 서버 검증된 webhook 또는 RoomService 조회 등으로 현재 참가자·게시 트랙을 확인한다. webhook을 쓰면 서명·중복·순서 역전을 처리하며 불확실할 때만 조회한다.

새 트랙은 현재 논리 플레이어·원격 Identity·세대·source 매핑이 확인되고 역할·거리·개인 종료를 다시 검사하기 전 기본 차단한다. 얼굴 사전 수신도 현재 활동 참가자의 가공 얼굴 트랙에만 적용한다. 이전 SID의 대기 작업은 폐기하되 실행 중 요청은 19.2로 종결한다. 소스 교체마다 SID가 반드시 바뀐다고 가정하지 않고 현재 게시 목록과 비교한다. [S3][S4]

19.4 호출 예산과 권한 적용 계측

분당 600회는 정상 10방 운용의 전체 관리 API 목표다. 구독·권한·토큰 회수·조회·룸 생성/삭제·재시도 호출을 전부 포함한다. 프로젝트 전체의 최근 60초 창을 하나로 제한한다. 첫 구현은 정상 목표 600회, 긴급 회수 포함 내부 안전 상한 900회로 시작해 공식 1,000회 대비 여유를 둔다. 이는 공급자의 보장 용량이 아니며 G2 정상 구간에서 600회를 넘기면 합격이 아니다. 정리와 허용이 경쟁하면 허용을 멈춘다. [S1]

참가자당 평균 6초에 한 번이라는 환산을 고정 폴링·차단 지연으로 사용하지 않는다. 정책 결정 시각, enqueue, 발송, API 응답, 실제 수신 효과 확인을 각각 측정한다. API 응답 지연과 실효 미디어 차단 지연은 별도 지표다. 불허 전부터 전달된 패킷·버퍼와 차단 효과 후 새로 전달되는 미디어를 구분한다. 시험은 합성 오디오/영상 표식과 트랙별 통계를 사용하고 실제 사용자 얼굴·음성을 녹화하지 않는다.

22.1 정리에 필요한 최소 운영 기록

사용량 체크포인트와 media issuance/revocation 저널은 컨테이너 임시 레이어가 아닌 서버의 지속 볼륨에 둔다. 저널에는 serviceNamespace, serverEpoch, match 참조, mediaRoomName, mediaIdentity, 세대, 발급 시각/예정 만료, PREPARED/REVOKING/REVOKED/UNRESOLVED 상태만 저장한다. JWT·Secret·사용자 닉네임·위치·맵·원본/가공 미디어는 넣지 않는다.

단일 쓰기자·순번·부분 레코드 감지·원자적 체크포인트 교체·필수 디스크 반영을 적용한다. 보안 발급·종료 확인은 기록 반영 뒤 완료하며 동기 디스크 IO를 GameCore Tick 안에서 호출하지 않는다. 첫 보관 정책은 종료·회수·공식 사용량 조정 확인 후 24시간 동안만 유지하고 압축·삭제하는 것이다. 미해결 기록은 자동 삭제하지 않고 운영 경보로 남긴다. 저장 실패·손상 시 발급을 잠그고 복구 전 운영을 재개하지 않는다.

24.1 미디어 종료 장벽

종료 시작 시 논리 플레이어·미디어 세대를 terminal로 표시하고 새 token·publish·subscribe 허용을 차단한다. 정상 클라이언트는 원격 오디오 출력을 즉시 끄고 게시 중지, Room.disconnect, 전체 미디어 재연결 취소, 로컬 트랙 중지·객체 폐기를 수행한다. 게임 중 카메라 폴백만 발생한 경우에는 이 전체 종료를 실행하지 않는다.

서버는 RETIRING/REVOKING을 저널에 남기고 RemoveParticipant와 Cloud 토큰 회수를 해당 구 Identity에 실행한다. 구독 큐의 일반 허용은 더 이상 발송하지 않는다. 참가자 부재·토큰 회수 응답을 확인하고 방 전체 종료면 기록된 모든 Identity를 회수한 다음 DeleteRoom을 요청한다. 방이 비었다는 조회 결과만으로 미입장 토큰까지 회수됐다고 기록하지 않는다. [S4][S14]

관리 호출 timeout/429는 결과 불명으로 남긴다. 조회·회수 재시도는 최신 시각 기준으로 최대 1·2·4초 간격으로 진행하고 첫 정리 목표 10초를 넘기면 UNRESOLVED 경보를 남긴다. API 예산을 우회하는 무제한 재시도는 금지한다. 정상 확인 전에는 예약 사용량·슬롯의 미디어 점유분을 유지하며 결과 화면 표시와 회수 성공 표기를 분리한다.

24.2 부팅·재시작 정리

새 프로세스는 RECOVERING에서 시작한다. ① 지속 저널과 예산 체크포인트 복구 ② 서비스 소유 LiveKit 방 목록과 이전 serverEpoch의 기록 대조 ③ PREPARED를 포함한 발급 Identity별 회수 ④ 이전 방 삭제와 잔존 참가자 재확인 ⑤ 사용량 예약·공식 잔량 정합 확인 ⑥ READY 순서다. 전용 이름 공간 밖 방은 삭제하지 않는다. 첫 설치 역시 “남은 방이 없을 것”이라고 가정하지 않고 서비스 소유 목록을 확인한다.

목록에는 없지만 저널에 남은 Identity도 회수한다. 저널에 없는 서비스 소유 잔존 방은 알려진 소유 범위에서 조회·회수 후 제거한다. 손상·유실된 저널 때문에 발급 이력을 복원할 수 없다면 현재 참가자만 지우고 재개하지 말고 운영자 확인과 G1 회수 검증 전까지 신규 발급을 막는다. 다른 서비스 방 정리, 기존 사용자 토큰 재발급, 사용량 0 초기화로 복구를 대신하지 않는다.

24.3 보장 범위와 중단 원칙

강제 종료의 한계

정상 클라이언트는 게임 서버 상실을 감지하면 미디어를 끊는다. 게임 서버가 살아 있거나 재시작한 뒤에는 Cloud 회수를 시도·확인한다. 하지만 AWS 호스트 전체 장애 중 변조 클라이언트를 정해진 시간 내 강제 종료하는 독립 감시자는 MVP에 없다. Cloud 제어도 불가하면 즉시 원격 차단을 보장하지 않는다. 이 경우 공개 중단·운영자 경보·미해결 기록을 유지하며 복구 후 우선 정리한다.

엄격한 무중단 외부 강제 회수를 요구하게 되면 별도 장애 도메인의 감시자가 필요한 새 요구사항이다. 이번 보완을 이유로 유료 Cloud·추가 서버·DB를 자동 도입하지 않는다. 토큰 TTL만으로 현재 연결·갱신 토큰 문제를 해결했다고 쓰지 않는다.

이번 주의 첫 차단 요소

LiveKit 강제 구독 제어의 실제 동작, 무료 API 한도 안의 청취 관계 갱신, 얼굴·비전·3D 동시 성능을 D1부터 확인한다. 후반까지 미루면 완성된 게임 규칙을 다시 바꾸거나 미디어 구조를 재설계할 수 있다.

핵심이 미완성인 경우 공개일을 미루고 통합 중간본으로 표기한다. 10방 검증만 남았다면 기능 완성 여부와 부하 미검증을 나란히 기록하고 실제로 검증된 방 수까지만 운영한다. 사용자 승인 없이 유료 플랜이나 별도 서버 증설로 해결하지 않는다.

남는 것은 사용자 선택이 아니라 외부 사실과 시험

실제 AWS 상품명·세대·리전·Ubuntu 버전·도메인/TLS·남은 LiveKit 할당량·대표 사용자 장치·현재 코드 진척을 배포 전에 확인한다. 게임 콘텐츠·기술 선택을 다시 하나씩 묻지 않고 본 기본안으로 진행한다. 단, 핵심 필수 요구와 플랫폼 한도가 양립하지 않는 것으로 입증되면 그 충돌을 명시해 범위나 운영 조건 승인을 받는다.
