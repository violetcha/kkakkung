# 분리 미디어 전달 요청의 내구 기록

관련 Jira는 [S15P21C204-215](https://ssafy.atlassian.net/browse/S15P21C204-215)다.
[서버 제어 조립](split-media-policy.md)의 후속으로, 전달 요청의 결과가 불명확한 상태에서
서버가 재시작해도 그 불확실성을 보존한다. 운영 팀원 제한과 공개 미디어 설정 차단은 유지한다.

## 해결하는 문제

기존 ForwardedMediaEdge는 결과가 불명확한 전달 요청을 메모리의 unknownForward로
기록했다. 같은 프로세스의 회수는 막았지만 재시작하면 해당 상태를 잃었다.
복구 시점의 참가자 부재만으로 이전 요청의 지연 효과까지 없다고 입증할 수 없으므로,
이 경로에서 회수 완료·사용량 정산·새 발급을 허용하면 안 된다.

## 저장과 종료 순서

제품 Coordinator는 실제 forward 호출 전에 OperationJournal.prepareForward를 사용한다.
세대의 불변 소유 범위 안에서 원본 방·신원·목적지와 고유 작업 ID를 기록하고 fsync한 뒤
전달을 시도한다. 한 세대는 최대5개 목적지의 얼굴/음성10개 미종결 요청만 보유한다.
토큰·얼굴·음성은 저장하지 않는다.

기존 저널의 직렬 큐에서 최신 세대 기록에 요청을 추가하거나 제거한다. 다른 edge의
동시 요청과 일반 회수/retry 기록이 미종결 목록을 덮어쓰지 못한다. 실제 응답이나
전송 전 확정 거절을 관측한 실행 중 프로세스만 종결 handle을 갖는다. 알려진 응답의
기록이 끝나더라도 전달본과 원본의 소유 범위·회수·부재 검사는 계속 필요하다.

재시작으로 복원한 요청에는 종결 handle이 없다. 복구는 원본/전달본 회수를 시도하되
미종결 요청이 남으면 FORWARD_EFFECT_UNCONFIRMED를 유지한다. 토큰 만료, 한 번의 부재,
반복 sweep이나 기록 축약은 이를 성공으로 바꾸지 않는다. REVOKED에 미종결 요청이
포함된 기록 자체도 거절하므로 예약 정산과 READY 복귀를 우회할 수 없다.

## 호환성과 인수 경계

새 forwardIntents 필드는 선택적이며 기존 단일 모드 기록과 기존 split 소유 기록을 읽는다.
구 reader는 새 필드를 모르는 엄격한 파서이므로 새 필드가 기록된 저장소를 구 이미지로
곧바로 되돌리면 정상 부팅을 보장할 수 없다. 현재 운영 모드는 이 필드를 쓰지 않으며,
새 reader가 배포된 뒤에만 검증된 분리 모드 쓰기를 활성화해야 한다.

파일 복원·동시 요청·기록 축약·지연 효과 시험 결과와 실제 Cloud 관측을 구분한다.
이번 변경만으로 실제 Cloud의 지연 전달·제품 HTTP/웹·전체 G1 통과를 선언하지 않는다.
예약 일부 성공 뒤 소유 기록 이전 crash는 별도의 발급 시작 기록이 필요한 후속 범위다.
